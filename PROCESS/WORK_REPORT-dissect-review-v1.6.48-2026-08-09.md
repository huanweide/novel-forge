# 工作单元费曼报告 · novel-forge v1.6.48 复检 dissect 拆书三页 + to-project 出口链路

> 瑞宝宝专属 · 用大白话讲清「干了什么、为什么、怎么做的、踩了什么坑」

## 一、干了什么（一句话）

用无头浏览器把 dissect 拆书模块的三张页面（列表 / 新建 / 详情）和「拆完书转成写作项目」这条出口链路，从头到尾真实点了一遍，确认它们不是「纸面能跑、一用就崩」，然后升版本、留档、推送。结论：**三页和出口都健康，没发现真故障**，所以这轮属于「健康基线确认」，没动业务代码，只更新了版本公告。

## 二、为什么这么做（拆到底层原理）

「拆书」是 novel-forge 里一个把现成小说/文稿自动拆成角色、世界观、势力、力量体系等 15 类设定、再一键转成可写作用户项目的功能。它是 v1.6.x 新加的模块，瑞宝宝还没亲自实测过。

按我们定的「检测→修复→验证→交付」循环，最稳的轮子是先确认**已经交付的功能是不是真能用**，再去动下一个。如果一上来就加新功能，万一是个「看起来写完了、一跑白屏」的空架子，那加再多新功能也是沙上筑塔。

所以本轮派马斯克人格执行 CEO 子 Agent 拍板，它选了 A 序列（dissect / workshop / settings / recycle / game 依次实跑）的第一个——dissect，先做健康确认。

## 三、用了什么方法 / 工具、效果如何

**工具：agent-browser（一个用命令行驱动的无头 Chrome 浏览器的工具）**。它能在没有显示器的情况下，真实打开网页、点击按钮、读页面内容，比「只看代码猜它能跑」可靠得多。我们之前 v1.6.44/46/47 已经把它跑顺了：先开一个浏览器实例保持住，之后命令都连同一个实例；点完用读网址的方式确认跳转成功（因为 Next.js 这种框架切换页面比较慢，不能点完就立刻判断）；页面慢就多等几秒。

**实跑过程（按时间顺序）：**

1. **列表页**：打开 `/dissect`，显示「还没有拆书任务」+「新建拆书」按钮，没有报错、没有白屏。
2. **新建页**：打开 `/dissect/new`，表单字段齐全（任务名称 / 原书名称 / 原书作者 / 上传文件 / 粘贴文本 / 拆解深度三档 quick·standard·deep / 开始拆解），点提交没报错。
3. **真正建一个任务**：直接调后端接口 `POST /api/dissect/start`（quick 深度，原文约 230 字），建出任务 `30050f95`，等了 51.6 秒拆解完成（流程是：先分章 → 再提取 15 个维度 → 标 completed），没超时没异常。
4. **详情页**：打开 `/dissect/30050f95...`，15 个维度全显示出来了——角色 1400 字、故事核心 330 字、世界观 378 字、地图 327 字、势力 290 字、特殊设定 240 字、力量体系 245 字、功法 188 字、货币 169 字等，共 13 个角色、12 条世界书词条，连文笔风格分析都有，页面零 React 报错、不白屏。
5. **出口链路（最关键的）**：调 `POST /api/dissect/[id]/to-project` 做「原样转换」，返回 HTTP 200，给出新项目 ID `762db094`，`adapted=false`（意思是 100% 忠实还原、没擅自改原著设定）。这条链路一通，就证明「拆书 → 建项目」是真的能用的。

**效果数据**：三页渲染健康率 100%，核心出口 HTTP 200 成功，15 维度提取数据量正常（单维度百字级），无报错。

## 四、关键取舍（为什么这么选、踩了什么坑）

- **为什么不改代码只升公告？** 因为实跑没暴露真故障。强行找 bug 改代码是空转，违背「不空转」铁律。这轮的价值是把「dissect 真健康」这个结论坐实并留档，给后续 workshop 等轮子铺路。
- **测试产物必须清掉**：实跑时建的任务 `30050f95` 和转出来的测试项目 `762db094` 都是垃圾数据，不是瑞宝宝的真作品。我查了后端删除接口——dissect 任务用硬删（`DELETE /api/dissect/[id]`，直接从库里抹掉），项目用软删（`DELETE /api/projects/[id]`，打上删除标记进回收站，子表跟着隐藏）。两个接口都不需要登录（本项目单用户无鉴权），直接调：任务硬删返回「任务已删除」，项目软删返回「recycled:true」，再查列表已空。环境回到干净。
- **双门禁（质量铁门）**：升版前跑了两道关——`tsc`（TypeScript 类型检查，0 错误）+ `vitest`（测试套件，35 个文件 323 个测试全过）。虽然这轮没改业务代码，但门禁照跑不省，因为改了公告文本文件，确认它没把别的带崩。

## 五、反自欺闸门（我真的做到了吗）

- 三页和出口是我用 agent-browser **真点真调**出来的，不是看代码猜的——有接口返回的真实 JSON（任务 ID、项目 ID、adapted=false）和详情页实测的 15 维度字数为证。
- 测试产物清理是**真调删除接口并复查列表为空**确认的，不是「以为删了」。
- 诚实标注：这轮**没有**做功能增强，只是健康确认；dissect 长文拆解是否有更深问题没深挖（比如极长原文会不会超时），留后续。不假装做了没做的事。
- 个人 IP 铁律：全程只迭代 novel-forge 工程，没另立 IP / 品牌，IP 永远归瑞宝宝（樊斯瑞）。

## 六、照做就能复现的步骤

```bash
# 1. 确保 dev server 在 3001 端口跑着（Windows 管理员需 agent-browser 加 --no-sandbox）
# 2. 用无头浏览器开列表页 / 新建页 / 详情页，读内容确认无报错
# 3. 调接口建拆书任务（quick 深度，原文≥100 字）
curl -s -m 120 -X POST http://127.0.0.1:3001/api/dissect/start \
  -H 'Content-Type: application/json' \
  -d '{"taskName":"复检测试拆书","bookName":"测试书","bookAuthor":"瑞宝宝","originalText":"<粘贴≥100字原文>","depth":"quick"}'
# 4. 拿返回的 id，调 to-project 出口
curl -s -m 30 -X POST http://127.0.0.1:3001/api/dissect/<任务id>/to-project
# 5. 清理：硬删任务 + 软删项目
curl -s -X DELETE http://127.0.0.1:3001/api/dissect/<任务id>
curl -s -X DELETE http://127.0.0.1:3001/api/projects/<项目id>
# 6. 双门禁
SAFE_DELETE_DISABLE=1 npx tsc --noEmit   # 期望 0 错误
npx vitest run                           # 期望 35 文件 323 测试全过
```
