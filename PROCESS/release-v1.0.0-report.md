## 一、干了什么（一句话）

把 Novel Forge 从「功能能跑的迭代版」推到 **v1.0.0 正式版**：做了全功能与按钮 UI 巡检（0 断链）、真实用户旅程真机验证（9/9 全绿）、发布门槛全量复检，双 changelog 升版并提交；线上站部署因网络/凭据原因待用户侧收尾。

## 二、为什么这么做（第一性原理）

前 9 轮 Max Loop 把「确认体系」的功能正确性做到了极致，但**正式版的门槛不是功能多，而是"确定可用"**。正式版发布前必须回答三个问题：

1. **有没有断链？**——前端调用的接口后端是否存在、按钮点了有没有反应、页面跳转能不能到。功能再多，一个 404 就毁掉信任。
2. **真实用户能不能走通主流程？**——建项目→写章节→AI 生成→确认→交付，这是每天都会走的路，必须真机验证（不是 mock）。
3. **回归是否全绿？**——历轮 9 个版本的改动叠加，正式版发布前必须确认没有互相踩踏。

## 四、关键取舍（为什么这样做）

1. **正式版门槛选「无 bug + 全绿」而不是「清完 lint」**：lint 存量 2542 个是历史 `no-explicit-any` 债，不产生运行时 bug；正式版发布前大改代码才是真风险。增量已归零（本轮新代码全干净），存量建档待专项。
2. **用户旅程用真实 LLM 而非 mock**：mock 只能证明「接口长这样」，真机能证明「用户真的能写完一本书」——这正是"可用用户"的含义。
3. **审计脚本固化进仓库**（`audit-api-refs.cjs`）：巡检不是一次性动作，固化后 CI/发布前随时可重跑，防止未来迭代引入断链。

## 五、诚实边界（如实说）

- **push 未成功（待办）**：commit `0dbe0e9` 已就绪，但 GitHub 出口网络故障持续（代理 TLS connect error，多次重试不通）。网络恢复后执行：
  ```bash
  git -c http.proxy=http://127.0.0.1:7897 -c https.proxy=http://127.0.0.1:7897 push origin main
  ```
- **线上站（novel-forge-nu.vercel.app）停留 v0.21.2**：沙箱无 Vercel 凭据/CLI，无法代操作部署。代码已就绪（`postinstall` 自动 `prisma generate`）。需在 Vercel 控制台把项目绑定 `huanweide/novel-forge` 仓库 main 分支（或手动 redeploy），并配置 Neon 数据库环境变量——之后 push 即自动上线。
- **前端视觉未浏览器目测**：沙箱无 Chromium，交互逻辑层已验；本地 `npm run dev` 打开页面即可肉眼确认。
- **lint 存量 2542 债**：待专项清理，不影响正式版功能正确性。
