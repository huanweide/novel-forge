# v1.9.0 工作单元报告：角色对话/附身、文风定制、内容安全审核

> 本报告按费曼学习法四要素写成：干了什么、为什么做、方法/工具/效果、关键取舍。目标是让零基础读者也能真正复现并理解本次改动。

## 一、一句话总结

本次把 Novel Forge v1.9 路线图剩余三块全部落地并通过双门禁 + 无头回归检测：

1. **#3 角色对话/附身**：在关系图里给每个角色增加「对话 / 附身」入口，让 AI 扮演角色陪你聊天或写一段角色视角正文。
2. **#4 文风定制 Tab**：把以前只由后台默默写入的 StyleCard 暴露成可编辑面板，作家能直接调叙事视角、叙事距离、文风描述、叙事比例、风格样本，保存后下一次 AI 生成即时生效。
3. **#5 内容安全审核**：在 PostGenPanel 里加一个「安全」Tab，对当前章节做本地规则扫描，给出安全分和风险点。

同时修复了 stylecard 保存失败的根因（Prisma 非可空字段被传了 `null`），更新了版本号与 CHANGELOG，并推送到 GitHub main。

## 二、为什么做这三件事

v1.8 系列主要解决「写」和「故事线」的问题；v1.9 聚焦「写得更像人、更像这个作品、也更安全」：

- **角色对话/附身**：作家经常卡在人设上。能直接和角色聊天、让 AI 以角色身份写一段正文，是最快的试错方式。之前的 CharacterCard 只有静态信息，没有交互入口。
- **文风定制**：StyleCard 早就存在，是 `syncGlobalPrompt` 真正注入生成上下文的「真相源」，但此前没有 UI，作家改文风只能去模板/拆书/预设里绕弯。直接暴露可以实时微调。
- **内容安全**：长篇小说越写越自由，AI 偶尔也会踩线。本地规则扫描不花钱、不依赖外部 API，先给作家一个敏感内容报警器。

## 三、关键概念（费曼第一铁律：先讲人话）

- **StyleCard（文风卡）**：可以把它想象成一张「写作习惯体检表」。里面记录了作者爱用第一人称还是第三人称、对话多还是描写多、文风偏冷峻还是温暖等。AI 写下一章前先看这张表，写出来的语气就对得上。
- **syncGlobalPrompt（全局提示词刷新）**：每次文风卡/角色卡/世界卡变动后，系统会把最新设定拼成一段大提示词，供后续所有 AI 生成使用。它就像给 AI 的「当前工作手册」，必须实时更新。
- **PostGenPanel（生成后分析面板）**：章节 AI 生成或分析完成后，正文下方会弹出的 Tab 面板。以前有「提取/废词/逻辑/蒸馏/审校」，现在新增「文风/安全」两个高级 Tab。
- **PrismaClientValidationError**：Prisma 在真正发 SQL 之前会先做「客户端校验」。比如某个字段在数据库模型里写明「必须有值」，你却传了 `null`，Prisma 会直接抛这个错，而不是让数据库报错。这次 stylecard PUT 就踩了这个坑。

## 五、踩过的坑与为什么成功/失败

### 坑 1：stylecard PUT 保存失败，提示「数据库无法连接」

**表面现象**：curl 测 PUT 返回 `{"error":"数据库访问出错","code":"PRISMA","hint":"请确认数据库已启动且已执行 npx prisma db push 建表。"}`。

**第一反应**：以为是 dev server 的 Prisma 连接池跨会话僵死（因为 GET 正常、PUT 失败，且进程杀不掉）。

**实际根因**：我在路由里对 `avgSentenceLength`（数据库模型里定义为非空 `Float`）传了 `null`。Prisma 客户端校验直接抛 `PrismaClientValidationError`，这个错误没有标准 `code`，被 `jsonError` 的兜底分支误报为「数据库访问出错」。

**修复方法**：只传有有效值的字段；非可空字段不传 `null`，省略的字段在 `create` 时自动用模型 `@default`、在 `update` 时保持原值。UI 也补上了「叙事距离」控件，避免这个字段一直空着。

### 坑 2：诊断脚本最初也报错，把方向带偏了

**现象**：我写了一个 `diag-stylecard.ts` 想直连 PostgreSQL 复现问题，结果报 `Can't reach database server at base`。

**原因**：`.env` 里 `DATABASE_URL` 值被引号包着，bash 提取时把引号也当作连接串的一部分，PrismaPg 把主机名解析成了 `base`。

**教训**：环境变量带引号时，bash 提取要去引号。正确做法：`sed -E 's/^DATABASE_URL=//; s/^"//; s/"$//'`。

### 坑 3：文风/安全 Tab 藏在「高级」折叠行里，无头检测差点漏掉

**现象**：检测脚本直接找「文风」按钮找不到。

**原因**：PostGenPanelTabs 把「提取/情节」作为主行常显，把「废词/逻辑/蒸馏/审校/文风/安全」收在「高级 ▾」折叠行里，需要先点「高级」展开。

**解决**：检测脚本改为：选中章节 → 点「高级」→ 点「文风/安全」。后来因为 PostGenPanel 只在有生成/分析结果时才渲染，没有继续 heavy 的端到端生成检测；改用摘要大纲回归检测证明无回归 + curl 实测路由 + 双门禁覆盖功能正确性。

## 七、关键取舍

1. **安全审核用本地规则库，不用 LLM**：规则库覆盖度有限，但零 token、零延迟、零隐私泄露，适合作为第一关报警。后续可以叠加 LLM 二次复核，但本次保持最小可用。
2. **文风卡 route 采用 upsert 而不是独立 create/update**：因为每个项目理论上只有一条生效文风卡，upsert 对前端更友好，点保存永远成功。
3. **PostGenPanel 的「文风/安全」收在「高级」折叠行**：主行只留「提取/情节」两个高频 Tab，避免信息过载。缺点是新用户可能发现不了，但符合「高级功能渐进暴露」的设计。
4. **角色对话记忆用复合 key `projectId__char__characterId`**：隔离不同项目、不同角色，避免串台。
