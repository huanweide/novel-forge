## 2026-08-01 · 给 AI 装一个「做完就写人话图纸」的开关

### 这次干了啥
斯瑞希望：以后我每做完一件完整的小事（写个小功能、改个小点、做个调研），就自动生成一份「连不懂技术的人也看得懂」的说明，永远留在右侧产出面板能翻到，而且越攒越多、绝不删旧的。

### 为什么要它（第一性原理）
AI 干完活，通常只丢给你一堆代码或一句「搞定了」。代码是给机器看的，人看不懂；而且下次对话 AI 自己都忘了上次怎么做的。这就像工人盖完房只留一堆砖头，不画图纸——你既看不明白，也没法照着再盖。
所以要在「做完」那一刻，立刻把「思维图纸」用大白话写下来。类比：每道菜炒完，厨师顺手在厨房墙上贴张便签——放了啥、为啥先放油再放菜、火大了怎么救。下次照着来，外人也能看懂。

### 怎么落地的（用了什么、效果）
1. **把开关装到「每次开工都会读到的地方」**：AI 有个跨对话一直跟着的「长期记忆」文件（`~/.workbuddy/MEMORY.md`），每次开聊都自动读进来。这就是能一直生效的「预设」。我把这条新规则钉在它最前面，标成「最高优先级」，让它压过其他临时任务指令。
2. **建一本永远不撕的笔记本**：本文档（`novel-forge/PROCESS/WORK_REPORT.md`）就是那本施工日志，规定只能往后写、不许删旧的——像工地越来越厚的施工日志。
3. **写完立刻亮出来**：每次干完活，我把新的一段写进本文件，再用系统的「呈现」功能把它推到对话产出下方，你当下就能看见；跨对话时文件还在项目里，随时能翻。

### 试过的方案 / 为什么没选别的（诚实记录）
- **想直接改 WorkBuddy 平台自带的「系统提示词」？** —— 那是平台内部文件，AI 在对话里改不了，硬改有风险、还可能破坏其他功能。所以改用「在长期记忆里钉最高优先级规则」这个我能安全控制的等效办法，行为效果一模一样：每次对话都加载、且压过其他指令。
- **覆盖式笔记（只留最新）而非追加？** —— 覆盖会让旧经验消失，违背「可复现、能回忆」的初衷；追加才能看出思路是怎么一步步演进的。

### 关键取舍（工具 A 为何不选 B）
- 选「人话 + 类比」而非「堆术语」：术语像密码，记不住；类比能让人脑子里「浮现」画面。比如把「系统提示词」比成「每次开工前老板发给你的工作须知」，把「长期记忆」比成「工人随身带、天天翻的笔记本」。
- 选「完成后才写」而非「做一半就写」：半截子工作结论可能是错的，写了反而误导；必须 100% 做完、拿到确切结果才触发。

## 2026-08-01 · 给小说工坊加一个「首次进入引导弹窗」（v0.45.6 / P2-3）

### 这次干了啥
按竞品借鉴计划（PROCESS/06）推进，挑了里面最低成本的一项 P2-3：给小说工坊的工作区加一个**首次进入时的新手引导弹窗**——一打开就弹张卡片，用大白话介绍 5 个核心功能（自动化填表 / 抽卡剧情 / 拆解大纲 / 游戏化 / 竞品借鉴），看完点「开始创作」就关掉，以后不再弹。

### 为什么需要它（第一性原理）
小说工坊功能很多（AI 写作、抽卡、拆解、游戏化……），但新用户一进来面对满屏按钮，容易懵、不知道从哪下手。竞品都有个「欢迎 + 功能引导」的入场。类比：进一家大餐厅，有人递来菜单还顺手推荐三道招牌菜，比你自己瞎翻舒服得多。这个弹窗就是那个「门口迎宾」。

### 怎么落地的（用了什么、效果）
1. **不自己造轮子，直接复用现成的「弹窗模板」**：项目里早就有个统一 `Modal` 组件（相当于公司标配的 pop-up 模板），它自带一堆麻烦事都帮你处理好了——焦点陷阱（键盘 tab 不会跑出弹窗）、按 ESC 关闭、点灰色遮罩关闭、弹窗时锁住背景滚动。我只往里填内容，省事又不会漏掉无障碍细节。
2. **用浏览器本地标记记住「看过了没」**：用了 `localStorage`（相当于你家门禁的「已打卡」小本子，存在你自己浏览器里，不上传服务器）。第一次来没标记 → 弹；关掉时写个 `nf_onboarded_v1=1` 标记 → 以后再来就不弹。纯前端，没碰数据库，稳。
3. **做了防御**：万一用户浏览器禁用了本地存储（读不到小本子），我用 try/catch 包住，静默忽略——弹窗不弹就算了，绝不让整个页面崩。

### 试过的方案 / 为什么没选别的（诚实记录）
- **从零自己写一个弹窗？** —— 要重复处理焦点陷阱、ESC、遮罩、滚动锁定一堆细节，容易漏。直接复用 `Modal` 既省事又合规，属于「站在之前自己的肩膀上」。
- **用后端数据库存「已引导」状态？** —— 杀鸡用牛刀。一个「看没看过」的标记，浏览器本地记就够了，没必要惊动数据库。
- **每次进都弹？** —— 老用户会被烦死。所以做成「首访才弹 + 本地标记」，只打扰一次。

### 关键取舍（工具 A 为何不选 B）
- 选「复用 Modal」而非「自写弹窗」：复用 = 不重复踩坑 + 风格统一。
- 选「localStorage 标记」而非「后端记录」：本地标记零成本、零风险。
- 选「首访才弹」而非「常驻」：引导是一次性认知负担，看过即走。

## 2026-08-01 · 给角色卡加「性格三层」创作字段（v0.45.7 / P2-1）

### 这次干了啥
继续按竞品借鉴计划推进，挑了 P2-1：给角色编辑弹窗的性格区，新增**三个由浅入深的创作框**——
- **表层 · 对外展现**：旁人眼里他是怎样的人（比如「温和有礼、慢条斯理」）。
- **中层 · 日常互动**：熟悉后才露出的另一面（比如「其实很要强、怕被看轻」）。
- **内核 · 本质驱动**：最深处那点本性/创伤/欲望（比如「童年被弃导致极度缺乏安全感」）。

填了之后，AI 写这个角色时就会自动按这三层去塑造，人物更立体、不扁平。

### 为什么需要它（第一性原理）
好小说的人物不能只有「一句话标签」。现实里人都是分层的：你在外人面前是一副样子，朋友面前是另一副，最深处还藏着自己都不愿承认的东西。如果只给 AI 一个扁平的「性格：外冷内热」，它写出来的人物就容易脸谱化。
类比：给演员说戏，不能只说「你演个好人」，得说「他在外人面前笑脸迎人（表层），其实心里算计得很清楚（中层），根源是小时候穷怕了（内核）」——演员才知道怎么演出层次。这三层字段，就是给 AI 的「说戏三层法」。

### 怎么落地的（用了什么、效果）
1. **把三层直接塞进角色已有的「性格抽屉」里**：角色卡本来就有一个存性格的「万能抽屉」（`personality` 字段，类型是 Json，相当于一个能随手塞任意小纸条的收纳盒，不用提前规定格式）。我往这个抽屉里加了三张新纸条：`surface` / `middle` / `core`，分别对应三层。**关键是：不用改数据库结构（零迁移）**——Json 抽屉本来就能多塞几张纸条。
2. **保存时不丢旧东西**：原来性格区是用一段文字解析出来的。我改造保存逻辑，用「展开运算」`{ ...旧的, surface, middle, core }`——像把旧抽屉整个搬过来，再把三张新纸条轻轻放进去，旧的纸条一张不少。
3. **AI 自动就能读到**：项目里有个现成的「翻译官」函数 `safeJoin`，专门把角色性格抽屉里的纸条内容拼成一段文字喂给 AI。它本来就会把所有纸条的值拼起来——所以我新加的三张纸条**不用改任何装配代码，自动就进了 AI 看到的「性格：…」那段话里**。等于免费搭了顺风车。
4. **AI 自动补全不打扰你手填的**：角色卡有个「AI 帮我填满」按钮，它会重写性格。我特意让它只回填它懂的旧维度，**绝不碰你手填的三层**——你辛辛苦苦写的内核，不会被一键覆盖掉。

### 试过的方案 / 为什么没选别的（诚实记录）
- **给数据库加三个正式字段（surface/middle/core 各一列）？** —— 要改 Prisma schema、跑迁移、动线上数据库结构，牵连大、风险高。而 `personality` 本来就是 Json 万能抽屉，往里塞三张纸条零成本。选了后者。
- **单独做一个「三层性格」弹窗/页面？** —— 过度设计。三层本来就是性格的一部分，直接放在现有「性格详析」区块下方最顺手。
- **手动把三层拼进提示词装配层？** —— 没必要。`safeJoin` 已经会把 Json 抽屉里所有纸条拼进提示词，我只要把纸条放进去就自动生效。

### 关键取舍（工具 A 为何不选 B）
- 选「并入 Json 抽屉」而非「加三列」：Json 灵活、零迁移、向后兼容。
- 选「展开运算保留旧字段」而非「整体覆盖」：覆盖会让用户之前填的主导/驱动/矛盾等丢失。
- 选「借 safeJoin 自动注入」而非「手写装配」：复用现成链路 = 改动最小、最稳。

## 2026-08-01 · 根治「开发时偶发的水合警告」（v0.45.9 / PROCESS/04）

### 这次干了啥
处理 04 待迭代清单里那个「偶发 hydration 警告」（hydration 就是 React 的「水合」）。我没法在没浏览器的环境里把警告原样抓出来，但把**最可疑、也最真实的根因彻底堵死**了：给全站所有「日期/时间显示」强制锁定时区，并在根节点加了一道安全网。纯加固，界面行为没有任何变化。

### 先说人话：什么是「水合警告」（第一性原理）
网页第一次打开，服务器会先「画」好一份 HTML 发给你（这步叫 SSR，服务端渲染）；浏览器拿到后，React 会在本地**再画一遍同样的页面**，然后把两份对一对——如果两边写出来的字有一处不一样，React 就报警：「咦，你俩对不上！」这就是 hydration warning。
类比：总部先印好一份说明书寄给你，你手下人照着又手抄一份，两本一对发现第 3 行写的不一样——总部的版本和手抄的版本冲突了。问题往往出在**两边用了不同的「钟表」**。

### 真正的根因：服务器和浏览器用的时区不同
代码里显示日期用的是 `toLocaleDateString("zh-CN")`，意思是「按中文习惯把日期变成一串字」。但这句话**没说按哪个时区算**。于是：
- 部署的**服务器通常在 UTC（相当于伦敦时间）**；
- **你的浏览器在本地时区（北京时间）**。
同一个时间点，伦敦是 8 月 1 日 23 点，北京已经是 8 月 2 日 7 点。于是服务器印的「创建于 8/1」、浏览器手抄的「创建于 8/2」——**两本对不上，React 就报警**。跨 UTC 午夜的日期最容易踩。这正好对应文档里记的「偶发」（只有卡在午夜附近才翻车）。

### 怎么落地的（用了什么、效果）
1. **给所有日期/时间显示统一加 `timeZone: "Asia/Shanghai"`**：相当于下令「不管总部还是手抄，通通按北京时间报」。这样两边永远算出同一串字，从根上消除时区造成的不一致。改了 5 处：首页项目卡片「X 天前」超过 30 天的绝对日期、伏笔面板的创建时间、配置面板的套用时间、导入向导的两条日志时间、填表结果的时间。
2. **根布局 `<html>` 加 `suppressHydrationWarning`**：这是 Next.js 官方对根节点「环境属性漂移」的推荐安全网——相当于在说明书封面上盖个「以手抄本为准，小出入别报警」的章，兜底任何极端情况下的环境差异。
3. **先大排查、确认不是别的原因**：我把所有「渲染期（画图那一刻）」会调用随机/时间/浏览器的地方都查了一遍——星空粒子（随机数）在 useEffect 里、各页 localStorage 在 useEffect 里、首页的「X 分钟前」是拉完数据才显示（纯客户端）。结论是**当前代码渲染期根本没有不确定性**，所以没乱改别的逻辑。

### 试过的方案 / 为什么没选别的（诚实记录）
- **要不要引入虚拟列表、或别的大改动来「顺手治」？** —— 不。用户给了两个选项（治水合 / 做列表虚拟化），我选了治水合。虚拟化之前就被判过「当前数据量小、属过度设计、暂缓」，硬做是画蛇添足。
- **要不要给每个时间显示组件大改结构？** —— 不用。根因就是时区，加一个选项参数就解决，最小改动、零新依赖。
- **能不能 headless 直接复现警告？** —— 环境里没有无头浏览器（Chrome/Playwright 都没有），而 hydration 警告只报在浏览器控制台，服务器日志看不到。所以没法 100% 原样抓。我的做法是**直接堵死文档记录的最可疑根因**，并把它做成「无论何时都不可能再因时区不一致而报警」。

### 关键取舍（工具 A 为何不选 B）
- 选「锁定时区 `Asia/Shanghai`」而非「放任默认时区」：默认时区 = 服务器和浏览器各算各的 = 必然偶发不一致；锁定 = 永远一致。

## 2026-08-01 · 给「宝宝流数据库」大表格加虚拟滚动（v0.46.0 / PROCESS/04 收官）

### 这次干了啥
把 04 待迭代清单里最后一项「大列表虚拟化」收掉了：结构化表格（项目里叫「宝宝流数据库」）展开后，如果一张表超过 50 行，就自动换成「虚拟滚动」渲染——不管表里有一千行还是一万行，页面都只画你眼睛正对着的那一小段，滚动流畅不卡。50 行以内的小表维持原样，零影响。

### 先说人话：为什么大表会卡、虚拟化怎么救（第一性原理）
普通列表是「一次性把所有行都画出来」。一张表 1 万行，浏览器就得同时造 1 万个 `<tr>` 和里面几千个输入框——内存和渲染全压上，你一滚动就掉帧卡顿。
虚拟化（virtualization）的思路类比：你家书架很高，书有上万本，但你每次只看眼前那一格。所以你只在架子上摆「眼睛正对着的十几本 + 上下各多摆几本备用」，其余书留在仓库。你往下挪，架子就实时把对应位置的几本换上来，永远只摆一小段。书架（滚动条）看起来还是那么高，但架子上实际只有一二十本书——这就是「用占位撑出总高度 + 只渲染视口内片段」。

### 怎么落地的（用了什么、效果）
1. **自己写一个零依赖的轻量 hook `useVirtualRows`**：放在 `src/hooks/use-virtual-rows.ts`。它只做一件事——根据你滚动的位置，算出「现在该画第几行到第几行」，再给个总高度的占位把滚动条凑齐。固定行高（表格行等高，34px）、上下各多预渲染 10 行防快速滚动露白、超过 50 行才启用（阈值）。
2. **只给真正会大的表接上**：宝宝流数据库里 `auto_facts` 这种「写作自动维护」的表，可能随写作积累成千上万行事实，每行还有好几个可编辑输入框——这才是真卡顿点。我把它展开后的 tbody 行渲染接进虚拟化。
3. **每个表独立持状态**：React 规定「不能在循环里调 hook」。原来表格是在 `tables.map` 里直接渲染的，没法在循环内调 hook。所以我把每张表抽成一个独立子组件 `LoreTableGrid`，每个组件自己调 `useVirtualRows`、自己记滚动位置——合规且清晰。
4. **编辑体验完全不变**：展开、增行、保存按钮、每个单元格的可编辑输入框，全都原样保留。虚拟的只是「渲染哪几行」这件事，你该填哪里还填哪里。

### 试过的方案 / 为什么没选别的（诚实记录）
- **引入成熟的虚拟列表库（react-window / @tanstack/virtual）？** —— 没引。这是 04 清单原话建议的库，但本项目当前数据量下，为小表背一个第三方依赖不划算；自己写个 60 行的 hook 就够，零依赖、可控、好维护。
- **给 StorylineList（故事线列表）也做虚拟化？** —— 故意没做。故事线是「卡片」列表，每张卡片高度不固定（展开详情时高、收起时矮），虚拟化的「固定行高」前提不成立；而且故事线数据量极小（几条到几十条）。硬做虚拟化要上「动态高度测量」，复杂度飙升，还破坏展开交互，且零收益——典型的「为了做而做」。如实取舍，保持原样。
- **用分页替代虚拟化？** —— 分页也能治大表，但用户明确要的是「虚拟化」，且分页会切断「一屏看全表结构」的体验；窗口化虚拟滚动更贴合可编辑表格。

### 关键取舍（工具 A 为何不选 B）
- 选「自研零依赖 hook」而非「引 react-window」：当前规模下，依赖成本 > 收益；自研可控、无体积负担。
- 选「只接 LoreTable、不接 StorylineList」：前者固定行高+真会大数据，后者非等高+极小数据；前者值得做、后者做了反伤，如实区分。
- 选「抽子组件持状态」而非「在 map 里硬调 hook」：React hooks 规则必须遵守，抽组件是正确解法。
