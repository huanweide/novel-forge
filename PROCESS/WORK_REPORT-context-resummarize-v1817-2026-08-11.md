# 工作单元报告：novel-forge v1.8.17 上下文窗口「重新摘要」+ 摘要确认（#221）

> 面向零基础大一新生的费曼式总结。每个术语第一次出现都用大白话讲清「它怎么运作」，再配生活化类比。

## 一、干了什么（一句话）

给小说写作平台的「上下文窗口」（看当前这章会塞进 AI 脑子里多少内容的面板）加了一个「重新摘要」按钮；点完之后不再像以前那样「生成完直接存盘」，而是先弹个框让你看一眼、还能改，你点头了才真正存进去。顺带修了「重复摘要会产生重复垃圾数据」的潜在 bug。

## 二、为什么这么做（拆到底层原理）

写长篇小说时，AI 每写一章都要把「前面所有章节」塞进有限的上下文窗口（相当于 AI 的短期记忆容量）。章节一多就塞不下。解决办法叫「摘要压缩」：把已经写完的章节压成几百字摘要存起来，以后只喂摘要不喂全文——这就是「中期记忆」。

瑞宝宝（用户）提的痛点：原来点「生成摘要」是「生成完直接落库 + 弹个 toast 告诉你结果」，你根本没机会看摘要写得好不好就存进去了。万一 AI 生成了一坨废话，它已经污染了记忆系统，后面所有章节都跟着错。所以要加一道「确认」闸门——先预览、能改、确认才存。这就是 #221 的核心。

## 三、用了什么方法 / 工具，效果如何

### 关键技术 1：摘要生成拆成「预览」和「确认」两步

**大白话**：把「生成」和「保存」拆开。先只生成不保存（像先 P 图不导出），给你看；你满意了点确认，才真正写进数据库（导出保存）。

**类比**：就像发朋友圈——你先写文案、选图（生成 + 预览），朋友圈界面让你「再看看」，你点「发表」才真的发出去；没点发表前，谁都看不到，也不会留下记录。

**做法（后端 `src/app/api/generate/summarize/route.ts`）**：
- 路由支持三种调用：
  1. `preview: true` → 跑 AI 生成，返回结果，**不碰数据库**（先预览）。
  2. 请求体里带 `summary` 字段 → 这是「确认」步骤：把你已看过的摘要 upsert 写库，**不再跑 AI**（省 token，也保证存的就是你确认的那版）。
  3. 默认（啥都不带）→ 生成 + 落库（向后兼容老入口）。
- 前端「重新摘要」按钮走模式 1（preview），拿到结果弹模态；模态里「确认保存」走模式 2（带 summary）。

**效果**：生成和落库彻底解耦，劣质摘要在「确认」前绝不会进记忆系统。

### 关键技术 2：落库从「永远新建」改成「有就更新、没有才新建」（upsert）

**大白话**：原来每次摘要都往数据库插一条新记录。同一章摘要两次，就变成两条——后面的代码数摘要数量时会算错，还可能重复。

**类比**：就像给同一份文件存草稿，原来每次都另存为新文件（草稿1、草稿2、草稿3 堆一桌）；现在改成「同一个文件名，有就覆盖、没有才新建」，桌上永远只有一份最新草稿。

**做法**：
- `ChapterSummary` 表按 `projectId + chapterId` 查旧记录：有就 `update`，没有才 `create`（始终一行）。
- `StoryBeat`（关键转折点）按章节 `deleteMany` 旧的后 `create` 新的，避免重复转折点累加。
- 这个改动对老的「工具栏生成摘要」也生效，顺带修掉了它重复摘要产生重复行的潜在 bug，且前端零改动。

**效果**：重复摘要不再产生垃圾数据，记忆系统计数始终准确。

### 关键技术 3：前端「重新摘要」按钮 + 确认模态（UI）

**大白话**：在上下文窗口的「中期记忆」那一行，加了个「重新摘要」小按钮（和展开箭头并排，不是套在展开按钮里——两个按钮不能互相嵌套，否则浏览器会报错）。点完按钮，弹出个框，里面是：
- 一个可编辑的摘要文本框（你不满意能当场改字）；
- 关键事件列表（只读，让你知道 AI 抽出了哪些转折点）；
- 角色状态快照（可折叠查看）；
- 底部「取消 / 确认保存」两个按钮。

**做法（`src/components/editor/ContextPreview.tsx`）**：
- 引入项目现成的 `Modal` / `ModalFooter` 组件（统一玻璃弹窗）和 `toast` 提示。
- 「重新摘要」按钮调用 preview 接口；拿到结果存入 `summaryDraft` 状态并打开模态。
- 模态里「确认保存」把编辑后的 `editedSummary` + 原始关键事件/角色状态发回「确认」接口；成功后 toast 提示，并 bump 一个 `reloadTick` 让上下文面板自动刷新（摘要数量实时更新）。
- 章节没内容时点按钮，接口返回「内容为空」错误，前端友好提示，不崩。

**效果**：用户首次能在落库前审阅并修正摘要，记忆系统数据质量可控。

## 四、关键取舍（工具 A 为何不选 B、踩坑与修复）

1. **「确认」走独立接口而非前端直接落库**
   - 否决：前端生成完直接 `fetch` 保存原接口（会把 AI 结果再生成一遍）——浪费 token 且「存的不一定是你确认的那版」。
   - 选定：preview 只生成返回，确认时把前端拿到的文本原样发回 `summary` 字段由后端 upsert。存的就是你看到/改过的那版，且确认步骤零 AI 调用。

2. **upsert 而非「先查后删再建」**
   - 选定 `findFirst` → `update`/`create` 二选一；`StoryBeat` 用 `deleteMany + create`（同一章转折点整体替换，最简单且不会留旧垃圾）。比「逐条 diff 合并」简单且够用。

3. **踩坑：JSX 结构不平衡（真实发生的错误）**
   - 现象：`tsc` 报 `JSX element 'div' has no corresponding closing tag` + 文件末尾 `Unexpected token`。
   - 原因：插入摘要模态时，把「角色读取统计」那个 `<div>` 的闭合标签 `</div>` 误一并替换掉了，导致该 div 没闭合，编译器一路找不到外层 div 的结尾。
   - 修复：补回那个 `</div>`。教训：做大段 JSX 替换时，闭合标签要成对核对，不能只盯新增部分。

4. **踩坑：`chapter.content` 是 `string | null` 类型**
   - 现象：`tsc` 报 `Type 'string | null' is not assignable to type 'string'`。
   - 原因：数据库字段允许 null，但摘要函数参数写死 `string`。
   - 修复：函数参数放宽为可空，内部用 `?? ""` 兜底（调用方此前已判空返回 400，运行时必为非空，兜底只是满足类型检查）。

5. **按钮不嵌套**
   - 「重新摘要」按钮与「中期记忆」展开开关做成了兄弟节点（并排的两个按钮），而不是把按钮塞进展开按钮里。这是前序 v1.8.11 修过的同类坑（嵌套 button 会引发 hydration 错误），本次直接规避。
