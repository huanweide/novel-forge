# 费曼报告：v1.6.23 自动填表 update 类精确还原（F2 修复）

> 瑞宝宝，这是 v1.6.23 的工作单元沉淀。用零基础也能懂的方式讲清「干了什么、为什么、怎么做、关键取舍」。

## 一、干了什么（一句话）

把「AI 自动填表时修改过的表格行」也能在「撤销章节」时精确还原回去——之前只能删掉新增的行，改过的旧行还原不了，这次补上。

## 二、为什么这么做（拆到底层）

**背景类比**：novel-forge 的「结构化表格」像 Excel 分表（地点表、人物表…）。AI 写每章时会往表里「自动填行」：要么新增一行（insert），要么把已存在的某一行改几个字（update，比如把「青龙镇·相关=？」补成「青龙镇·相关=江边」）。

v1.6.19 做了「撤销章节」功能：删正文时，把这一章 AI 自动**新增**的表格行也删掉，避免残留。但有个洞：如果 AI 是**修改**了既有行（update），撤销时只删新增行，被改的那行就回不去了——等于「撤销」没完全还原表格。这就是 F2 缺口。

**第一性原理**：撤销 = 让表格回到「这一章填表之前」的状态。新增行好办（直接删），但 update 行需要知道「改之前长什么样」。所以必须在填表那一刻，把「改之前的整行」偷偷记下来，撤销时再贴回去。

## 三、用了什么方法、效果如何

**方法（零侵入，不碰核心）**：
1. 在填表函数 `babyloreFill` 里，填表前先给每张表拍一张「前快照」`beforeRowsById`（深拷贝）。
2. 填表后，拿「后状态」和「前快照」逐行 diff：
   - 后状态里有、前快照里没有的 row_id → 是新增行，记进 `insertedRowIds`（沿用旧逻辑）。
   - 前后都有、但内容变了 → 是被 update 改写的旧行，把「前快照那一行」存进新字段 `updatedRowsBefore`（一个 `row_id → 改前整行` 的字典）。
3. `revertBabyloreFill`（撤销）时：删掉新增行 + 把 `updatedRowsBefore` 里的行贴回原处。
4. **数据安全保护**：如果同一行后来被「更晚的章节」也改过，撤销较早章节时**不**动这行，避免把后面章节的真实编辑覆盖掉。做法是查本项目所有填表批次，算出「被后续批次碰过的行集合」，这些行一律不动。

**效果（实测，非推测）**：
- tsc 0 错误；vitest 299/299 全绿（较 v1.6.22 的 297 新增 2 条单测）。
- 两条新单测钉死：① 撤销时 update 行精确还原到改前值、不删行；② 后续章节也改过同一行时，撤销较早章节不还原（保护后续数据）。
- schema 已 `prisma db push` 同步本地 PG17，`updatedRowsBefore` 落库。
- 已推 `origin/main`（`894989f..cdd785e`，绕过 PR + 状态检查）。

## 四、关键取舍

- **为什么用「前后快照 diff」而不是改 `applyOps` 核心？** `applyOps` 是填表落库的核心，动它风险高。快照 diff 在外层做，零侵入、好测，且能一把覆盖「去重合并」和「命中更新」两类 update。
- **为什么不直接还原、要加「后续批次保护」？** 多章可能共享同一行（比如「青龙镇」在第三章、第五章都被 AI 补充）。若撤销第三章时把该行硬还原到第三章之前，会连第五章的补充一起抹掉——这是数据丢失。保守策略：只要后续章节碰过这行，就不动它。代价是「跨章共享行的完美还原」做不到，但「绝不丢数据」优先。
- **诚实边界**：本修复只覆盖「这一章填表造成的新增/更新」；delete 类操作（AI 删行）仍不在还原范围，因为删除后再还原需要额外变换且沙箱无端到端验证，留后续专项（F2 的 delete 部分）。
