# novel-forge v1.6.43 工作单元报告：UI 复检揪出 stale client 阻塞，顺手增强错误诊断

> 读者对象：零基础大学生。目标——让你照着做能复现，且真懂「为什么会出这个故障、怎么治」。

## 一、干了什么（一句话）

用一台**真实的无头浏览器**把 novel-forge（本地 AI 写小说平台）从头点到尾，第一次发现并修掉了一个隐藏故障：**只要有人改了数据库结构却没重启开发服务器，所有项目都打不开（报 503）**；同时把报错提示从「请检查数据库」改成更准确的「请重启开发服务器」。

## 二、为什么这么做（底层原理，用大白话）

### 背景类比
之前的十几个版本（v1.6.x）都在改代码、改类型，**从没真用浏览器看过界面长什么样**。这就像建筑师改了一堆图纸，却从没去工地看房子漏不漏水。马斯克人格的「执行 CEO」子 Agent 拍板：下一轮方向就定为「UI 复检」——真用浏览器跑一遍核心流程。

### 故障的原理（核心知识点）
novel-forge 用 Prisma 当「数据库翻译官」：代码通过它对数据库说话。数据库结构（有哪些表、哪些列）写在 `schema.prisma` 里，Prisma 会据此生成一个「客户端」（翻译官的脑子）。

**关键陷阱**：如果你改了 `schema.prisma`（比如加了一列 `confirmedAt`），必须让 Prisma 重新生成客户端、并且**重启开发服务器**（它脑子里还装着旧的翻译规则）。否则——翻译官脑子里是旧规则，却要去查新结构的数据库，一查到新列就懵了、报错。

这就叫 **stale client（过期客户端）**。它特别阴：首页能正常显示（因为查的是旧结构就有的表），但你一点进具体项目（查询碰到了新列），立刻 503 崩溃。

## 三、方法、工具与效果

### 工具
- **agent-browser**：一个 Rust 写的浏览器自动化工具（不是 Playwright/Puppeteer），通过 Chrome 的 CDP 协议控制真实 Chrome。
  - 关键坑：在 Windows 以**管理员**身份跑 Chrome，必须加 `--no-sandbox` 参数，否则 Chrome 初始化直接卡死（本次第一个踩的坑，卡了 4 分钟）。
  - 包装脚本 `C:/Users/Administrator/ab-agentbrowser.sh` 注入了 `AGENT_BROWSER_ARGS="--no-sandbox"`，并规避了 Git Bash 的路径转换 bug（用 Windows 风格绝对路径直接调 node 跑 bin）。

### 步骤（可复现）
1. **启动无头 Chrome 打开首页**：`bash ab-agentbrowser.sh open http://127.0.0.1:3001/` → `snapshot` 抓无障碍树。首页导航、项目星海、作品列表渲染正常。
2. **点进项目**：通过 `eval` 取链接 href，发现 `/api/projects/[id]` 返回 503。
3. **curl 复现确认真实故障**：
   ```bash
   curl -s http://127.0.0.1:3001/api/projects/5550f26f-4237-427d-bb6d-e34b851cfe70
   # 返回 {"error":"数据库访问出错","code":"PRISMA",...} HTTP 503
   ```
4. **查进程时间锁定根因**：
   ```powershell
   # 3001 端口监听 PID 启动于 08/08 2026 01:12:35
   # schema.prisma 最近修改 08/08 2026 20:11（v1.6.23 加 confirmed_at 列）
   ```
   开发服务器比 schema 变更**早 19 小时**启动 → 内存里是旧 Prisma 客户端 → 实锤 stale client。
5. **修复（环境层）**：
   ```powershell
   taskkill /PID 23464 /T /F   # 杀旧 dev server 进程树
   ```
   ```bash
   node node_modules/next/dist/bin/next dev -p 3001   # 重启，加载新客户端
   ```
6. **验证修复**：curl 复现 → 200，返回完整 JSON（含 `"name":"星辰"` + 全部关联数据）；浏览器重载工作台 → 错误页消失，章节树/编辑器/创作工具全部正常渲染。
7. **代码增强**：`src/lib/api-error.ts` 的 `classifyError` 新增子分支——检测 Prisma 报错里含 `Unknown arg` / `Invalid prisma ... invocation` / `column does not exist` 等「schema 不匹配」特征时，返回准确提示「数据库已连接，但本地 Prisma 客户端版本与数据库表结构不一致……请重启 dev server 或执行 npx prisma generate」，不再误报「请检查数据库已启动」。

### 效果数据
- 门禁：`tsc` 0 错误 + `vitest` 35 文件 323/323 全绿。
- UI：工作台核心创作流程首次真用浏览器验证通过。
- 故障：本地所有项目「打不开」的阻塞已消除。

## 四、关键取舍（为什么这么选）

1. **为什么重启而非改代码？**
   这是**环境故障**，不是代码缺陷。线上（Vercel）每次部署构建时自动重新生成 Prisma 客户端，根本不存在 stale client。本地开发时改了 schema 忘了重启，才会踩。所以治法是「重启开发服务器」，不是改业务代码。

2. **为什么顺便增强错误提示？**
   实踩坑时发现：原来 503 提示写「请确认数据库已启动」，但故障时数据库明明好好的——这会把开发者往错误方向引（去查数据库而不是重启 dev server）。花 13 行代码让提示准确，下次再踩能一眼看到正确解法。属于「花小钱办大事」的防御性改进。

3. **踩坑实录（诚实记录）**
   - agent-browser 默认无头，但管理员需 `--no-sandbox`，否则卡死（已固化进包装脚本）。
   - 初次误判「点击没导航」：其实 Next.js App Router 客户端路由跳转慢（>5 秒），是我的等待时间不够，不是应用 bug。改用 `eval` 直接触发链接点击 + 延长等待后确认导航成功。
   - Git Bash 的 `seq` 命令不可用，改用 `{1..40}` 大括号循环。

4. **没做的事（范围克制）**
   生成类功能（真调 DeepSeek 续写/精修）因 DeepSeek 偶发 503 未实测，留后续专项——不为了「看起来验证全了」而硬跑一个已知会不稳定的外部依赖。
