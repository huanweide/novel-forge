# 工作单元报告 · v1.6.46 — 生成类功能端到端实测 + 修复 DeepSeek 偶发空响应重试

> 费曼式教学文档。读者默认零基础：能讲给大一新生听懂，才算真懂。

## 一、干了什么（一句话）

把 novel-forge 的「AI 写小说」引擎真正跑起来验证了一遍（之前只验证了界面能不能显示，从没验证过「点一下能不能真的写出字」），发现 DeepSeek 偶发「返回空内容」会让整章写入失败，于是加了一层自动重试把这个坑填上。

## 二、为什么这么做（拆到底层原理）

**第一性原理**：这个软件存在的唯一理由，是帮人用 AI 写长篇小说。如果「生成」这条核心链路是坏的，界面再漂亮也是空壳。前面 v1.6.43/44 用无头浏览器只验证了「页面能渲染、按钮能点」，但「点完生成按钮，字到底有没有真的写进数据库」从来没端到端验证过——这是个危险盲区。

**为什么空响应值得修**：AI 接口（DeepSeek）不是 100% 可靠的。它有时候会「连接成功、开始返回数据流，但一个字都没给就结束了」（业内叫空响应 / 截断）。这种偶发故障平时概率低，但落到用户头上就是「我等了一分钟，章节里啥也没生成，白等」。这属于「用户高频操作 + 偶发必现」的组合，优先级高。

## 三、用了什么方法 / 工具，效果如何

### 1. 端到端真跑（不靠猜，靠真打接口）

- 工具：`curl` 直接打本地 dev server 的 SSE（流式）生成接口 `http://127.0.0.1:3001/api/generate/continue` 和 `/api/generate/refine`。
- 为什么用 curl 而不是点界面：生成要几十秒到两分钟，curl 加 `-N`（不缓冲流）和 `-m 220`（超时 220 秒）能把完整响应落盘慢慢分析，避免在终端刷屏。

**实测结果**：

| 路径 | 第1次 | 第2次 | 第3次 | 结论 |
|------|-------|-------|-------|------|
| continue（自动建节点续章） | 200、113s、758 token、1206 字落库 | — | — | **端到端跑通** |
| refine（精修/微调） | token=0，报错「微调内容为空」 | 357 token 被截断 | 1161 token 成功 | 暴露 2 个断点 |

- **断点1（空响应）**：refine 第一次调用，DeepSeek 返回了 0 个正文 token，上层守卫直接把整章判失败。这就是要修的坑。
- **断点2（长章截断）**：refine 要求模型「把已有 1206 字原文重输出 + 再写 500 字续写」，逼近 token 预算上限，长章必被 `length` 截断。这是「重输出全文」契约的固有风险，完整修要改契约（高风险），本轮只记录，不硬改——而且现有截断保护已经会在截断时**保留原正文不污染**，安全。

### 2. 修复断点1：在生成函数里加空响应重试

改动文件：`src/core/agents/orchestrator.ts` 的 `writeSection` 方法。

**大白话讲清原理**：原来调用 AI 的代码（叫 `chatStream`）只重试「连不上」的情况。但「连上了却没给字」它认为「正常结束」就返回了。我在外层（真正写章节的地方）补了一层——

```
最多重试 2 次（WRITE_MAX_RETRIES=2）
每次退避：第1次等 0.6 秒，第2次等 1.2 秒，封顶 8 秒（指数退避：越重试等越久，避免狂打接口）
判断标准：本次尝试「一个字都没收到」才重试；「收到过字」就当成功，直接结束（防止重复累积正文）
特例：如果是密码/鉴权错误（401/403/api key 错），重试也没用，直接报错
```

这样 DeepSeek 偶发空响应时，会自动等一下再试，显著提升续写/精修成功率。

### 3. 验证（双门禁，不靠嘴）

- `SAFE_DELETE_DISABLE=1 npx tsc --noEmit` → **0 错误**（类型检查，确保没写崩）
- `npx vitest run` → **35 文件 323/323 全绿**（回归测试，确保没弄坏别的功能）
- 重启 dev server 加载新代码后，再真跑一次 refine → **1161 token、无截断、填表 7 行 applied**，证明重试逻辑不破坏正常流程。

### 4. 数据清理（诚实收尾）

实测时在星辰项目里自动建了一个测试章节节点（order=3），验证完用 `DELETE /api/story/nodes/[id]` 软删（进回收站可恢复，不物理删），把项目恢复成原始的 3 个节点，不污染用户数据。

## 四、关键取舍（为什么这么选，不这么选）

1. **为什么修空响应、不修长章截断？**
   - 空响应：低风险（只加一层重试，不改任何数据流），高收益（直接消除「白等失败」），确定性命中已知故障。
   - 长章截断：要改 refine 的「重输出全文」契约（改成「只续写不重输出」），涉及提示词、后处理、自动填表多处联动，高风险。且现有截断保护已经安全（不污染原文），所以留后续专项。这是「最小彻底修复」原则的取舍。

2. **为什么用 curl 真打而不是写单元测试？**
   - 单元测试 mock 了 AI 接口，永远测不出「真实网关偶发空响应」。真打才能暴露断点1。代价是空响应重试本身无法「确定性复现」（依赖网关偶发），所以靠代码审查 + 正常流程验证放行，并在报告里**诚实标注**这一边界，不假装测过。

3. **为什么不直接删测试节点、而是走软删 API？**
   - 软件自己的软删 API 会顺带处理关联数据（如自动填表行的回收），直接手删数据库会留垃圾。用它的 `DELETE` 接口，与用户点「删除章节」走同一条路，最干净。

```bash
# 1. 起 dev server（已含修复）

node ./node_modules/next/dist/bin/next dev -p 3001

# 3. 取一个已有节点 ID（用于 refine 精修）
curl -s http://127.0.0.1:3001/api/projects/<项目ID> | node -e "let s='';process.stdin.on('data',d=>s+=d).on('end',()=>{const p=JSON.parse(s);console.log(p.storyNodes[0].id)})"

# 4. 真跑 refine（精修/微调）
curl -N -s -m 220 -X POST http://127.0.0.1:3001/api/generate/refine \
  -H "Content-Type: application/json" \
  -d '{"projectId":"<项目ID>","nodeId":"<节点ID>","instruction":"请基于现有正文自然续写约500字","targetWords":500}' \
  -o refine_sse.txt

# 5. 解析 SSE 看 token 数与是否成功
node -e "const fs=require('fs');const r=fs.readFileSync('refine_sse.txt','utf8');let t=0,e=0;for(const l of r.split('\n')){if(!l.startsWith('data: '))continue;try{const o=JSON.parse(l.slice(6));if(o.type==='token')t++;if(o.type==='error')e++;}catch{}}console.log('token=',t,'error=',e)"
```
