## 一句话结论

从 v1.6.51 到 v1.8.0，novel-forge 长出了一套「跨章一致性引擎」——专门解决长篇小说最容易翻车的事：**前面写的设定，后面写忘了、写反了**。v1.8.0 是这套引擎的里程碑印章，全链路闭环、双门禁全绿、零 schema 迁移风险。IP 永远归瑞宝宝（樊斯瑞）。

## 这条引擎到底干了啥（大白话）

写长篇时，作者最怕「设定前后打架」：第 3 章写主角「灰眸」，第 20 章手滑写成「黑眸」，读者一眼出戏。以前 AI 写作工具不管这个，novel-forge 现在管了，而且是一条龙：

1. **抽设定**：AI 读你每章定稿，把「谁几岁、什么发色、哪个门派、和谁是师徒」这类事实抽成一张清单（设定集）。
2. **注入**：生成新章节时，把这张设定集塞进提示词，提醒 AI「写作时务必遵守，别写反」。
3. **找矛盾**：新章节写完后，AI 拿正文和设定集比，发现「正文说黑眸、设定记灰眸」就标红报警（只标红，不改你正文）。
4. **给改法**：作者点一下，AI 直接给一句「把『黑眸』改成『灰眸』」的改写建议，复制即用（仍不改正文）。
5. **人能改 AI 的设定集**：作者发现 AI 抽错了，能编辑/删除/手填设定；手填的设定打「手动」印章，AI 重抽时不动它。
6. **省成本**：抽取自动去重防堆积；纯续写时不重复全量重抽，省大模型调用。

**贯穿全程的铁律**：AI 只标红、只建议，**绝不替作者改正文**——创作主权在作者。

## 关键工程决策（第一性原理）

1. **零 schema 迁移**：手动事实用现有 `source` 字段标 `manual` 来标记，而不是新增布尔列。理由：线上 Neon 额度耗尽、靠本地 PG17 验证，能不 `prisma db push` 就不 push——降风险。能用现有字段解决就别加字段（KISS）。

2. **重抽只清自动事实**：`deleteMany({ projectId, source: { not: "manual" } })`。否则「手动重抽」会把作者手填设定抹掉——这是实现人工纠错时提前堵住的致命 bug。

3. **解析逻辑全抽纯函数 + 单测**：`parseFactsFromLLM` / `parseConflictsFromLLM` / `parseSuggestionFromLLM` / `validateFactInput` / `dedupeFacts` 全是纯函数，单测锁死。大模型返回格式千奇百怪（代码围栏、开场白、客套话），纯函数能独立测、不依赖网络/数据库。

4. **触发闸门只罩重抽不罩检测**：重抽贵（读全章+调模型），续写时跳过；冲突检测便宜且每次该跑（新句子可能打架），照常。
