# v1.6.20 修复循环评审 · 费曼（真实性校验）

> 我的尺子只有一把：把"已修"和"循环"讲给一个不懂代码的人听。能让他点头说"真的修干净了、真的在转"，才算数；只能说"我加了测试、我写了报告"，那就是自欺。下面每句话都先过了"它真的跑过吗"这一关。

## 一、核心诊断（检验"已修"与"循环"的真伪）

**先说 #6 修复算不算真修——我的结论：只算"半修"，而且是诚实声明过的半修。** 我亲自读了 `src/core/babylore/fill.ts`：

- `babyloreFill`（606–616 行）填表前确实给每张表拍了 before 快照（`beforeRowsById`，596–598 行），填完后只做一件事——对比出"哪些 `row_id` 是新冒出来的"，把这些 `row_id` 存进 `BabyloreFillBatch.insertedRowIds`。
- `revertBabyloreFill`（977–1004 行）撤销时，只按这批 `row_id` 把行删掉（994 行）。

**为什么只删新增行还原不了 update？大白话讲：** 自动填表对每一章干的事只有两类——"新增一行"（insert）和"改写已有行"（update）。v1.6.19 的快照其实拍了整张表的完整 before 状态，但拍完只用来算"哪些是新增的"，**那些被 update 改过的行的"旧值"被随手丢掉了，根本没落库**。于是：

- 场景 A（撤销不干净）：第 3 章把"青龙镇"的 `related` 从空改成"主角故乡"（这是 update）。撤销第 3 章时，系统只删"第 3 章新增的行"，而"青龙镇"早存在，所以撤销后 `related` 仍是"主角故乡"——旧值没回来，等于没撤干净。
- 场景 B（整行误删，正是 F2 说的）：第 3 章 insert 了"新门派"，第 5 章 update 给"新门派"补"掌门=张三"。撤销第 3 章按 `row_id` 把"新门派"整行删掉，第 5 章补的内容也跟着没了——因为第 5 章的 update 挂在同一行上。

**测过没有？没有。** 我读了 `fill.revert.test.ts`：三个撤销用例（138–176 行）全只测 insert 删除，**一个 update 回滚用例都没有**。实现没做、测试没覆盖，所以 F2 的"update 类不可精确撤销"是真问题，且当前修复对此是**已知空白**——这点和诚实边界声明一致，没撒谎，但也确实没修。

**再说 F1：经我核查，引用的文件 `sync-global-prompt.ts` 在本仓库不存在**（glob 全仓未命中）。"待审隔离"这个关注点本身合理——`game-engine.ts:511` 写了 `reviewStatus:"pending"`，而 `loop.ts` 的 recall 只按 `deletedAt:null` 过滤、确实没看 reviewStatus（F3 方向可成立）——但 F1 的具体文件名+行号**无法核实，疑似误标/张冠李戴**，不能当既成事实用。

**循环是否真转？我的判断：目前是"会议纪要式空转"的风险最高。** `.loop-state.json` 还停在 `v0.30.0 / commit d13fb46`，而 HEAD 已是 `v1.6.19 / 33cb223`——循环元数据与真实发布严重脱节。本轮"检测→开会→修复→循环（派下一轮复验）"是一份**意图声明**，不是已执行的代码流水线。如果复验只停留在"再开一场会、再写一份报告"，而没有"重跑测试+读代码确认"，那就是空转。

## 二、提升框架

① **#6 必须补 update 回滚**：快照 already 拍了 before，缺的只是把"被 update 行的旧值"也存进 `BabyloreFillBatch`（增 `beforeValues` 字段），撤销时先恢复原值再删新增行。
② **F1/F3 重定位**：先 grep 出真正漏 `reviewStatus` 的取用端（recall、章纲、fill 入口），按真实文件改，别顶着不存在的文件名修。
③ **循环要"代码级复验"**：每轮复验的判据必须是"测试通过 + 人工读关键函数"，不是"又开了一场会"。
④ **大书导出内存（F4）**：实测峰值未给数据，先埋 `process.memoryUsage()` 打点，别凭感觉优化。

## 三、具体可落地步骤

1. 给 `BabyloreFillBatch` 模型加 `beforeValues`（`loreTableId → {row_id: 旧行快照}`），在 `babyloreFill` 的 before 快照阶段一并落库（改动集中在 fill.ts:606–616）。
2. `revertBabyloreFill` 增加"先按 `beforeValues` 还原被本 node 改过的行、再删 `insertedRowIds`"两步；并新增**针对 update 回滚的单测**（当前最该补的空白）。
3. 派一人用 `Grep` 全仓搜 `reviewStatus` 与取用端（recall/章纲/outline），列出真实遗漏清单，替换 F1 的假路径。
4. 把 `.loop-state.json` 的 `current_version/commit` 接到发布脚本自动更新，杜绝元数据滞后。
5. 下一轮复验须附：diff 链接 + 新增/改动测试名 + 实测输出，缺一不可算"已转"。

## 四、风险提示

- **最大风险是"报告自洽即视为已修"**：F1 顶着不存在的文件、F2 的 ops Json 方案（把每次 op 存 `ops` 字段、撤销时反向执行）**尚未实测**——我必须诚实标出：F2 的 ops 反演方案是高概率方向，但没跑过原型，可能遇"同 row_id 被多章 update 的合并顺序"难题，落地前需小样验证。
- **半修的 #6 会给人"已安全"错觉**：用户撤销含 update 的章节会静默丢改动，比不修更隐蔽。
- **循环空转反噬信任**：多轮漂亮报告若不变代码，团队会以为"在迭代"，实际在绕圈。

## 五、与其他职能的张力

- 与**马斯克（第一性原理）**的张力：他可能直接质问"撤销到底要不要 100% 还原"，逼我把 #6 从"只删新增"升级到"完整快照回滚"——我同意，但需说明为何先做半修（存量风险可控、改动小）。
- 与**墨白（诊断/实测）**的张力：他会要我把 F1/F3 重定位成真实清单，这与我"诚实标出推测"一致，不冲突。
- 与**乔布斯（体验）**的张力：用户感知不到 update 回滚缺失，直到撤销时丢数据才暴雷——我偏向"先补底层正确性，再谈体验包装"，与他"体验优先"有次序分歧。
- 与**tri（主席）整合**的张力：若多数人格主张"循环已闭环"，我必须拍桌子指出 `.loop-state` 滞后 + F2 无测试这两处硬证据——**形式化闭环比不闭环更危险，因为它让人停止怀疑**。

---
**诚实边界小结**：① #6 "只删新增行"经代码+测试双重核实为真·半修；② F2 的"update 不可还原"为真·未修·未测；③ F1 文件名本仓不存在·未核实；④ ops 反演方案为**未经实测的推测**；⑤ 循环"真转"无代码级证据·当前偏空转风险。
