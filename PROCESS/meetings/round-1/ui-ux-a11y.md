> 评审方式：源码阅读 + 无头浏览器（Playwright / Chrome）实跑截图 + DOM/色彩/尺寸提取 + WCAG 2.x 对比度计算

## 报告头

本次评审以「真实用户操作」为第一视角，对 novel-forge 的「故事线工作台」这一核心编排功能做端到端体验走查，并叠加可访问性（WCAG 2.1 AA）视角的专项检查。评审覆盖了三大组件：弹窗主体 `StorylineWorkbench.tsx`、列表入口 `StorylineList.tsx`、侧栏容器 `LeftPanel.tsx`，以及它们依赖的 `Modal` / `DialogUI` / `States` / `globals.css` 设计令牌体系。

技术核验手段包括：
1. 源码逐行阅读（重点组件 + 设计令牌定义）；
2. 使用仓库自带 `shot2.cjs` 对入口做整页截图（无 console error / warning）；
3. 自写 Playwright 脚本驱动 UI：切到「故事线」Tab → 点击主线项打开工作台弹窗 → 验 Esc 关闭 / 焦点陷阱 / 内部列宽与可聚焦元素数量 → 触发「AI 生成」后台轮询态；
4. 自写 Node 对比度脚本，将 `--nv-*` 令牌（含 oklch 功能色）换算为 sRGB 后按 WCAG 公式逐对计算对比度。

核心结论先行：**故事线工作台在「信息架构」与「视觉完成度」上已具备相当水准——三套主题（暗色 / 苍青 / 浅色）令牌经过刻意对比度调校、弹窗具备焦点陷阱与 Esc 关闭、空/错/载三态齐备；但在「键盘可达性」「功能色文字对比度」「侧栏布局高度」「AI 生成的可感知进度」四处存在明确可修复的体验与无障碍缺陷。** 详细发现见文末「发现清单」（共 16 条，P1 级 6 条、P2 级 10 条，未发现阻断性 P0）。

## 第一部分：用户体验视角

### 一、自身操作体验

我把整个故事线工作台当作一个第一次接触这个产品的小说作者来走查，操作路径如下：

**第一步，找到入口。** 进入 workspace 后，左侧是一条 256px 宽的侧栏（`<aside>`），顶部排列着「大纲 / 角色 (15) / 世界 (70) / 故事线 (13) / 更多 ▾」五个 Tab。这里第一感受是：Tab 数量被刻意控制在「常显 4 个 + 更多 1 个」，把低频的「规则」收进「更多 ▾」菜单，主工作区密度是克制的、合理的。但紧接着我注意到一个刺眼的问题——**这条侧栏在 900px 高的视口里只占了 284px 高**（实测：drawer 容器 `fixed inset-y-0 … h-full` = 805px，但内部 `<aside>` 自身高度仅 283.97px），也就是说侧栏下半部约 520px 是一整片空白带。作为用户，我第一反应是「这个面板是不是没加载完 / 卡住了」，这种来自布局断裂的不安感在第一秒就建立了。它不影响功能，但严重伤害「这是一个打磨过的产品」的第一印象（详见 F-03）。

**第二步，打开列表。** 点击「故事线 (13)」后，列表区出现「13 条故事线」计数 + 一个紫罗兰色的「AI生成」小按钮，下面是以「主线卡片」为单位堆叠的条目：每张卡片显示金色星标 + 主线标题 + 「已完结」徽章（若有）+ 主线进度条 + 百分比，卡片内还可展开支线。整体信息密度舒服，主线/支线的层级通过金色星标（`star`）与箭头（`arrowRight`）图标区分。我点开一条主线「龙陨之地·主线」，工作台弹窗以弹性动画（`animate-spring`）居中弹出，尺寸 1024×803，遮罩 `bg-black/60 + backdrop-blur`，标题「故事线工作台」带书签图标。

**第三步，弹窗内操作。** 弹窗左列是 288px 的导航（主线→支线树），右列 734px 是详情。左列每条故事线是一个可点选的卡片，带 4px 高的进度条；右列顶部是「标记完结 / 编辑 / 删除」三个操作，下面依次是「七要素·总纲」网格（欲望/阻碍/行动/结果/意外/转折/结局）、「章节进展时间轴」、「线索集」。点击左列另一条「龙元裂缝的第七个白日」能即时切换右列，切换顺滑。点「编辑」进入编辑态，标题/简述/类型/状态/归属/七要素都可改，底部「取消 / 保存」。点「标记完结」会即时把状态改为 completed 并弹 toast「「xxx」已完结 ✓」。

**第四步，AI 生成。** 我回到列表点了「AI生成」，弹窗重新打开并进入轮询态：按钮变成「生成中… 10%」带旋转 loader，但右侧仍显示普通列表视图。约数秒后（后台任务完成）弹窗主体被「AI 生成结果·中间编辑态」覆盖，列出若干条主线/支线建议，每条可改标题、简述、七要素，底部「放弃 / 采用并落库」。点「采用并落库」后 toast「故事线」并关闭中间态、刷新列表。

**操作流畅度总结：** 主路径（浏览 → 选线 → 看详情 → 编辑 → 完结 → AI 生成 → 落库）是连贯的、可学习的，没有断链或死按钮。但有两处打断了我作为用户的心理预期：
- 其一是侧栏空白带（上文）；
- 其二是 AI 生成进行中时，弹窗「看起来和没生成时一模一样」，只有右上角按钮那一行小字在变百分比，我无法判断「现在到底在发生什么、还要多久、结果会出现在哪」。对于一次可能耗时十几秒的 AI 任务，缺少区域级进度/骨架屏，会让用户怀疑是不是点错了（详见 F-07）。

### 二、功能与看法评价

**做得好的地方（值得肯定）：**
- **七要素模型落地扎实。** 把一条故事线拆成「欲望/阻碍/行动/结果/意外/转折/结局」七格，并在查看态用两列网格平铺，编辑态可逐项填写，AI 生成态可直接改后再落库。这不是装饰性功能，而是真正贴合「小说故事线编排」心智模型的结构化设计。
- **进度条 + 百分比的颗粒度恰当。** 主线卡片、左列导航、弹窗内都复用了 `computeStorylineProgress` 的 `overallPercent`，用户在三个层级看到一致的进度语义，没有信息打架。
- **AI 生成「中间编辑态」是聪明的解法。** 没有直接把 AI 结果硬塞进库，而是先呈现可改草稿再「采用并落库」，既保留 AI 效率又尊重作者主权。配合真后台任务（`generation-tasks`）轮询，关页面也不丢服务端任务，工程上考虑到了异步健壮性。
- **三态规范（EmptyState / Loading / ErrorState）齐备。** 列表空时有带插画图标 + 标题 + 「AI 自动生成」行动的空态；加载中有「加载中…」；出错有红框 + 文案 + 「重试」。这是超出许多同类产品的完成度。
- **弹窗可访问性基线到位。** `Modal` 组件统一处理了遮罩点击关闭、Esc 关闭、body 滚动锁定、`role="dialog"` + `aria-modal` + `aria-labelledby`，并内置 `useFocusTrap`。实测 Esc 能正确关闭弹窗，且 `aria-labelledby="workbench-title"` 正确关联可见标题，读屏可报出「故事线工作台」。

**可以更好的地方：**
- **「标记完结」的切换入口在左列导航里是一个 `<span onClick>`，不是 `<button>`。** 对鼠标用户无感，但对键盘用户和读屏用户，它是完全不可达、不可知的（详见 F-01）。这是「功能存在但部分用户用不了」的典型无障碍欠账。
- **AI 生成按钮的紫色文字对比度不达标。** 紫罗兰 `--nv-creative` 文字压在 `--nv-creative-soft` 浅紫底上，实测仅 3.75:1，低于 WCAG AA 对正常文字要求的 4.5:1（详见 F-02）。按钮文字是 12px 正常字号，不是大字，因此这条会真实影响低视力用户辨识「AI 生成」按钮。
- **侧栏高度塌陷**（F-03）与上面操作体验重合，不再赘述，但它确实拉低了整体「精致感」评分。
- **时间轴为空时只有一行弱灰色提示**，没有复用全局 `EmptyState` 的插画+标题规范，和「三态规范」的自我要求不一致（F-11）。
- **触控/键盘一致性**：右列「标记完结/编辑/删除」是标准 `<button>`（删除还带 `aria-label`），但线索区的「编辑/删除」图标按钮只有 `title` 没有 `aria-label`，读屏只能偶尔读到 tooltip（F-05）。同一个弹窗里，按钮的无障碍待遇不统一，说明组件级 a11y 契约还没完全沉淀。

**与同类工具的心智模型契合度。** 我把故事线工作台放在「小说写作助手」这一品类里横向感受：多数同类产品把「故事线/情节」当成大纲的一个子标签页，或干脆塞进角色卡里做附庸；novel-forge 却把它做成独立的一级入口（左侧栏常显 Tab），并用「七要素 + 进度条 + 时间轴 + 线索集」四件套撑起一个完整的工作台。这种「把情节结构当作和角色、世界平等的一等公民」的产品决策，非常贴合长篇小说创作的真实痛点——写长篇最怕的就是「埋下的线忘了收、支线抢了主线戏份、伏笔和回收对不上」。七要素网格本质上是在逼作者把一条线的「起承转合」想清楚，`computeStorylineProgress` 又把「这条线写到哪了」量化出来，这比纯自由文本大纲对创作更有牵引力。从这个角度，故事线工作台不是功能堆砌，而是有清晰创作方法论支撑的。它唯一在「方法论落地」上略欠火候的是：七要素里的「结局」被设计成「不预填、仅标记收束」（line 711 副标题明说），这是尊重作者不剧透自己的善意，但系统因此对「完结度」的判定只能停留在「作者手动标记 completed」这一粗粒度，无法基于七要素是否填满给出更细的完成度——属产品取舍，供后续讨论。

### 三、项目文案文字观感

从「文字观感」这一更偏主观的维度看，novel-forge 的文案整体属于「克制的产品经理式中文」，没有过度堆砌的营销辞令，也没有机器翻译腔，是加分项。具体观察：

- **组件标题精准。** 「故事线工作台」「七要素·总纲（结局不预填，仅标记收束）」「章节进展时间轴（写作自动记录大事件）」「线索集 / 纸集（融合龙王寨、菜市场注释、尸检报告等）」——这些副标题既是功能说明，又带一点「懂行」的语气（龙王寨、尸检报告显然是该项目样例的世界观元素），让作者感到「这工具是为写小说的人做的」。这种把示例世界观揉进占位/说明文案的做法，比干巴巴的「请输入内容」亲切得多。
- **按钮文案意图清晰。** 「采用并落库」「标记完结」「AI 自动生成」都是动宾结构、动作指向明确，没有歧义。
- **toast 文案有温度。** 「「xxx」已完结 ✓」「故事线」创建成功提示，简短但有正反馈。

但有两处文案一致性瑕疵值得修：
- **「AI生成」vs「AI 生成」空格不统一。** 列表入口按钮写的是 `AI生成`（无空格，`StorylineList.tsx:130`），而工作台头部按钮写的是 `AI 生成`（有空格，`StorylineWorkbench.tsx:410`）。同一功能的标签在同一产品里两种写法，略显随意。
- **「放弃」按钮语义偏弱。** 在 AI 生成中间态，右上角是「放弃 / 采用并落库」。「放弃」对作者而言可能意味着「我不要这些 AI 建议了」，但也可能被误读为「放弃整个故事线」。考虑到这是破坏性操作（丢弃刚生成的草稿），「放弃」不如「取消生成」或「丢弃草稿」来得无歧义。当然它不删库，风险有限，但文案可更稳。

### 四、按钮与 UI 设计评价（位置、可见性、禁用态、布局密度、暗色对比度、响应式、滚动溢出、弹窗遮挡裁切）

这一节按评审模板要求的细分维度逐项体检。

**1) 位置与可见性。**
- 工作台头部右侧集中放了「AI 生成」+「关闭（X）」两个动作，位置符合「右上角收口」的桌面弹窗惯例，可见性 OK。关闭按钮有 `aria-label="关闭"` 与 `title`，且 hover 有底色反馈，符合预期。
- 右列详情的「标记完结/编辑/删除」贴在标题行右侧 `shrink-0`，不随标题滚动丢失，位置合理。删除按钮用最弱的 `text-[var(--nv-text-tertiary)]` 且 hover 才变红，是恰当的「低强调危险操作」处理。
- 列表入口的「AI生成」是 10px 的极小按钮，嵌在「13 条故事线」计数右侧。位置 OK，但 10px 字号 + 紫底紫字（见对比度问题）让它成为整页最「费力去读」的按钮之一。

**2) 禁用态。**
- 全局 `button:disabled` 有 `opacity-50 + cursor-not-allowed`（globals.css:414），统一生效。AI 生成按钮在 generating 时 `disabled`，视觉上变灰，状态传达清晰。
- 删除按钮在 `deletingId === selected.id` 时 `disabled:opacity-40`，也有反馈。
- 但「标记完结」切换 `<span>` 没有 disabled 概念（因为它不是 button），在 generating 等状态下它仍可被点——逻辑上它与列表数据一致不会出错，但缺乏禁用态语义一致性。

**3) 布局密度。**
- 工作台内部密度优秀：左列 288px 导航、右列 734px 详情，在 1024 弹窗里比例协调；七要素网格 `sm:grid-cols-2` 在窄时单列、宽时两列，响应式友好。
- 左列 `LineNav` 用 `line-clamp-2` 限制标题两行、进度条 4px 高，密度克制不拥挤。
- 例外是侧栏 Tab：五个 Tab 在 256px 内各约 51px，「角色 (15)」「世界 (70)」「故事线 (13)」这类带计数的标签在 51px 里很紧，虽然实测未溢出（scrollWidth==width），但已贴边，若计数变三位数（如「世界 (120)」）必然换行或挤压。属潜在密度风险（F-10 相关）。

**4) 暗色对比度（重点，已逐对计算）。**
基于设计令牌换算后按 WCAG 公式实测（深色主题，面板背景合成约 rgb(27,33,48)）：
- 主文字 `#F8F7F2` on 面板 = **14.98:1**（远超 AA/AAA）；
- 次文字 `#B9B7AD` on 面板 = **7.99:1**（AA）；
- 三级文字 `#98968C` on 面板 = **5.41:1**（AA），on 左列 surface-1 = **4.97:1**（AA，但接近下限）；
- 占位/禁用 `#8E8B82` on 面板 = **4.72:1**（AA）。
- 选中态金色文字 `--nv-accent` on `--nv-accent-soft` = **8.41:1**（AA，良好）。
- **问题项：AI 紫罗兰文字 `--nv-creative` on `--nv-creative-soft` = 3.75:1（仅达 AA-large/UI，未达正常文字 4.5）；on 面板 = 4.48:1（同样未稳过 4.5）。** 这是全组件最明确的对比度不达标点（F-02）。
- **次问题项：错误态「重试」链接 `--nv-primary` on 面板 = 3.79:1（未达 4.5），且字号仅 10px（F-04）。**

整体看，设计团队对文字层级令牌做了大量对比度调校（globals.css 注释里反复出现「达 WCAG AA」「保层级」的论证，甚至为 surface-3 专门提亮了 muted 变体），方向非常正确；但功能色（creative / primary）作为「文字色」直接压在自身 soft 底上时，仍跌破了 AA 阈值——这说明调校覆盖了「文字层级」却漏了「功能色文字 on 功能色浅底」这一组合。

**5) 响应式。**
- 工作台 `max-w-5xl`（1024px）在 >=1024 视口舒适；但在 <1024（如 768 平板）会贴边甚至溢出视口内边距（`p-4`）。左列固定 `w-72`(288) 在窄屏占比过高，右列被挤压。缺少明确的 `md` 断点把左列收窄或改为可收起（F-10）。
- 侧栏本身是 `fixed … max-w-[85vw]`，移动端友好；但如前所述，其内部 `<aside>` 未撑满高度。

**6) 滚动溢出。**
- 左列 `overflow-y-auto`、右列 `overflow-y-auto` 均正确设置，长列表/长详情可独立滚动，且弹窗整体 `overflow-hidden` 防止双击放大越界。实测左列 288×746、右列 734×746 滚动容器工作正常。
- 自定义滚动条 `custom-scrollbar` 仅 4px 宽、hover 才显形，美观但**触控/粗指针用户极难抓取**（F-12 相关）。在无鼠标的环境下，4px 滚动条几乎不可操作。

**7) 弹窗遮挡与裁切。**
- 弹窗 `z-[110]`，高于侧栏 drawer `z-40`，遮挡关系正确，不会被侧栏或主内容透出。
- 弹窗 `max-h-[92vh]` + 内部 `overflow-hidden` + 头部 `shrink-0` + 主体 `flex-1 min-h-0 overflow-y-auto`，头部固定、主体滚动的经典结构，没有被裁切风险。
- 但 `Modal` 的 bare 模式把滚动交给 `panelClassName`：StorylineWorkbench 传了 `overflow-hidden` + 内部自行滚动，结构正确；而 `Modal` 非 bare 模式自带 `overflow-y-auto`，两种模式滚动归属不同，若将来有人误用易出双滚动条。属于架构提醒。

### 五、空状态与长列表滚动走查

评审模板特别点名要检查「空状态、加载态、滚动长列表」，我把这三者在故事线工作台的真实表现单独走查一遍：

**空状态。** 列表层与弹窗层都复用了统一的 `<EmptyState>`：带一个 56×56 圆角插画图标（creative-soft 紫底 + 紫图标）、标题「还没有故事线」、以及行动按钮「AI 自动生成 / 点击 AI 自动生成」。视觉上这个空态是「友好且有引导」的——它不只是告诉你「没有」，还顺手把下一步（让 AI 生成）递到你手上。这是合格甚至偏上的空态设计。但有两处不统一：其一，弹窗内左列若为空（比如进入一个故事线被全删的 project），同样走 `EmptyState` 且行动按钮复用 `handleGenerate`，逻辑通；其二，右列「章节进展时间轴」为空时却**没有**用 `EmptyState`，只丢一行 `text-[var(--nv-text-tertiary)]` 的弱提示（line 759-763），与全站「三态规范」自我要求打架（即 F-11）。同一弹窗里，列表空态用插画卡、时间轴空态用一行灰字，这种「同组件内规范不统一」会让用户潜意识觉得「这个角落没被认真对待」。

**加载态。** 列表层 `loading` 时整块显示「加载中…」居中弱灰字（line 110）；弹窗左列 `loading` 时同理（line 502）。都无 spinner 图标，仅文字。对于本地 SQLite 这种毫秒级返回，纯文字够用；但一旦 project 故事线数量大或后端偶发慢，纯文字「加载中…」缺少旋转指示，用户难判断是「在加载」还是「卡了」。更稳妥的是统一用 `States.tsx` 里现成的 `<Loading>`（带旋转图标）替换裸文字，和 `EmptyState` 一样走规范组件。

**长列表滚动。** 这是本次评审里「看起来稳、实际上有隐忧」的一点。左列导航 `overflow-y-auto`、右列详情 `overflow-y-auto` 都正确，实测 288×746 与 734×746 两个滚动容器独立工作、不互相干扰，长标题用 `line-clamp-2` 不会撑破卡片——单看当前 13 条故事线，体验顺滑无瑕疵。但我要指出架构层面的两个「规模债」：① 没有虚拟列表，故事线一旦上百条，左列会把上百个 `LineNav` 卡片一次性渲染，且每条都跑 `computeStorylineProgress`（含七要素解析）；② 每次 `handleSave` / `handleToggleComplete` / 线索增删改后都 `void load()` 全量重拉并重算进度，操作越频繁、列表越大，主线程抖动越明显。现在没事，是因为数据量小；真正的风险是「规模上来那天没人记得这里没做分页」。这不构成当前体验缺陷，但应在架构评审里记一笔。

### 六、三主题（暗色 / 苍青 / 浅色）切换观感

novel-forge 提供三套主题：默认「虚空玻璃」暗色、青绿深的「苍青」、以及「昼面」浅色，均通过覆盖 `--nv-*` 令牌实现，组件零改动换肤。我基于令牌数值与对比度脚本（见附录）评估三套主题在故事线工作台上的可读性：

- **暗色（默认）：** 文字层级令牌经刻意调校，primary/secondary/tertiary/muted 在面板背景上分别达 14.98 / 7.99 / 5.41 / 4.72:1，全部过 AA。问题只在功能色文字（creative / primary 链接，见 F-02/F-04）。整体可读性优秀，是三套里最稳的。
- **苍青：** tertiary `#7C918D` on surface-3 合成达 5.23:1、muted `#6A807C` 4.8:1，均过 AA；青绿主色在深青底上辨识度高，可读性同样良好。说明团队为每套主题都做了独立的对比度预算，不是简单改 hue。
- **浅色：** 这是最容易翻车的主题（浅底 + 功能色小字）。令牌里专门为浅色提亮了 tertiary（`#5E616B`，surface-3 上 4.57:1）并新增 `--nv-accent-text-on-light` 变体解决金色小字在浅底对比度不足（F01 注释说明），连 `--nv-text-muted-on-surface-3` 都做了浅色专用值。能看到团队在浅色主题上花的功夫比暗色更细——因为浅色确实更难。唯一仍临界的是 placeholder muted（F-06）。

**结论：** 三主题的可访问性意识是这套产品最让我意外的亮点，远超同体量工具。真正要补的是「功能色文字 on 自身 soft 底」这一被漏掉的对比度组合（F-02/F-04），它跨主题都存在（creative 在浅色同样是用 soft 底，问题同源）。

### 七、动画与焦点反馈观感

细节体验上，故事线工作台的微交互是「有设计感」的：

- **入场动画：** 弹窗用 `animate-spring`（弹性缩放入场，line 645 定义 0.4s spring 曲线），左列/右列内容随弹窗一起弹入，不突兀；比起硬切，弹性入场给「打开了一个工作台」的仪式感。
- **按压反馈：** 全局 `button:active:not(:disabled){scale-[0.98]}`（globals.css:411），所有按钮按压都有轻微回弹，点击有「实感」；主操作 `.btn-primary` 还叠加了 inset 阴影模拟「按下去」的凹陷，触感层次更丰富。
- **hover 反馈：** 左列 `LineNav` 未选中时 hover 变 `surface-2` 底（line 837），右列操作按钮 hover 变对应功能色边框+文字（如删除 hover 变红），反馈明确、不喧宾夺主。
- **焦点环：** 全局 `button:focus-visible` 有 `ring-2 ring-ring/50 + ring-offset-2`（globals.css:417），键盘 Tab 时焦点清晰可见、且有 2px 透明间隙避免贴边——这是「键盘用户被当回事」的信号。实测 Tab 进弹窗后焦点确实落在可聚焦元素上（22 个可聚焦元素被陷阱约束）。

**可改进：** ① 4px 自定义滚动条（F-12）在触控环境难抓；② `prefers-reduced-motion` 已全局兜底（动画压到 0.01ms），但生成中的 `animate-spin` loader 在减少动效下会变成静止图标，用户可能误以为「卡住」而非「加载中」，建议减少动效时给 loader 一个静态但明确的「加载中」文字兜底；③ 弹窗内 AI 生成进行中没有任何动效/进度暗示（F-07），与产品其他处的动效语言不一致。

## 第二部分：总体视角

### 一、对项目的整体看法

站在一个既用过同类写作工具、也做过前端工程的评审者角度，我对 novel-forge 故事线工作台的整体判断是：**它已经跨过了「能用的 demo」门槛，进入「接近产品」的区间，但在「无障碍作为一等公民」和「极端状态的可感知性」这两道门槛前，还差最后几步打磨。**

积极面非常实在：七要素模型、AI 中间编辑态、真后台异步生成、三主题对比度调校、统一的三态组件、带焦点陷阱的弹窗——任何一条单拎出来都不稀奇，但**它们同时出现在 v1.8.9 这样一个本地小说写作工具里，说明团队有一套管线化的设计系统与质量意识**，而不是东拼西凑。尤其 `globals.css` 里那些「为 surface-3 专门提亮 muted 变体以满足 WCAG AA」的注释，证明对比度不是事后想起，而是被纳入了设计令牌的演进。

但我必须诚实指出，这个「接近产品」的状态里仍混着一些「半成品」的气息：
- 左侧栏高度塌陷（F-03）这种一眼可见的布局 bug 还活着，说明视觉走查可能没覆盖到「侧栏内容不足一屏」的真实场景；
- 键盘用户无法在左列标记完结（F-01），说明 a11y 检查还没下沉到「每个交互元素是否真是 button」这种颗粒度；
- AI 生成进行中几乎「无声」（F-07），说明异步状态的可感知性还没被当作体验问题来设计。

这些都不是致命伤，但叠加起来，会让人觉得「壳子很漂亮，内里还差几道工序」。所幸每一条都是低成本可修的——它们大多是对现有组件的局部修补，不需要重构。

我把这种状态概括为「九十分的壳，七十分的里」：视觉系统、设计令牌、主题化、弹窗基建都冲着九十分去；但「每个交互元素是否真 button」「功能色文字是否真达标」「侧栏是否真撑满」「异步是否真可感知」这些「里子」工程，还停留在七十分的自觉度。从产品成熟度曲线看，这恰恰是「从能用到好用」那道最磨人、也最值得过的坎——因为里子问题单条都不难，难的是建立一套能防止它们复发的流程（比如把「交互元素必须语义化」「功能色文字必须过对比度」写进组件 lint / 视觉回归测试）。novel-forge 既然已经有 `globals.css` 里那种「为对比度写论证注释」的文化，我相信补上这几道工序只是时间问题。

另外我想单独表扬一个容易被忽略的点：**这个产品的文案有「作者感」**。无论是把示例世界观（龙王寨、菜市场注释、尸检报告）揉进占位与说明，还是 toast 那句「「xxx」已完结 ✓」的轻巧正反馈，都让人觉得「做这工具的人自己写小说、或者至少深度访谈过写小说的人」。在工具类产品的体验里，这种「被懂」的感觉，比多一个图标、多一层毛玻璃值钱得多。这恰恰是很多堆功能的竞品最缺、也最难抄的东西。

### 二、架构与代码质量（仅与本 lens 相关）

从 UI 结构与组件边界看，这套代码有几个清晰的优点和几处可优化点：

**优点：**
1. **组件边界清晰。** `StorylineWorkbench`（弹窗主体）、`StorylineList`（列表入口）、`LeftPanel`（侧栏容器）职责分离；`Modal` / `DialogUI` / `States` 作为共享基建被复用，避免了「每个弹窗重写遮罩」的反模式（Modal.tsx 顶部注释明确写了「收编此前散落的两套 overlay 风格」）。
2. **状态管理分层合理。** 列表层（`StorylineList`）只负责「导航 + 打开工作台」；工作台层（`StorylineWorkbench`）通过 `initialId / initialTaskId / onClose / onRefresh` 解耦，AI 后台任务用 `startPolling` 这一独立 `useCallback` 被「列表入口挂载即轮询」与「工作台内生成」两处共用（注释 v1.8.7 明确说明收敛意图），没有重复轮询逻辑。
3. **卸载清理到位。** `StorylineWorkbench` 用 `useEffect` 在卸载时 `clearInterval(pollRef.current)`（line 78-82），避免定时器泄漏；且注释明确「服务端任务不受影响，关页面继续跑」——异步心智正确。
4. **设计令牌集中。** 所有颜色走 `--nv-*` CSS 变量，组件里几乎看不到硬编码色值，换肤（dark/azure/light）零改组件。这是可持续的架构。

**可优化点（UI 结构相关）：**
1. **「更多 ▾」菜单与 visibleTabs 的耦合略脆。** `LeftPanel` 里 `visibleTabs` 写死 4 个、`moreTabs` 写死 1 个（line 43-51），新增 Tab 要同时改两处，且「故事线」被硬编码进常显组。若未来 Tab 增多，这套 if/more 的切分会再次失衡。更稳的做法是给每个 Tab 标 `priority`，运行时按可用宽度自动决定常显/收起。
2. **`LineNav` 的完结切换用了 `<span onClick>` 而非 `<button>`**（line 862-875）。这是「为了 hover 样式方便而绕过语义元素」的典型妥协，直接导致 F-01。在 React 组件里，凡是可点击、可触发状态变更的元素，都应优先用 `<button>`（或至少 `role="button"` + `tabIndex=0` + 键盘监听）。
3. **重复样式散落。** 左列 `LineNav` 的选中高亮、右列「标记完结」按钮、线索区按钮，各自手写 `hover:border-[var(--nv-x)]/50 hover:text-[var(--nv-x)]` 这类组合，没抽成统一工具类。一旦要统一 hover 语言，要改多处。建议沉淀如 `.icon-btn` / `.pill-btn` 之类的原子类。
4. **`btn-ghost` 与 `variant="outline"` 可能叠加。** 工作台「放弃」按钮同时传 `variant="outline"` 和 `className="btn-ghost"`（line 482-483）。需确认 `Button` 组件在 outline + btn-ghost 时不会出现「双边框 / 双重底色」。这是样式契约不清晰留下的隐患（F 类）。
5. **空/错/载三态在列表层与弹窗层各写一遍**（StorylineList:110/137/146 vs StorylineWorkbench:502/503/511），虽都用了 `EmptyState`，但加载/错误的内联结构未抽成统一小组件，存在「两处未来不同步」的漂移风险。
6. **缺少「可访问性／视觉回归」的自动化闸门。** 从仓库根目录能看到 `e2e-*.mjs`、`contrast_calc.mjs`、`contrast_table.mjs` 等脚本，说明团队已在用脚本辅助质量；但对比度计算（contrast_calc.mjs）目前是「手动跑、人工看结果」，尚未接成 CI 门禁，也未覆盖「功能色文字 on soft 底」这一组合（正是 F-02 漏掉的原因）。建议把 `contrast_calc.mjs` 扩展为对所有 `--nv-*` 文字/背景两两组合的自动断言，并在 CI 失败，从源头防住对比度回归。

### 三（补）、可访问性合规总评（WCAG 2.1 AA 视角）

把上面所有 a11y 发现收口成一张合规清单，便于团队直接对着修：

- **1.1.1 键盘（A 级）：F-01 不通过。** 左列完结切换是 span 非 button，键盘不可达。这是唯一一条硬性的 A 级不通过项，优先级最高。
- **1.4.3 对比度（AA 级）：F-02、F-04 不通过；F-06 临界。** 功能色文字（creative / primary 链接）on 自身 soft 底或深底跌破 4.5:1；placeholder muted 4.33:1 临界。文字层级主/次/三/弱在常规背景上均过 AA，是合规基本盘。
- **4.1.2 名称／角色／值（A 级）：F-01、F-05 部分不通过。** 弹窗 `aria-labelledby` 已正确关联（通过），但图标按钮缺 `aria-label`（F-05）、非 button 交互元素无角色（F-01）。
- **2.4.7 焦点可见（AA 级）：通过。** 全局 `focus-visible` 焦点环存在，实测 Tab 焦点清晰。
- **2.1.1 / 2.1.2 无键盘陷阱（A 级）：通过。** 弹窗焦点陷阱只在内聚焦、Esc 可退出，未形成永久陷阱。
- **1.4.11 非文字对比度（AA 级）：F-12 临界。** 4px 滚动条在粗指针环境难抓取，建议 `@media (pointer:coarse)` 加宽。
- **1.3.1 信息／关系（A 级）：基本通过。** 主线/支线层级靠图标+缩进表达，但有弱化风险（F-13），建议强化文字层级。

**一句话结论：** 故事线工作台在 WCAG 2.1 AA 上「基础盘稳、两处硬伤」——把 F-01（键盘）与 F-02/F-04（对比度）修掉，即可从「大部分合规」跃升到「实质合规」；其余为打磨项。考虑到团队已有对比度脚本与焦点环基建，这两步的边际成本极低。

### 三、质量与风险判断

按「断链 / 空按钮 / 未处理异常 / 性能瓶颈 / 数据一致性」五个维度评估：

1. **断链 / 空按钮：未发现。** 所有可见按钮都有 handler；AI 生成、编辑、保存、删除、完结、线索增删改均有对应 fetch 与 toast 反馈。没有「点了没反应」的死按钮。这一点比很多产品强。

2. **未处理异常：基本覆盖，但边缘有缝隙。**
   - `load()`（line 133-151）对 HTTP 非 200 与网络异常都有 `setError` + 重试，良好。
   - `handleGenerate` / `handleCommitGen` / `handleSave` 等均有 `try/catch` + toast，良好。
   - **缝隙：** AI 轮询 `startPolling`（line 89-121）里，网络抖动被 `catch {}` 静默吞掉（line 118-120），只靠「下一拍再试」。若后端任务已 `failed` 但某次轮询恰好网络错误，用户会一直看到旋转 loader 直到下一次成功轮询才拿到 failed——极端情况下进度卡死且无声。建议在网络错误累计 N 次后主动提示。
   - **缝隙：** `handleCluePatch` / `handleClueDelete`（line 344-363）的 catch 只 toast 不刷新，若 PATCH 失败本地状态可能与服务端不一致（不过它们调完都 `void load()` 重拉，实际会自愈，尚可）。

3. **性能瓶颈：未见明显问题。**
   - 列表与详情都是按需 fetch，无全量重渲染迹象；`line-clamp-2`、固定列宽避免了长标题撑破布局。
   - AI 轮询间隔 1500ms（line 121），频率温和，不会压服务端。
   - 潜在点是：每次 `load()` 都重拉全量 storylines 并 `setList`，若故事线数量极大（上百条），左列 DOM 与进度条计算（`computeStorylineProgress`）会随每次操作全量重算。当前 13 条无感，但架构上没做分页/虚拟列表，属「现在没事、规模上来会痛」的债务。

4. **数据一致性：有两处需警惕。**
   - **F-08（AI 草稿不持久化）：** `genSuggestions` 仅存于组件内存（line 69）。若用户在 AI 生成完成后、点「采用并落库」之前关闭了工作台，这批已生成、未落库的建议就丢了——即使服务端任务已 `done`，再次打开工作台也不会自动回显（因为 `initialSuggestions` 只在初次传入）。对作者而言，「我刚让 AI 想好的故事线，关个弹窗就没了」是实实在在的数据丢失感。建议：生成完成后把 suggestions 暂存到 store / 后端草稿，重开可续。
   - **F（类型/归属一致性）：** `handleSave`（line 269）里 `parentId: form.type === "main" ? null : form.parentId || null`，逻辑正确；但 `startEdit`（line 249）把 `parentId: s.parentId ?? ""`，而编辑态 `select` 的「无归属」选项是 `value=""`。前后用空串/ null 表示「无归属」一致，OK。这条无风险，记一笔以示已查。

5. **可访问性总体风险（本 lens 核心）：** 见发现清单。最高优先级是 F-01（键盘不可达的完结切换）与 F-02（功能色文字对比度）。这两者都属 WCAG 2.1 AA 的硬性条款（2.1.1 键盘、1.4.3 对比度），在合规审计里会被记为不通过项。

## 发现清单（结构化，附证据）

> 严重度说明：P0=阻断使用/数据安全；P1=重要（a11y 合规或明显体验缺陷）；P2=次要/打磨。
> 对比度计算基于 `globals.css` 令牌换算 sRGB 后按 WCAG 2.x 公式；布局尺寸基于 1440×900 视口 Playwright 实测。

### P0（未发现阻断性缺陷）
- **P0-0**：本轮评审**未发现**阻断性 P0 缺陷。数据落库、删除、AI 生成均有 `try/catch` + toast 兜底，未发现死按钮或断链。以下为 P1/P2 级可修复项。

### P1（重要）

**[F-01] 严重度 P1 · 键盘/读屏不可达的「标记完结」切换**
- 文件:行号：`src/components/workspace/StorylineWorkbench.tsx:862-875`（`<LineNav>` 内的完结切换）
- 现象：左列导航每条故事线右侧的「标记完结/已完结」切换是一个 `<span onClick={...}>`（line 863），不是 `<button>`，没有 `role`、`tabIndex` 或 `aria-label`。鼠标点选正常，但键盘 Tab 无法聚焦、Enter/Space 无法触发、读屏不报「标记完结」。
- 根因推测：为复用 hover 样式（`hover:text-[var(--nv-accent)]`）与 `stopPropagation` 方便，直接用 span 承载点击，绕过了语义化交互元素。
- 建议修法：改为 `<button type="button" aria-label={s.status==='completed'?'取消完结':'标记完结'} onClick={(e)=>{e.stopPropagation();onToggle();}}>`，保留 `stopPropagation` 以免误触发选中。右列详情里同样的切换已是标准 button（line 676），可作范本。

**[F-02] 严重度 P1 · AI 生成按钮文字对比度未达 WCAG AA**
- 文件:行号：`StorylineWorkbench.tsx:398-413`（头部 AI 生成按钮）、`StorylineList.tsx:118-133`（列表 AI生成按钮）
- 现象：按钮文字用 `text-[var(--nv-creative)]`（紫罗兰 oklch(0.62 0.21 295)）压在 `bg-[var(--nv-creative-soft)]`（同色 /0.14 浅底）上。实测对比度：
  - creative 文字 on creative-soft = **3.75:1**（正常 12px 文字要求 ≥4.5:1，未达标）；
  - creative 文字 on 面板 = **4.48:1**（同样未稳过 4.5）。
  - 列表入口按钮字号仅 `text-[10px]`（更小），对比度要求更严却更弱。
- 根因推测：设计令牌调校覆盖了「文字层级（primary/secondary/tertiary）on 背景」，但漏了「功能色文字 on 自身 soft 浅底」这一组合；creative-soft 透明度 0.14 过低，导致底色仍接近深色，而文字本身明度不足以拉开差距。
- 建议修法：① 提高 `--nv-creative-soft` 不透明度至 ~0.22，或 ② 把按钮文字改用在 creative-soft 上达标的中性浅色（如 `#EDE6FF`），或 ③ 直接采用 `.btn-creative` 那套「深底 + 浅字（#F0EEE8）」的实心按钮样式（其渐变底对比度远高于 soft 底）。优先方案③，视觉也更像「主操作」。

**[F-03] 严重度 P1 · 左侧面板 `<aside>` 未撑满抽屉高度，底部大面积留白**
- 文件:行号：`src/components/workspace/LeftPanel.tsx:55`（`aside` 类 `w-64 … flex flex-col shrink-0 overflow-hidden`，无 `h-full`）
- 现象：实测 drawer 容器 `fixed inset-y-0 left-0 z-40 w-64 h-full` 高度 = 805px，主内容区 `main` 高度 = 805px，但内部 `<aside>` 高度仅 **283.97px**。侧栏下半部约 520px 为空白带，与右侧 805px 内容区高度严重不一致，第一眼像「面板没加载完」。
- 根因推测：drawer 容器是 `display:block` 且 `h-full`，但 `<aside>` 作为子元素没有 `h-full` / `min-h-full`，于是塌缩为内容高度；父链 `align-items` 也非 stretch。
- 建议修法：给 `<aside>` 加 `h-full`（或 `min-h-full`），并把 drawer 容器改为 `flex` 以保证子项拉伸；同时确认侧栏内部 `overflow-y-auto` 的滚动容器正确继承高度。

**[F-04] 严重度 P1 · 错误态「重试」链接对比度未达 AA**
- 文件:行号：`StorylineWorkbench.tsx:506`（左列错误重试）、`StorylineList.tsx:140`（列表错误重试）
- 现象：重试链接用 `text-[var(--nv-primary)]`（靛蓝 oklch(0.66 0.19 270)）压在面板/列表背景上，实测 **3.79:1**，未达 4.5:1；且字号为 `text-[10px]`，属正常小字，要求更严。
- 根因推测：同 F-02，功能色文字直接当链接色用在深底上，未纳入对比度调校。
- 建议修法：重试链接改用已达标的中性浅色（如 `--nv-text-primary` 或 `--nv-info` 在浅底上的变体），或把底色局部提亮；至少保证 ≥4.5:1。

**[F-05] 严重度 P1 · 图标型按钮缺 aria-label（线索区 / 线索集展开）**
- 文件:行号：`StorylineWorkbench.tsx:942,949`（线索编辑/删除图标按钮，仅 `title`）、`StorylineWorkbench.tsx:770`（线索集展开按钮，仅图标+文字混排无 label）
- 现象：线索行的「编辑/删除」是纯图标 `<button>`，仅有 `title` 属性，无 `aria-label`；读屏对 `title` 的播报不可靠（多数读屏默认不读 title）。删除是危险操作，缺可访问名风险更高。
- 根因推测：icon-button 未统一约定「必须带 aria-label」，部分按钮（如右列删除 line 701）带了，部分（线索区）没带，契约不统一。
- 建议修法：所有图标按钮补 `aria-label`（如「编辑线索」「删除线索」）；可在 `Icon` 组件或统一 `icon-btn` 类上强制约定。

**[F-06] 严重度 P1（边界）· 输入框占位符对比度临界**
- 文件:行号：`src/app/globals.css:613-615`（`input-glass::placeholder` 用 `var(--nv-text-muted)` #8E8B82）、`src/components/workspace/DialogUI.tsx:46,52`（placeholder 文案）
- 现象：占位符文字 `#8E8B82` 压在输入框底（约 rgb(27,33,48) 合成）上实测 **4.33:1**，低于 WCAG 对占位符「建议 ≥4.5:1」的最佳实践（虽 placeholder 非强制 4.5，但属明确欠账）。
- 建议修法：占位符改用 `--nv-text-tertiary`（#98968C，5.41:1）或提亮 muted 一档；与「文字层级」令牌统一。

### P2（次要 / 打磨）

**[F-07] 严重度 P2 · AI 生成进行中缺区域级可感知进度**
- 文件:行号：`StorylineWorkbench.tsx:406,426`（生成中仅按钮文字变化；genSuggestions 覆盖层仅 done 后出现）
- 现象：点 AI 生成后，弹窗主体仍显示普通列表视图，只有右上角按钮「生成中… 10%」在变。长任务下用户无法判断进度归属与完成预期。
- 建议修法：生成中在右列/主体显示骨架屏或「AI 正在构思故事线…」区域态 + 进度环；或把百分比/步骤提示从按钮移到更显眼处。

**[F-08] 严重度 P2 · AI 草稿（genSuggestions）不持久化，关弹窗即丢失**
- 文件:行号：`StorylineWorkbench.tsx:69,215-239`
- 现象：`genSuggestions` 仅组件内存；完成后未落库前关闭工作台，下次打开不会回显（initialSuggestions 仅初次传入），已生成的建议实质丢失。
- 建议修法：生成 done 后把 suggestions 写入 store 或后端草稿表；重开工作台时若有未采纳草稿则直接进中间编辑态。

**[F-09] 严重度 P2 · 三级文字令牌对比度裕量偏紧**
- 文件:行号：`src/app/globals.css:116`（`--nv-text-tertiary` #98968C，注释称 5.2:1）
- 现象：实测 tertiary on 左列 surface-1 = 4.97:1，已贴近 AA 下限 4.5；一旦背景换成更亮的 surface-2/surface-3 或浅色主题微调，极易跌破。属「达标但零裕量」风险。
- 建议修法：为 tertiary 预留 ≥0.3:1 裕量（如提亮至 ~#A2A099），或在令牌文档标注「禁止 tertiary 用在比 surface-1 更亮的底上」。

**[F-10] 严重度 P2 · 窄屏 / 高密度下布局与 Tab 挤压**
- 文件:行号：`StorylineWorkbench.tsx:386`（`max-w-5xl` 无 md 断点收窄左列）、`LeftPanel.tsx:56-62`（5 个 Tab 各 ~51px）
- 现象：工作台在 <1024 视口贴边；左列固定 288px 占比过高。侧栏 Tab 在 256px 内各 51px，「角色 (15)」等带计数标签已贴边，计数变三位数必溢出/换行。
- 建议修法：工作台加 `md:` 断点把左列收窄或改为可收起；侧栏 Tab 超宽时省略计数（如「角色」）或自动收进「更多」。

**[F-11] 严重度 P2 · 时间轴空态未复用 EmptyState 规范**
- 文件:行号：`StorylineWorkbench.tsx:759-763`
- 现象：章节进展时间轴为空时仅一行弱灰提示（text-tertiary），与全局 `EmptyState`（插画图标 + 标题 + 行动）三态规范不一致。
- 建议修法：复用 `<EmptyState icon="history" title="还没有章节进展" description="写作时会自动回写大事件" />`，统一视觉语言。

**[F-12] 严重度 P2 · 4px 自定义滚动条触控难抓取**
- 文件:行号：`src/app/globals.css:709-721`（`custom-scrollbar` 宽 4px）
- 现象：滚动条仅 4px，hover 才显形；无鼠标（触控板/触屏/粗指针）环境下极难定位抓取。
- 建议修法：至少在非精确指针（`@media (pointer:coarse)`）下加宽至 8-10px，或保留常显细滚动条。

**[F-13] 严重度 P2 · 左列主线/支线文字层级仅靠图标区分**
- 文件:行号：`StorylineWorkbench.tsx:850-853`（选中/主线/支线文字在左列均主要为 text-primary，仅图标 star/arrow 区分类型）
- 现象：未选中的主线与支线在左列都用 `text-[var(--nv-text-primary)]`，类型区分仅靠前导图标，弱视觉层级；在长列表里容易看混「这是主线还是支线」。
- 建议修法：主线标题可加权（如 `font-semibold`）或支线用次级色，强化层级差异。

**[F-14] 严重度 P2 · 「btn-ghost」与 `variant="outline"` 可能叠加**
- 文件:行号：`StorylineWorkbench.tsx:482-483`（放弃按钮）、`StorylineWorkbench.tsx:638`（取消按钮）同模式
- 现象：多处 `<Button variant="outline" className="btn-ghost">`，需确认 `Button` 组件在 outline + btn-ghost 时不会出现双边框/双重底色。属样式契约不清晰隐患。
- 建议修法：明确 `Button` 各 variant 与全局 `.btn-*` 类的互斥/叠加规则，或统一只用其一。

**[F-15] 严重度 P2 · 「AI生成」/「AI 生成」文案空格不统一**
- 文件:行号：`StorylineList.tsx:130`（`AI生成`）vs `StorylineWorkbench.tsx:410`（`AI 生成`）
- 现象：同一功能标签在同一产品两种写法，略显随意，也影响搜索/一致性。
- 建议修法：统一为「AI 生成」（带空格，更符合中文排版）。

**[F-16] 严重度 P2 · 轮询网络错误被静默吞掉，极端情况进度卡死无声**
- 文件:行号：`StorylineWorkbench.tsx:118-120`（`catch {}` 仅下一拍重试）
- 现象：轮询中若某次 fetch 网络错误，被空 catch 吞掉，只在下一拍重试；若后端已 failed 但本次网络错，用户持续看到旋转 loader 且无声。
- 建议修法：累计网络错误次数，超过阈值（如 5 次）主动 toast「生成状态同步失败，请重试」并停止轮询，避免无限静默。
