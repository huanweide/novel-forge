## 第一部分：用户体验视角（约 5600 字）

### 1.1 初次进入：教程与就绪态

以真实用户身份从工作区点进某章节的「游戏模式」路由，首屏出现一块模态教程（page.tsx:521-562）。教程文案清楚：把"写这一章"变成"互动跑团"，AI 扮演剧情引擎，每轮给叙事+选项，你选或自由输入，边玩边写出正文；并明确承诺「本章已有正文会带入游戏（含原有字数）——游戏从现有内容之后续接，不推翻已写情节」「世界观、角色卡、章纲全部生效，与工作区设定实时联动」。文案质量整体中等偏上，没有中英混排硬伤，emoji 被统一禁用、改用 `<Icon>`，符合设计体系。

但教程有一个隐患：它承诺"不推翻已写情节"，而后续真实导出行为恰恰推翻了已有正文（见 [G1]），这是"文案许诺"与"代码行为"的直接矛盾，是本次体验中最严重的用户可感知问题。

关闭教程后进入就绪态（showStartScreen）。中央是「游戏模式已就绪」卡片，主按钮「开始游戏」，下方「构思开头」次级按钮。布局留白充足、主行动非常醒目，第一眼知道该点哪。右栏默认「正文」标签显示"正文将在游戏互动过程中实时生成…"的空状态提示，左栏「情节」显示"暂无情节点数据"——空状态文案得体，不空洞。

### 1.2 构思开头（concept）：加分项，但边界清晰

点「构思开头」→ 调 `/api/game/concept`，按钮变「构思中…」禁用态，约 1–2 秒返回一段 2–4 句的钩子构思（实测温 237 字），并给出「建议的起始行动」。随后出现三个按钮：「采用此构思开场」「重新构思」「不用，直接开始」。这套交互完整、无断链，且"重新构思"可重跑、"不用"可直开，选择权交还用户，体验加分。

需要注意的细节：concept 是**非流式**接口（route.ts:88 之前收集完整响应，concept 同理），所以构思期间只有按钮的"构思中…"文案，没有进度条。对一段 200 字左右的小文本，等待可接受；但若 LLM 较慢，用户面对的是一个静止的次级按钮，缺少任何"进行中"的视觉反馈（顶部不确定进度条只在 generating/ending 态出现，concept 态不在其列）。这是一处可被感知的"无反馈空窗"。

### 1.3 开局（start）：能跑通，但"等得没底"

点「开始游戏」后，状态切到 `generating`，顶部出现一条紫→青的不确定进度条（page.tsx:486-489）。后端 `game/start` 是**非流式**收集（start/route.ts:88-94），把整段开场叙事一次性算完再返回。实测开场叙事 ~488 字，从发请求到叙事整段落地的端到端延迟约数秒（取决于模型）。

**问题一：开局期间没有"停止"按钮。** 底部动作栏（含「停止」）只在 `status==="playing"` 渲染（page.tsx:1217-1224），而开局期间状态是 `generating`，所以底部栏不显示，"停止"按钮不可见。用户在此期间面对的只有顶部进度条，若 LLM 卡住或想换构思，没有取消入口，只能干等或刷新页面。这属于"卡死无退路"的可感知缺陷（见 [G5]）。

**问题二：开局非流式 ≠ 行动流式，体验割裂。** 开局整段"啪"地出现，而随后的每轮行动是逐字流式的。同一场游戏里，第一段是"整段出现"、后续是"逐字流出"，节奏不一致，老用户会疑惑"为什么第一段不像后面那样打字出来"。

抛开这两点，开局本身过得去：返回的叙事质量尚可，自动给出 3–4 个编号选项（不足 2 个时后端有兜底三选项），左栏"情节"出现第 1 轮卡片，右栏"正文"开始累积，"背包"空态提示友好。

### 1.4 每轮行动（action）：体验最顺的一段

进入 `playing` 后，底部出现 6 个快捷动作（观察/对话/战斗/探索/使用物品/休息）+ 一个自由输入框 + 「发送」。点选项或快捷动作或回车发送，状态切 `generating`，SSE 逐 token 流式渲染到主画布，右上「停止」按钮出现，可中途打断。

实测 SSE 字节流健康（`text/event-stream`，17580 字节，token 事件连续，末尾 `game_done` 携带 narrative/options/newEntities/itemChanges/plotProgress/wordCount）。流式渲染顺滑，没有"先空白很久再整段弹"的现象。每轮结束：左栏情节进度条+轮次卡片更新，右栏字数进度条（按 3000 上限）增长，新实体触发顶部"发现：角色·xxx"药丸提示 + 粒子爆发（GameParticles）。这些微反馈让"每轮推进"有正反馈感，是目前体验里最舒服的环节。

可感知的小瑕疵：
- **自动推进**开启后，每轮结束 1.4 秒自动以"自动推进剧情"作为玩家行动再跑一轮。问题是这个字面串会被写进左侧情节列表的"玩家行动"里（page.tsx:393-399），看起来像用户自己输入了"自动推进剧情"，语义暧昧（见 [G7]）。
- 选项区是 2 列网格固定 3–4 个，若某轮 AI 给到 4 个选项，第 4 个和前 3 个同宽，没问题；但选项文本较长时 2 列会换行挤压，移动端更明显。

### 1.5 停止 / 中断：设计周全，但依赖后端对账

点「停止」→ `streamRef.abort()`，触发后端 `processGameTurn` 的 abort 透传（game-engine.ts:339-340、348、399-401），丢弃本轮不落库，再 `reconcileWithBackend()` 用 GET /api/game/state 的权威态整体覆盖前端（page.tsx:420-428）。这一套在单元测试里有 5 个用例覆盖（abort 不提交、$transaction 0 次、chatStream 携带 signal、AbortError 不产 error 事件、空流不产幻影轮次），真机我也验证过 SSE 正常。结论：停止=放弃本轮的语义是干净且自愈的，不会出现"前端显示第 5 轮、后端只有第 4 轮"的错位。这是架构上做得扎实的地方，值得肯定。

### 1.6 回退：能撤销上一轮，但语义藏得深

左栏底部「回退」按钮（page.tsx:721-781），`disabled={turns.length<=1}`。点它调 `DELETE /api/game/state?round=N`，后端删除该轮及之后并回滚 session 的 currentRound/totalWords/plotProgress（state/route.ts:8-62），然后前端用返回的权威摘要整体覆盖。覆盖逻辑处理得比早期版本稳（优先用后端摘要，失败才前端重建）。可感知问题：回退按钮位置在左栏最底部、字号小、无图标，容易被忽略；且它和"停止"是两套不同的撤销语义（停止=放弃进行中本轮，回退=删除已完成的上一轮），新手可能分不清（见 [G13] 轮号依赖风险）。

### 1.7 结束并导出：最关键的"翻车点"

玩到想收尾，点顶栏或右栏底的「结束并导出」→ `game/end` → 后端 `endGameAndExport` 检查章纲「章尾悬念」钩子、生成 2–3 段收尾、拼接全部叙事、落 `node.content`，再走轻确认（见 1.8）。导出期间有全屏"正在收束并导出本章正文…"遮罩（page.tsx:492-502），避免误操作。

**致命问题（[G1]）**：若这一章在写作模式里本来就有正文，开局时 prompt 会让 AI"从现有正文之后续接"，但导出时 `endGameAndExport` 只拼接 `session.states`（游戏轮次叙事），**完全不把 node 原有正文纳入 finalContent**（game-engine.ts:546-553、611-612）。我实跑验证：原正文"林惊羽握紧断剑，立于悬崖之巅…"（41 字）在导出后从 node.content 消失，导出正文以全新 AI 文本"风雪灌入脖颈…"开头。也就是说，用户在写作模式辛苦写的内容，一旦"结束游戏导出"就被无声覆盖。教程还明说"不推翻已写情节"——这是承诺与行为的硬矛盾，且对用户是**不可逆数据丢失**。这是本次体验唯一会让我作为用户" rage quit"的问题。

### 1.8 轻确认（light-confirm）边界：主路径顺、副作用隐蔽

导出时的状态走 `evaluateConfirmEligibility` + `applyConfirm`（confirm-guard.ts）。主路径：项目「智能审阅」默认开且质量达标 → `status=confirmed` + `reviewLogs` 追加 `auto-confirm` + 自动填表（safeFillAfterWriting）+ 质量分回写（实机 qualityScore=88/91）。边界：关掉 `autoConfirmEnabled` → `status=drafting`，由用户去确认栏手动定稿（实机验证通过）。结束页脚据此显示「已导出并自动定稿（质量分 88）」或「待你手动确认」。这条边界清晰、可预测，真机闭环我完整跑通、断言全过，是游戏模式里"确定可用"的硬证据。

**隐蔽副作用（[G2]）**：主路径自动确认时，`applyConfirm` 会触发 `safeFillAfterWriting` 自动回填世界书/角色卡。也就是说，游戏导出一章，会**静默改动项目的设定库**（世界书新增词条等）。对写作模式的"自动确认"这是预期能力，但对"玩一局游戏导出正文"的用户而言，导出动作顺带改了设定，界面没有任何"已自动回填设定"的提示，属于超出预期的副作用。

### 1.9 与写作模式的切换与状态混淆

游戏页通过顶栏「返回工作区」（`router.push(/workspace/{projectId})`）回到主工作区，路由完全独立（独立暗黑沉浸 UI），不会误把游戏态带进写作编辑器。游戏数据存在独立的 `gameSession`/`gameState` 表，与写作的 `storyNode` 通过 `nodeId` 关联——**状态隔离是干净的**：游戏轮次/背包不会污染写作编辑器的内存态。

但"混库"点在于导出：游戏最终把正文写回同一个 `storyNode.content` 并改写其 `status`（confirmed/drafting）。所以"游戏"和"写作"在**章节节点这一层是共享的**。这带来两个用户可感知风险：
1. 如前所述，游戏导出会覆盖节点原有正文（[G1]）；
2. 游戏导出把节点置为 confirmed/drafting，直接进入写作模式的确认流——若用户在写作模式正编辑同一节点（虽然 UI 上不能同时打开两个路由，但 DB 层面无锁），游戏导出会覆盖其未保存或已保存的编辑。建议对"进行中游戏会话的节点"加写锁或导出前 diff 提示。

### 1.10 本地推理（Ollama）可用性

设置里把 `llmProvider` 设为 `local` 后，`getSettings` 走免 Key 分支（src/lib/llm.ts:77-86），只需填 Base URL（默认 `http://localhost:11434/v1`）和模型名。`createLLMClient` 对 OpenAI 兼容协议通用，Ollama 完全可用，游戏链路无需任何 Key。这点对"本地运行、隐私优先"的 Novel Forge 定位是加分项。

但你要注意：Ollama **没有零配置自动发现**——用户必须手动在设置里切到 local 并填 URL；且推理预算保护（`resolveMaxTokens` 对命中 `REASONING_MODEL_RE` 的模型强制抬到 2500）只认模型名正则，本地小模型若不命中则沿用小预算，可能产出偏短/偏空正文而无明确告警（见 [G12]）。此外，若 Ollama 没启动，game/start 会优雅返回 500「无法连接 AI 服务」（mapLLMError 翻译过），前端把错误显示在就绪屏，不会白屏——失败处理是体面的。

### 1.11 文案、按钮、暗色对比度、响应式

- **文案**：整体准确、口语化，无明显错别字/语病；"回退""自动推进""结束并导出"等术语一致。唯一硬伤是教程"不推翻已写情节"与 [G1] 行为矛盾。
- **按钮可见性/禁用态**：「开始游戏」主按钮阴影+发光，醒目；快捷动作在 `playing` 才可用，禁用态 `opacity-40` 清晰；「发送」在输入框为空时禁用。禁用态表达到位。
- **暗色对比度**：采用 "Void Glass" 体系（`--nv-void` 底 + `--nv-creative` 紫罗兰主调）。正文用 `--nv-text-secondary`、强调用 `--nv-creative`、成功用 `--nv-success`、危险用 `--nv-danger`。我无法在此环境做像素级对比度仪测，但变量体系分层合理；需提醒：左栏"势力"等次要文字用 `--nv-text-tertiary`，在纯黑底上若饱和度偏低可能偏灰——建议后续用对比度工具抽样（此项为方法局限，未做截图验证）。
- **响应式**：三栏在 `lg` 以下折叠为可切换抽屉（左/右各一个 `lg:hidden` 切换按钮 + 遮罩 + 焦点陷阱 focus-trap），窄屏主体仍可玩。抽屉 `inert` 主区域逻辑正确。缺陷：选项区 2 列在极窄屏（<360px）会拥挤；教程卡片 `max-w-lg` 在手机上左右留白略紧。

## 第二部分：总体视角（约 4500 字）

### 2.1 游戏闭环是否成立、是否"确定可用"

**结论：闭环成立，且"确定可用"。** 我用真机把 concept→start→action×N→end 完整跑通，并且官方轻确认脚本断言全过（confirmed + auto-confirm reviewLog + qualityScore 回写；边界 drafting）。SSE、abort 对账、回退、空流保护都有单元+真机双重证据。对于一个 v1.0.0 正式版，游戏模式不是"能跑的 demo"，而是可信赖的主功能。

但"可用"不等于"无坑"。最硬的一块石头是 [G1] 的数据丢失：它是闭环里"导出"这一环的语义错误，直接动摇"游戏模式安全用于已有章节"的信心。如果官方定位是"游戏模式主要用于从章纲/空节点开新章"，那应在教程里去掉"带入已有正文不推翻"的承诺，并改为"游戏会基于现有正文续写并覆盖"。当前既承诺不推翻、又实际覆盖，是必须修的 P0。

### 2.2 与写作模式的状态隔离是否干净

**隔离在"内存/UI 层"干净，在"存储/节点层"共享，且共享处无保护。**

- 干净处：`gameSession`/`gameState` 与写作编辑器完全分离；游戏轮次、背包、实体面板都是游戏页私有状态；路由独立不会串内存。abort/回退的对账机制保证前后端轮次一致（P0-1/P0-2 在单测中有 5 个用例护航）。
- 风险处：导出把正文与 `status` 写回 `storyNode`，与写作模式共用同一节点。这里没有"该节点是否正在被写作模式编辑"的锁或冲突提示；且 [G1] 的覆盖式写入对原正文是破坏性的。架构上建议把"游戏导出"视作对 `storyNode` 的一次"受控提交"，在写入前对 `existingContent` 做保留/合并，而不是整体覆盖。

### 2.3 架构与代码质量

**模块边界清晰，重复代码少，但类型安全偏弱、存在若干可维护债。**

优点：
- 提示词归一化点唯一（game-prompts.ts 的 `OP_MAP`，中文操作→英文枚举），避免了四处比较分支（注释里也写明了"唯一需要改动的地方"）。
- 物品变动 `applyItemChanges`（引擎）与 `applyFrontendItemChanges`（前端）逻辑对齐，且有单测覆盖 name+owner 隔离、unequip/destroy/skip 分支；背包按 (name, owner) 二元组隔离，处理得很细致（阿游 P1）。
- 推理模型预算保护收敛在 client 的 `resolveMaxTokens`（start/action 调到 2500，concept 经 client 自动抬），N1 空正文问题从架构层根治，而非在各路由打补丁。
- 轻确认复用写作模式的 `confirm-guard`（evaluateConfirmEligibility/applyConfirm），单一质量阈值真相源（`QUALITY_PASS_THRESHOLD`），避免阈值分裂。

债与隐患：
- **类型安全弱（[G8]）**：game-engine 里 JSON 列的读写几乎全用 `as unknown as any[]` / `as any`（如 game-engine.ts:185、243、431-449 的 upsert data）。`parseGameOutput` 返回的是有类型结构，但落地时全部 cast，解析结构与持久化结构之间没有编译期约束，未来改字段名极易引入"静默字段错位"。建议为 gameState 的 items/entities/options 定义严格 Json 类型或 zod 运行时校验。
- **`maxWords` 硬编码 3000（[G4]）**：start/route.ts:54 与 game-engine.ts:163 各写死一次，未从项目/章节配置读取；进度条上限恒 3000，章节篇幅不可配置。
- **每轮重发 existingContent（[G10]）**：game-prompts.ts:234-236 把原章节正文（最多 3000 字）每次行动都塞进 system prompt，是恒定 token 开销，长游戏里累积浪费明显（虽单次不算大，但属可优化）。
- **早期剧情记忆衰减（[G9]）**：historySection 仅取最近 6 轮、每轮叙事截断 150 字（game-prompts.ts:265-274）。超过 6 轮后，早期事件/伏笔在 prompt 中消失，AI 可能前后矛盾或遗忘伏笔——对"长线跑团"是真实的质量天花板。
- 测试覆盖偏"纯逻辑"：game-engine.test 用 vi.mock 把 prisma/llm 全 mock 掉，验证的是纯函数与生成器控制流，未覆盖 `endGameAndExport` 的"导出覆盖原正文"这一真实 IO 路径（正是 [G1] 漏网之处）。建议补一个集成测试：带 existingContent 的节点 end 后断言 content 含原正文。

### 2.4 质量与风险判断

- **断链**：未发现前端调不存在接口的情况；所有按钮都有对应路由（concept/start/action/end/state 均存在且 200/400 行为正常）。
- **空按钮**：无 onClick 为空的按钮；「回退」在 `turns.length<=1` 时禁用、「停止」仅在 generating 可见、「发送」在空输入禁用——禁用态语义合理。
- **未处理异常**：各路由均有 try/catch 返回 jsonError；SSE action 路由对 error 事件有 write；LLM 调用失败有 mapLLMError 中文翻译；空流/abort 均有优雅处理。异常面比多数同类项目扎实。
- **性能（上下文累积）**：每轮重建 system prompt，包含 existingContent(≤3000) + 世界观(8×150) + 角色(20) + 历史(末 6 轮×~230)。注意：**完整累积叙事并未每轮重发**（只发末 6 轮摘要），所以 token 随轮次是近似常数增长，不是 O(n²) 爆炸——这点架构上是对的。主要浪费在 existingContent 重复发送（[G10]）和角色/世界观全量注入（可改为按需/检索式）。单轮延迟主要由 LLM 决定，推理模型经 2500 预算保护后仍可能偏慢，但非代码瓶颈。
- **数据一致性**：游戏会话表与写作节点通过 nodeId 关联，导出写回节点——一致性在"单用户单会话"下成立；风险仅在"游戏导出覆盖原正文"（[G1]）与"无并发写锁"两处。

### 2.5 一句话总评

游戏模式是一个**架构扎实、闭环可信、细节（abort 对账/背包隔离/轻确认）做得到位**的正式功能；但它背着两个必须正视的问题：一是 [G1] 导出覆盖原正文的数据丢失（P0，且文案自相矛盾），二是若干体验一致性债（开局非流式且无停止、自动推进语义歧义、记忆衰减、类型安全弱）。修复 [G1] 与 [G2]/[G9] 后，游戏模式可从"能用"晋级为"敢放心用"。

## 发现清单（结构化，附证据）

### [G1] 严重度 P0 — 游戏导出覆盖/丢弃写作模式已有正文（数据丢失 + 与教程承诺矛盾）
- **文件:行号**：`src/core/game/game-engine.ts:546-553`（existingNarrative 仅取自 session.states）、`:611-612`（finalContent = 游戏轮次+结尾，未含 node.content）、`:631-639`（node.content 被 finalContent 整体覆盖）；教程承诺 `src/app/workspace/[projectId]/game/[nodeId]/page.tsx:547`（"不推翻已写情节"）。
- **现象描述**：在已有正文的章节开启游戏并"结束并导出"后，原写作正文从 `node.content` 消失。真机验证：原正文"林惊羽握紧断剑…"（41 字）导出后 `contains(PRE)=false`，导出以全新 AI 文本开头。
- **根因推测**：`endGameAndExport` 只拼接 `session.states`（游戏轮次叙事），而 AI 在开局时仅产出"续写片段"而非"原文+续写"，导出时未把 `node.content`（existingContent）纳入，导致原文被覆盖。
- **建议修法**：导出时将 `node.content` 作为第 0 段前置拼接，或在 `resetGameSession` 时把现有正文写入 round 0 的 gameState；并同步修正教程文案去掉"不推翻"的承诺或真正实现不推翻。

### [G2] 严重度 P1 — 游戏导出自动确认时静默回填世界书（超出用户预期的副作用）
- **文件:行号**：`src/core/game/game-engine.ts:642-654`（autoConfirm→applyConfirm）、`src/core/confirm-guard.ts:100-147`（applyConfirm→safeFillAfterWriting）。
- **现象描述**：主路径（智能审阅开且达标）游戏导出会触发 `safeFillAfterWriting` 自动回填世界书/角色卡，导出一章即改动项目设定库，界面无"已自动回填"提示。
- **根因推测**：为与写作模式确认流统一（Round1 #519）复用 `applyConfirm`，未对游戏场景做副作用提示。
- **建议修法**：在游戏导出确认态明确提示"已自动回填设定"，或提供项目级开关控制游戏导出是否触发自动填表。

### [G3] 严重度 P2 — 游戏结束后无法续玩/恢复（会话被重置）
- **文件:行号**：`src/core/game/game-engine.ts:677-686`（resetGameSession 删除旧会话）、`page.tsx` 重新进入逻辑。
- **现象描述**：结束导出后再进同一章节游戏，`resetGameSession` 删已完成会话，游戏从头开始，此前轮次不可恢复。
- **根因推测**：游戏会话设计为一次性；无 resume 入口。
- **建议修法**：提供"恢复上次游戏"入口，或对 completed 会话提供 resume 而非强制 reset。

### [G4] 严重度 P2 — maxWords=3000 硬编码，未按项目/章节配置
- **文件:行号**：`src/app/api/game/start/route.ts:54`、`src/core/game/game-engine.ts:163`。
- **现象描述**：进度条与字数上限恒为 3000，章节设定无法调整游戏篇幅。
- **根因推测**：两处写死常量，未从项目/章节配置读取。
- **建议修法**：从项目/章节配置读取上限，或至少抽到单一常量便于配置。

### [G5] 严重度 P2 — 开局（game/start）非流式，且开局期间无"停止"按钮
- **文件:行号**：`src/app/api/game/start/route.ts:88-94`（收集完整响应非 SSE）、`page.tsx:1217-1224`（停止按钮仅在 footer，footer 需 `status==="playing"`）。
- **现象描述**：点"开始游戏"后仅顶部不确定进度条，叙事整段出现；若开局 LLM 慢/卡，用户无取消入口（footer 在 generating 态不渲染）。
- **根因推测**：开局走非流式收集，且停止按钮绑定 playing 态。
- **建议修法**：开局也改为 SSE 流式；或在 generating 态也渲染停止按钮。

### [G6] 严重度 P2 — "结束并导出"按钮重复出现（顶栏 + 右栏底）
- **文件:行号**：`page.tsx:598-605`（顶栏）、`page.tsx:1138-1147`（右栏底）。
- **现象描述**：同一操作两处可见，用户可能困惑哪个生效。
- **根因推测**：两处独立实现同一动作。
- **建议修法**：保留一处（建议顶栏），右栏底改为"查看正文/返回工作区"。

### [G7] 严重度 P2 — 自动推进把字面"自动推进剧情"写入玩家行动记录
- **文件:行号**：`page.tsx:393-399`（autoAdvance 触发 `handleAction("custom","自动推进剧情")`）。
- **现象描述**：开启自动推进后，每轮左侧情节列表显示玩家行动="自动推进剧情"，像用户真实输入。
- **根因推测**：自动行动复用自由输入通道，未标记系统行为。
- **建议修法**：加"〔自动〕"前缀或在 UI 区分系统自动行动与用户行动。

### [G8] 严重度 P2 — 游戏引擎类型安全弱（大量 as any）
- **文件:行号**：`src/core/game/game-engine.ts:185、243、431-449` 等多处（`as unknown as any[]` / `as any`）。
- **现象描述**：JSON 列读写几乎全为 any，解析结构与持久化结构无编译期约束，易引入静默字段错位。
- **根因推测**：Prisma Json 字段无严格类型，直接 cast。
- **建议修法**：为 gameState 的 items/entities/options 定义严格 Json 类型或 zod 运行时校验。

### [G9] 严重度 P1 — 早期剧情记忆随轮次衰减
- **文件:行号**：`src/core/game/game-prompts.ts:265-274`（historySection 仅取最近 6 轮、每轮叙事截断 150 字）。
- **现象描述**：长游戏（>6 轮）早期事件/伏笔在 prompt 中丢失，AI 可能前后矛盾或遗忘伏笔。
- **根因推测**：为控 token 仅发末 6 轮摘要，未做关键实体/伏笔的持久化摘要注入。
- **建议修法**：增加"关键实体/伏笔摘要"持久化并注入 system prompt，而非仅截断叙事。

### [G10] 严重度 P2 — 每轮重复发送 existingContent（最多 3000 字）
- **文件:行号**：`src/core/game/game-prompts.ts:234-236、282-291`。
- **现象描述**：原章节正文每次行动都重新塞入 system prompt，恒定 token 浪费。
- **根因推测**：existingContent 每次全量注入，未做首轮/变更注入或检索式注入。
- **建议修法**：仅首轮或变化时注入，或改为检索式按需注入。

### [G11] 严重度 P2 — 结束且导出为空时的界面分支混乱
- **文件:行号**：`page.tsx:477-478`（showStartScreen = ended && !narrative）。
- **现象描述**：若导出 finalContent 为空（极端：轮次全被 abort/空流），ended 态回退到开始界面并显示"返回工作区"，语义混乱。
- **根因推测**：ended 与 ready 共用 showStartScreen 条件，未对空导出单独处理。
- **建议修法**：ended 态始终显示导出结果/错误，不回退到开始界面。

### [G12] 严重度 P2 — 本地推理(Ollama)需手动配置且非空响应无友好兜底
- **文件:行号**：`src/lib/llm.ts:77-86`（local 分支免 Key）、`src/core/llm/client.ts:83-91`（resolveMaxTokens 仅认推理模型正则）。
- **现象描述**：Ollama 可用但需手动切 local 并填 URL；本地模型若不命中 REASONING_MODEL_RE 则沿用小预算，可能产出短/空正文而无明确告警。
- **根因推测**：无零配置自动发现；预算保护依赖模型名正则，本地模型覆盖不到。
- **建议修法**：设置页提供"本地推理"一键预设；对本地模型空响应给出更友好提示。

### [G13] 严重度 P2 — 回退(rollback)依赖前端 turns 轮号
- **文件:行号**：`page.tsx:721-776`（用 `turns[last].round` 作删除起点）、`src/app/api/game/state/route.ts:8-62`（DELETE ?round=N 删 >=N）。
- **现象描述**：回退以绝对轮号 N 删除 >=N；若因 reconcile 导致轮号不连续，可能删错区间。
- **根因推测**：前端以"最后一轮轮号"作为删除起点，后端按 >= 删除，语义耦合轮号连续性。
- **建议修法**：回退以"删除最后一轮"语义实现，避免依赖绝对轮号连续性。
