## 第一部分：用户体验视角

### 一、作为中文用户阅读所有文案的真实感受

当我以一个中文写作者的身份打开故事线工作台时，第一眼看到的是标题栏「故事线工作台」——这个词组干净、专业，没有歧义。它清楚地告诉我这是一个「操作台」而非「查看器」，暗示我可以在这里做编辑、生成、管理等一系列动作。配合左侧的书签图标（bookmarked），整体传达出「这是一个可以深入工作的专业区域」的信号。

然而，随着视线向下移动，我开始遇到一些微妙的困惑。

#### 1.1 七要素区域的文案观感

七要素网格是整个工作台最核心的信息展示区。七个卡片标签——欲望、阻碍、行动、结果、意外、转折、结局（待收束）——每一个都是双字词，读起来节奏感很好，符合中文「短标签」的习惯。这七个词的选择也相当精准：「欲望」比「目标」更有文学张力，「阻碍」比「困难」更具体，「转折」比「变化」更有叙事感。

但问题出现在第七个要素上。「结局（待收束）」这个标签在 ELEMENT_META 数组中被硬编码为 `label: "结局（待收束）"`（第 40 行）。这里使用了全角括号 `（）`，而同一文件中其他位置的括号用法并不统一——比如第 431 行的 `额外要求（可选，仅作提示，不影响已生成内容）` 也用了全角括号，但第 711 行的 `七要素 · 总纲（结局不预填，仅标记收束）` 同样用了全角括号。看起来在故事线工作台内部，全角括号的使用是一致的，但跨组件对比时（比如 LeftPanel 中的 `角色 (15)`、`世界 (70)`、`故事线 (13)` 使用了半角括号），就出现了风格割裂。

更值得讨论的是「待收束」这三个字。作为一个中文用户，我第一遍读到时停顿了一下——「收束」不是日常用语，它更像是一个从日语或学术语境借来的词。在小说写作的场景下，「待完结」「待填写」「留白」可能更亲切。当然，「收束」有其精确性：它暗示结局不是被「写死」的，而是被「收拢」的，这与产品设计中「结局不预填」的理念一致。但这个词汇选择确实给非专业用户带来了一瞬间的认知摩擦。

当七要素卡片为空时，前六个显示的是 em-dash `—`，而结局卡片显示的是「待收束」。这种差异化处理是好的——它告诉用户「结局本来就应该为空」，避免了用户误以为这是数据缺失。但 em-dash 和「待收束」并存，视觉上不够统一。如果其他六个空卡片也能有类似的占位说明（如「未设定」），体验会更一致。

#### 1.2 线索集标题的困惑——「纸集」是什么？

这是我整个审查过程中遇到的最大的文案困惑点。

在第 773 行，线索集区域的折叠标题被写成：

```
线索集 / 纸集（融合龙王寨、菜市场注释、尸检报告等）
```

当我第一次在截图中看到这行字时，我的反应是：「纸集？这是什么？」我完全不理解「纸集」和「线索集」之间是什么关系。是同义词？是子类型？还是两个不同的概念用斜杠并列？

经过全项目 Grep 检索，「纸集」一词在整个 `src/` 目录中仅出现这一次（StorylineWorkbench.tsx:773）。没有任何其他文件、注释、文档或代码使用过「纸集」。这意味着：

1. 它是一个孤立术语，没有在任何地方被定义或解释；
2. 用户在其他界面（如备份对话框、导入向导）中看到的对应功能叫法不同；
3. AI 提示词和 API 文档中也从未提及「纸集」。

我推测「纸集」可能是开发过程中的内部代号或实验命名，在重构时没有被清理掉。斜杠 `/` 的使用暗示它可能是「线索集」的别名或另一种称呼，但这种并列方式在没有上下文的情况下只会让用户更加困惑。

更糟糕的是，括号中的示例文字「融合龙王寨、菜市场注释、尸检报告等」过于具体。这些明显是当前测试项目（龙陨之地）中的专有名词。当一个用户创建一个全新的项目（比如古言、科幻）时，看到「龙王寨」「尸检报告」这样的示例会感到莫名其妙——这些例子与他们的项目毫无关系。这说明该文案是从特定项目的上下文中直接复制过来的，没有做通用化处理。

#### 1.3 空状态文案的细致审视

故事线工作台中有多个空状态场景，让我逐一评价。

**场景 A：左导航无故事线**

```
标题：还没有故事线
按钮：AI 自动生成
```

这个空状态的优点是：
- 标题口语化自然，「还没有」比「暂无」更温和；
- 提供了明确的行动按钮，用户知道下一步该做什么；
- EmptyState 组件本身的设计（图标 + 标题 + 操作按钮）符合现代 UI 规范。

但缺点也很明显：
- 只提供了「AI 自动生成」一条路径。如果用户想手动创建故事线呢？当前界面上没有任何「新建故事线」的入口。这意味着空状态把用户锁定在了 AI 路径上。虽然这可能是有意的产品决策（AI-first），但从文案角度看，至少应该在描述中说明「目前仅支持 AI 生成」或者提供未来手动的预期。
- 没有描述性副文本。EmptyState 组件支持 `description` 属性，但这里没有使用。加上一句如「让 AI 基于你的大纲自动规划主线与支线」会显著降低用户的困惑感。

**场景 B：右详情面板未选中故事线**

```
文本：从左侧选择一条故事线查看详情
```

这是一条纯引导性文案，没有操作按钮。它的语气中性、清晰，没有问题。但它是一个「被动等待」的状态——用户必须自己去左列点击。如果能在旁边加一个小箭头图标指向左侧，或者让左列的第一项自动选中，就可以避免这个中间态的出现。

**场景 C：章节进展时间轴为空**

```
文本：暂无章节进展记录（写作时会自动回写大事件）
```

这条文案写得相当好：
- 「暂无」是标准的空状态前缀；
- 括号内的补充说明了「为什么空」以及「什么时候会有内容」，消除了用户的疑虑；
- 「自动回写大事件」虽然略带技术色彩（「回写」），但在上下文中可以理解。

唯一的小问题是「大事件」这个词比较模糊。什么叫「大事件」？系统判断的标准是什么？如果能加一句 tooltip 或更具体的说明（如「里程碑事件与关键情节节点」），会更好。

**场景 D：线索集为空**

```
文本：暂无线索，可在下方添加。
```

简洁有效。「可在下方添加」直接指引了操作位置。句末使用了句号，与其他空状态文案的风格一致。没有问题。

#### 1.4 加载与进度文案

加载状态的文案整体质量较高：

- `加载中…` —— 标准、简洁；
- `生成中…` / `生成中… XX%` —— 带百分比的进度反馈非常好，让用户知道系统在工作且有多少进展；
- `保存中…` / `落库中…` —— 这里有一个有趣的用词差异：「保存」用于普通编辑保存，「落库」用于 AI 生成结果的确认提交。「落库」是一个偏技术的词汇（来自数据库「写入」的俗称），对于普通写作者来说可能不太直观。建议考虑改为「确认入库」或「提交保存」。

错误提示文案方面，我注意到以下几类：

| 场景 | 文案 | 评价 |
|------|------|------|
| 加载失败 | `加载故事线失败：{具体错误}` | 清晰，有具体原因 |
| 网络错误 | `网络错误：{message}` | 清晰 |
| 生成失败 | `生成失败：{error ?? "未知错误"}` | 有兜底 |
| 保存失败 | `保存失败：{error \|\| HTTP {status}}` | 有 HTTP 状态码，对开发者友好但对普通用户可能太技术化 |
| 落库失败 | `落库失败：{error \|\| HTTP {status}}` | 同上，且「落库」一词需考虑 |
| 删除确认 | `确定删除这条故事线？此操作不可恢复。` | 标准、有警告力度 |
| 状态更新 | `「{title}」已完结 ✓` / `已重新开启` | 友好，有视觉符号 ✓ |

总体而言，错误提示遵循了「前缀 + 具体原因」的模式，一致性较好。但有两处可以改进：

1. `轮询失败`（第 95、97 行）——「轮询」是纯技术术语，普通用户不懂。建议改为「获取生成结果失败」；
2. `未知错误` 作为兜底出现了多次（至少 8 处）——虽然是合理的 fallback，但如果能根据 HTTP 状态码给出更友好的提示（如 403 →「权限不足」、500 →「服务器繁忙」），体验会更好。

#### 1.5 编辑态与查看态的文案切换

工作台的编辑态和查看态之间的文案切换是流畅的：

- 查看态的操作按钮：「标记完结」「编辑」（+ 删除图标）——动词简洁；
- 编辑态的表单字段：「标题」「简述」「类型（主线/支线可互换）」「状态」「所属主线」——标签清晰；
- 下拉选项：「活跃中」「已完结」「已废弃」——状态名称标准；
- 底部按钮：「取消」「保存」/「保存中…」——符合通用交互惯例。

特别值得一提的是「类型（主线/支线可互换）」这个标签——它在括号里补充了重要的交互说明，防止用户以为类型选定后不能改。这是一种很好的「预防性文案」设计。

「所属主线」下拉框中的默认选项 `（无归属）` 使用了全角括号，与前面提到的半角/全角不一致问题类似。这里用全角括号是为了视觉上的「选项感」（像是一个特殊的占位选项），所以可以接受，但最好在全项目中统一。

#### 1.6 AI 生成中间态的文案

AI 生成结果编辑器覆盖了正常主体，其文案包括：

- 标题区：`AI 生成结果 · 中间编辑态（可修改后再落库）`
- 额外要求字段：`额外要求（可选，仅作提示，不影响已生成内容）`
- 占位符：`例如：增加一条复仇支线`
- 操作按钮：`放弃` / `采用并落库` / `落库中…`

「中间编辑态」这个说法比较技术化。普通用户可能不理解什么是「中间态」。建议改为「预览编辑」或「生成草稿」。

「可修改后再落库」——「落库」再次出现。如果决定保留这个词，至少应该在整个产品中保持一致使用，并确保用户通过 tooltip 或首次使用引导理解其含义。

「放弃」按钮的文案是中性的，不会让用户担心丢失数据（因为后面还有确认步骤）。「采用并落库」则明确表达了动作的含义。这两个按钮的文案对比平衡得不错。

### 二、功能评价

从文案视角看故事线工作台的功能完成度：

**做得好的方面：**
1. 七要素体系完整呈现，每个要素都有清晰的中文标签；
2. 所有交互状态（加载中、生成中、保存中、错误、空态）都有对应的文案覆盖；
3. Toast 通知文案丰富，涵盖了成功、失败、进行中等多种状态；
4. 删除操作的二次确认文案有足够的警告力度；
5. 进度百分比实时展示（`生成中… XX%`）减少了用户的等待焦虑；

**存在缺口的方面：**
1. 缺少「手动新建故事线」入口——整个界面上只有 AI 生成一种创建路径；
2. 线索集的「纸集」术语令人困惑；
3. 部分技术术语（「落库」「轮询」「回写」）直接暴露给了终端用户；
4. 空状态缺少描述性副文本（EmptyState 的 description 属性未被充分利用）；
5. 示例文案（龙王寨、尸检报告等）与项目强耦合，不具备通用性。

### 三、UI 设计评价（聚焦文案相关的视觉表现）

#### 3.1 空状态视觉

EmptyState 组件采用了「虚空玻璃」设计语言：虚线边框 + 浅色背景 + 居中图标 + 标题 + 可选操作按钮。这种设计在视觉上是舒适的，不会让空状态显得「报错般刺眼」。图标使用了 creative 色调（蓝紫色系），传达出「创意/可能性」的正向情绪。

但正如前面所述，空状态缺少 description 文本，导致视觉上略显单薄——只有一行标题和一个按钮，中间有大片空白。

#### 3.2 占位符样式

输入框的 placeholder 文案使用了灰色 tertiary 文本色，在深色主题下对比度适中。placeholder 内容分为两类：
- **示例型**：`例如：增加一条复仇支线`、`标签（如：龙王寨 / 尸检报告）`——给出了具体格式参考；
- **说明型**：`线索内容（可无限延伸、每条可编辑）`——解释了能力边界。

这两类 placeholder 的设计思路都很好。但同样的问题：示例内容与特定项目耦合。

#### 3.3 标签与徽章

- 类型徽章：「主线」（accent 色）/「支线」（neutral 色）——视觉区分明确；
- 状态徽章：「完结」（success 绿色）——语义色使用正确；
- 数量徽章：线索集右侧的数字 badge 使用 9px 超小字号——信息密度合适但不抢眼；

#### 3.4 时间轴的文案层级

时间轴区域使用了三级文案层级：
1. 区域标题：`章节进展时间轴（写作自动记录大事件）`（xs font, tertiary color）
2. 节点标题：事件名称或「里程碑」（xs font, tertiary color）
3. 节点内容：事件详情（sm font, secondary color）

这个层级结构清晰。但区域标题过长（18 个字符），在小屏幕上可能折行。

## 第二部分：总体视角

### 一、项目整体文案风格一致性

#### 1.1 术语矩阵分析

我对故事线相关功能涉及的核心术语进行了全项目检索，整理出以下术语使用矩阵：

| 术语 | 含义 | 使用位置 | 使用频率 |
|------|------|----------|----------|
| **故事线** | Storyline 功能的主 UI 名称 | 左侧 Tab、工作台标题、列表计数、toast | 高（UI 层） |
| **剧情线** | Storyline 的同义词 | BackupDialog、ImportDialog、AI prompt、plan-chapter.ts 等 | 高（后台层） |
| **主线/支线** | Storyline 的 type 分类 | 工作台、列表、七要素 prompt | 高（全栈一致） |
| **七要素** | Seven Elements 框架 | 工作台 UI、generate.ts prompt、changelog | 中（一致） |
| **总纲** | 七要素区域的副标题 | 工作台第 711 行 | 低（仅此处） |
| **大纲** | Chapter Outline 树 | 左侧 Tab、CenterPanel、OutlineDialog | 高（独立功能） |
| **线索集** | CLUE 类型事件的集合 | 工作台 UI、API 注释 | 中 |
| **纸集** | ??? | 工作台第 773 行（唯一一处） | 极低（孤立） |
| **落库** | 写入数据库 | 工作台 toast/button | 低 |

从这个矩阵可以看出最严重的一致性问题：**「故事线」vs「剧情线」的分裂**。

在面向用户的 UI 层（LeftPanel tab、工作台标题、列表标题、toast 通知），统一使用「故事线」。但在备份导出对话框（BackupDialog.tsx:18）和导入向导（ImportDialog.tsx:17）中，同一个功能被称为「剧情线」。而在 AI 后台代码（plan-chapter.ts、outline-context.ts、generate.ts）中，更是大量使用「剧情线」或「活跃剧情线」。

这意味着：
- 用户在主界面学到的是「故事线」；
- 当他们去导出备份时，看到的是「剧情线 / 主线/支线及七要素」；
- 如果他们去读 AI 的生成日志（如果有），会看到「剧情线」。

这种不一致虽然不会导致功能故障，但会增加用户的认知负担——他们需要在不同上下文中映射同一个概念的两种名称。

**建议**：统一为「故事线」（因为它是面向用户的主 UI 名称），将所有「剧情线」替换为「故事线」。如果「剧情线」在某些上下文中有特殊含义（比如强调「情节推进」而非「结构框架」），则需要明确定义两者的区别并在 UI 中体现。

#### 1.2 省略号风格的全项目不一致

这是我在审查中发现的最广泛的一致性问题。省略号（ellipsis）在中文排版中应使用全角 `…`（U+2026），但我发现项目中同时存在两种风格：

**正确使用全角 `…` 的文件（故事线相关）：**
- StorylineWorkbench.tsx：全部使用 `…`
- StorylineList.tsx：全部使用 `…`
- BuildConfigDialog.tsx：`保存中…`
- ConsistencyPanel.tsx：`生成中…`
- ForeshadowingPanel.tsx：`生成中…`
- PreGenConfirm.tsx：`生成中…`
- PostGenPanelHeader.tsx：`保存中…`
- CenterPanel.tsx（部分）：`草稿保存中…`、`加载中…`

**错误使用半角 `...` 的文件：**
- CenterPanel.tsx:252：`章纲生成中...`
- CenterPanel.tsx:390：`生成中...`
- OutlineDialog.tsx:109：`生成中...`
- RulesPanel.tsx:189：`保存中...`

共 4 处使用了半角 ASCII 三点。这在视觉上的差异是明显的：半角 `...` 占三个字符宽度且间距较大，而全角 `…` 是单个字符宽度且间距紧凑。在中文 UI 中混用两者会显得不专业。

**建议**：全局替换所有 `...` 为 `…`，并在团队编码规范中加入此规则。

#### 1.3 括号风格的不一致

全角括号 `（）` 与半角括号 `()` 的使用在项目中没有统一规则：

- **全角括号使用者**：故事线工作台内部（结局（待收束）、总纲（结局不预填...）、额外要求（可选...）、所属主线的（无归属））
- **半角括号使用者**：LeftPanel 的 tab 计数（角色 (15)、世界 (70)、故事线 (13)）、BuildConfigDialog 等多处

严格来说，中文排版规范推荐在中文文本中使用全角括号。但这取决于团队的风格指南。关键是**在同一类 UI 元素中保持一致**。当前的问题是：同类元素（如带括号的标签/说明）在不同组件中使用了不同的括号风格。

### 二、架构与代码质量（文案硬编码 / 可维护性）

#### 2.1 文案的硬编码程度分析

故事线工作台的文案几乎 100% 硬编码在 JSX 中。具体分布：

| 文案类别 | 数量 | 是否集中管理 | 可维护性评估 |
|----------|------|-------------|-------------|
| 七要素标签 | 7 个 | ELEMENT_META 常量数组 | 好——集中定义，易修改 |
| UI 标题/按钮 | ~30 个 | 散落在各 JSX 分支 | 一般——每次改文案需定位到具体行 |
| 错误提示 | ~15 个 | 内联在 catch/toast 调用中 | 较差——相同模式重复多遍 |
| 空状态文案 | ~5 个 | 直接写在条件渲染中 | 一般 |
| Placeholder | ~5 个 | 在 DialogInput 的 prop 中 | 一般 |

**亮点**：ELEMENT_META 数组（第 29-41 行）是一个很好的实践——七个要素的 key/icon/label 集中定义，label 的修改只需改一处。这种模式应该在更多地方推广。

**问题**：错误提示文案存在大量重复模式。例如 `未知错误` 至少出现了 8 次（每次都是 `.catch(() => ({ error: "未知错误" }))`），`请重试` 出现了 6 次。这些应该抽取为常量。

更理想的做法是引入一个轻量的 i18n 或文案常量文件，至少将用户可见的字符串集中管理。考虑到 novel-forge 目前主要面向中文用户，不需要完整的国际化方案，但一个 `src/lib/copy.ts` 或 `src/lib/messages.ts` 常量文件就能大幅提升可维护性。

#### 2.2 文案与逻辑耦合

部分文案与业务逻辑紧密耦合，导致修改文案可能影响功能：

```tsx
// 第 182 行：toastSuccess 的文案中嵌入了数据
toastSuccess(next === "completed" ? `「${s.title}」已完结 ✓` : `「${s.title}」已重新开启`);
```

这里的模板字符串混合了动态数据和静态文案。如果将来要调整格式（比如去掉书名号、改变 ✓ 符号的位置），需要改动代码逻辑。建议将格式字符串抽为常量：

```typescript
const COPY = {
  storylineCompleted: (title: string) => `「${title}」已完结 ✓`,
  storylineReopened: (title: string) => `「${title}」已重新开启`,
};
```

#### 2.3 Toast 消息的系统性与完整性

Toast 通知使用了三个不同的函数：
- `toastError()` — 错误通知（红色）
- `toastSuccess()` — 成功通知（绿色）
- `toastCreated()` — 创建成功通知（蓝色/特殊）

在故事线工作台中，toast 的使用覆盖了以下场景：

| 触发场景 | 函数 | 文案 |
|----------|------|------|
| 轮询失败 | toastError | `生成任务失败：{msg}` |
| 生成结果为空 | toastError | `生成结果为空，请重试` |
| 生成失败 | toastError | `生成失败：{msg}` |
| 创建任务失败 | toastError | `创建生成任务失败：{msg}` |
| 网络错误 | toastError | `网络错误：{msg}` |
| 落库失败 | toastError | `落库失败：{msg}` |
| 保存失败 | toastError | `保存失败：{msg}` |
| 状态更新失败 | toastError | `状态更新失败：{msg}` |
| 线索增删改失败 | toastError | `新增/更新/删除线索失败：{msg}` |
| 线索内容为空 | toastError | `线索内容不能为空` |
| 状态变更成功 | toastSuccess | `「{title}」已完结 ✓` / `已重新开启` |
| 创建成功 | toastCreated | `故事线` |

覆盖面是完整的——每个可能出错的操作都有对应的错误提示，每个成功的状态变更也有反馈。但 `toastCreated("故事线", "故事线")` 这个调用（第 229 行）看起来有些奇怪——两个参数都是 `"故事线"`，可能是 API 设计遗留。需要确认 `toastCreated` 的签名意图。

### 三、质量与风险（文案错误导致用户误解的可能性评估）

#### 3.1 高风险项

**P0-01：「纸集」术语导致用户无法理解功能**

风险等级：高
影响范围：所有使用故事线工作台的用户
误解概率：>70%（基于「纸集」无任何上下文解释的事实）

用户看到「线索集 / 纸集」后，可能的反应包括：
- 认为「纸集」是一个独立的功能模块，试图寻找它在哪里；
- 认为自己需要准备某种「纸质材料」来使用此功能；
- 直接忽略此区域，因为名称令人困惑。

**P0-02：「剧情线」与「故事线」混用导致认知分裂**

风险等级：中高
影响范围：使用备份/导入功能的用户
误解概率：~40%

当用户在导出备份时看到「剧情线」而不是熟悉的「故事线」，可能会：
- 不确定是否导出了正确的数据；
- 向客服反馈「找不到故事线选项」。

#### 3.2 中风险项

**P1-01：技术术语暴露（「落库」「轮询」「回写」）**

风险等级：中
影响范围：遇到错误提示或高级功能的用户
误解概率：~30%

「落库」一词对非技术用户来说完全不透明。用户可能理解为：
- 「落到数据库里」——如果用户恰好有技术背景；
- 「落下/掉落」——完全错误的解读；
- 一个陌生的品牌名或功能名。

**P1-02：项目耦合的示例文案**

风险等级：中
影响范围：非「龙陨之地」项目的用户
误解概率：~25%

「龙王寨」「尸检报告」「菜市场注释」这些示例在新项目中会让用户困惑。

#### 3.3 低风险项

**P2-01：省略号风格不一致**
**P2-02：括号风格不一致**
**P2-03：空状态缺少 description**

这些不影响功能理解，但影响产品的专业感和精致度。

#### [P0-01] 孤立术语「纸集」无定义、无上下文

- **严重度**：P0
- **文件**: `StorylineWorkbench.tsx:773`
- **现象**: 线索集区域标题写为 `线索集 / 纸集（融合龙王寨、菜市场注释、尸检报告等）`，其中「纸集」在整个项目中仅此一处出现，无任何定义或解释

  - 同时必须将括号内示例通用化，去除「龙王寨」「尸检报告」等项目专有名词

#### [P0-02] 「故事线」与「剧情线」术语分裂

- **严重度**：P0
- **文件**: `BackupDialog.tsx:18`、`ImportDialog.tsx:17`，以及 `plan-chapter.ts`、`outline-context.ts`、`generate.ts` 等后台代码约 20+ 处
- **现象**: UI 层统一称「故事线」（Tab 名、工作台标题、toast），但备份/导入对话框称「剧情线」，AI prompt 和管线代码也称「剧情线」或「活跃剧情线」
- **根因推测**: 功能早期命名「剧情线」，后来 UI 层更名为「故事线」但后台代码和次要界面未同步更新
- **证据**: 
  - LeftPanel.tsx:47 → `故事线 (${count})`
  - BackupDialog.tsx:18 → `{ key: "storylines", label: "剧情线", desc: "主线/支线及七要素" }`
  - ImportDialog.tsx:17 → 同上
  - plan-chapter.ts 全文使用「剧情线」
- **建议修法**:
  - 将所有面向用户的「剧情线」统一替换为「故事线」（BackupDialog、ImportDialog、ForeshadowingPanel 等 UI 组件）
  - 后台代码（prompt、注释、变量名）中的「剧情线」可以在下一轮重构中逐步统一，优先级低于 UI 层
  - 建议在 `src/lib/copy.ts`（新建）中定义术语常量 `TERM_STORYLINE = "故事线"` 供全项目引用

### P1 级别（应当修复——影响专业性或部分用户理解）

#### [P1-01] 技术术语「落库」暴露给终端用户

- **严重度**：P1
- **文件**: `StorylineWorkbench.tsx:226,235,489,492`

- **建议修法**:

  - 错误提示改为「保存失败：…」（复用已有的「保存失败」模式）

- **文件**: `StorylineWorkbench.tsx:95,97`
- **现象**: 轮询失败时的错误提示为 `生成任务失败：轮询失败` 和 toast `生成任务失败：轮询失败`

- **建议修法**: 改为 `生成任务失败：获取结果失败` 或 `生成任务失败：网络中断，请检查连接后重试`

#### [P1-03] 项目耦合的示例文案缺乏通用性

- **严重度**：P1

#### [P1-06] 无「手动新建故事线」入口

- **严重度**：P1（偏功能性，但文案层面体现在空状态只有单一行动路径）
