# 偏差观测报告 · Agent 确认流程 Round 1

> 观测智能体：偏差观测（CodeBuddy）
> 监测锚点：用户原始需求「设计一个多智能体协作系统……由开会决定智能体团队的大致确认流程，所有的按钮 UI」
> 核心交付物定义：本轮会议必须产出「确认流程」的**完整按钮 UI 规格**，必须含四项——①按钮清单 ②界面布局 ③状态机 ④计划流程。后续由工程实现、由**AI 智能体真实走通验证**。

## ① 逐份偏差判定

| 文件名 | 是否偏离 | 偏离点 / 风险 |
|--------|----------|--------------|
| **jobs.md**（乔布斯） | 基本未偏离 | 含按钮清单/布局/状态机，最"像产品"。但①主语泛化为"作者"，未提"智能体团队要走通"；②提"批量确认"却未给项目级/卷级层级，计划流程缺一环。 |

| **pg.md**（PG） | **部分偏离** | ①把"确认"重构为"锁定/解除锁定"，删去"打回/诊断"独立按钮，偏离"确认流程"的常规语义与用户预期；②状态机仅 `draft ⇄ locked`，无"待确认"中间态，弱化了"闸门"概念；③主语是"作者/maker"，几乎未碰"智能体团队"。 |

| **munger.md**（芒格） | 基本未偏离 | 逆向风险视角，含清单/布局/状态机（4 态）。但主语是"用户/作者"；状态机引入 `completed(已生成)` 与 `pending_review` 并存，与多数报告"草稿即待确认"的设定冲突。 |

| **gongfang.md**（工坊） | 基本未偏离 | 工程落地最具体，含清单/布局/状态机/改动步骤。但主语是"作者"；状态机用 `rejected` 终态，与"已确认→重开/打回"可逆设计冲突。 |

**判定小结**
- 跑题（无关话题）：**0 份**。无报告泛谈 AI 写作哲学或扯与确认无关的功能。
- 真正偏差：**主语漂移（7 份中 6 份）** + **规格碎片化（7 份各一套）**。

## ② 系统性偏差模式

**模式 A — 主语漂移（最关键、最隐蔽）**
用户需求的主语是「**智能体团队**确认流程」，且明确"由**AI 智能体真实走通验证**"。但 7 份报告里有 6 份把主语替换成"作者 / 写手 / 用户 / 零基础用户"。结果是：设计的按钮、措辞、状态都是从"人类写手"视角出发，而非从"AI 智能体如何操作并验证"出发。这直接威胁下游——工程实现后，AI 智能体走通时可能发现按钮语义对自己不成立（例如"锁定本章/解除锁定"对智能体意味着什么？"整本项目交付"由谁点？）。

**模式 B — 状态机七套互不一致（碎片化）**
七份给出七套状态机，核心分歧：
- 有无独立"待确认"中间态：PG 无（draft⇄locked）；其余都有。
- 终态是 `confirmed` 还是 `rejected`/`locked`：命名与语义混乱。
- 是否含项目级确认：仅 agent 显式给出 `project_confirmed`。
- 状态数从 2（PG）到 5（feynman/agent）不等。
未收敛则工程无从落地。

**模式 C — 按钮清单与命名不统一**
- 按钮数：jobs 5、agent 3+1、pg 2、zhangxuefeng 4+2、munger 4、feynman 4~5、gongfang 3+1。
- 命名：确认/锁定/确认定稿/确认通过/提交确认……同一动作 5 种叫法。
- "诊断"是否独立成按钮：jobs/zhang/munger/feynman/gongfang 要，PG 反对（认为诊断是环境不是仪式）。
Chair 若不强制归一，前端会出现"同一功能多套文案"。

**模式 D — 布局位置打架**
- 底部常驻栏：jobs、agent、zhang、munger、feynman
- 顶部：pg、gongfang
同一确认条被建议放在"顶部""底部""PostGenPanel 之上/之下/末尾"，互相矛盾。

**模式 E — "简易初衷"被双向拉扯**
用户要的是"大致确认流程"（大致=粗粒度、不要过度设计）。PG 极致做减法（2 键），feynman/jobs 反而加键（4~5）。两端都偏离"大致"的中道：一端可能弱化成无闸门，一端可能复杂化成审批流。

## ③ 对 Chair 的纠偏指令（整合必须包含的最低 UI 规格项）

Chair 在整合 Round 1 结论、产出最终规格时，**必须强制收敛并显式包含以下四项**，缺一不可：

**M1 · 锚定主语（纠偏模式 A）**
开篇一句话锁定："本规格的确认流程主语 = **AI 智能体**（及 equivalents 的作者），由AI 智能体真实走通验证。" 所有按钮文案、状态名、计划流程的"操作者"字段一律写"智能体团队/智能体"，禁止默认写成"作者"。

**M2 · 唯一按钮清单（纠偏模式 C）**
从 7 份中取交集，收敛为**一套**带固定中文文案的按钮（建议基线）：
1. `确认通过`（主按钮，唯一主色，常驻）
2. `打回重写`（次级，保留上一版快照）
3. `诊断`（复用 PostGenPanel/analyze-chapter，可选但保留——采纳 majority）
4. `批量确认`（卷级/项目级入口，二次确认防误触）
- 禁止再出现"锁定/解除锁定""提交确认""确认定稿"等并行业务命名；PG 的"锁定"若保留，必须映射为上述 `确认通过` 的同义词并注明。
- 按钮数控制在 3~4 个（含批量），守住"大致/简易"。

**M3 · 唯一状态机（纠偏模式 B）**
强制归一为一棵状态树（采纳 agent 的四层骨架 + 多数人"待确认"中间态）：
```
outline_only → drafting → pending_confirm(待确认)
pending_confirm ──确认通过──▶ confirmed(已确认)
pending_confirm ──打回重写──▶ drafting(保留 revision 快照)
pending_confirm ──诊断迭代──▶ drafting(写入新 revision)
confirmed ──可重开──▶ drafting
confirmed ×N ──批量确认──▶ project_confirmed(项目级确认)
```
- 否决 PG 的无中间态方案、munger 的 `completed` 并存方案、gongfang 的 `rejected` 终态方案。
- 状态名对终端用户一律显示中文（待确认/已确认），`pending_confirm` 等仅作内部枚举。

**M4 · 唯一布局（纠偏模式 D）**
确认条**固定在 PostGenPanel 底部常驻栏**（jobs/agent/zhang/munger/feynman 多数共识），不在顶部、不新开弹窗、不新开页面；左栏章节树挂状态徽标（灰=草稿/橙=待确认/绿=已确认）；右栏监测 tab 加"确认看板"（待确认数/已确认率/低分拦截数）。批量确认入口置于项目级工具栏。

**M5 · 显式计划流程（补齐"计划流程"交付项）**
规格必须单列一段端到端"计划流程"，描述AI 智能体走通顺序：
生成 → 落库为 `pending_confirm` →（可选）诊断 → 逐章 `确认通过` / `打回重写` → 全程保留 `StoryNodeRevision` 快照 → 卷级 `批量确认` → 项目级 `project_confirmed`。并标注关键时序约束：**自动填表（safeFillAfterWriting）必须推迟到 `confirmed` 之后**，否则未审章污染设定库（agent/munger 共识）。

**M6 · 收敛纪律**
Chair 输出物命名为 `agent-confirm-spec.md`，结构严格按 M2~M5 四节 + 主语声明。任何报告里"仅自己持有、未被多数支持"的异见（如 PG 的极简 2 键、feynman 的 5 键拆分）只允许作为"备选/驳回说明"附录，不得混入主规格。

---

### 一句话总评
7 份报告**都守住了"谈确认流程的按钮 UI"这一底线，无一跑题**；但共同犯了一个会致命的错——**把"智能体团队确认"写成了"作者确认"，并各自给了一套互不兼容的规格**。Chair 当前最该做的不是"再讨论"，而是**强制归一主语 + 归一状态机 + 归一按钮 + 归一布局**，产出一份AI 智能体真能照着点下去的单一规格。
