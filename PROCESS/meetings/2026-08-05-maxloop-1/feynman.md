# 真实性校验纪要：哪些「已验证」我不能信

> 口头禅：「你确定这是真的吗？」本纪要所有断言皆附可复现的证据点，凡无证据的宣称一律不采信。

## 一、核心诊断

**宣称一：「单一质量阈值真相，批量确认 / 自动确认 / 流水线三处复用，消除阈值分裂」（changelog-data.ts:99）——经核查为假。** 全仓库只有三处 import confirm-guard（auto-confirm、game-engine、post-processor），但 batch-confirm/route.ts 是第四份**内联复制**：自带 `QUALITY_PASS_THRESHOLD=60`、`gradeOf`、完整 applyConfirm 逻辑，且**丢失了 confirm-guard 的空正文/过短（<50 字）拦截**。这不是「阈值分裂风险」，而是已经分裂：同一章空正文 + qualityScore≥60，走 auto-confirm 被拦，走 batch-confirm 会被放行。阈值现在碰巧都是 60，改一处即分叉，宣称与代码不符。

**宣称二：「自动填表已执行」。** `applyConfirm` 中 `safeFillAfterWriting` 失败仅记入 fillMsg，「不影响确认」。全部验证脚本只断言 status 与 reviewLogs 含 auto-confirm 标记，**没有任何脚本断言填表产出的表单记录真的落库**。副作用没被验证，不能叫「已验证」。

**宣称三：「自动放行率 100%」（agent-smart-deliver-verify.cjs:48）。** 该脚本用 auto-confirm 确认了全部章节后，再断言 autoRate===100%。分子分母都是脚本自己制造的——**同义反复，不是验证**，也从未测混合场景（部分手动确认）下 autoRate 是否准确。

**宣称四：「均真机验证通过」。** agent-gen-autoconfirm-verify 与 agent-game-light-confirm-verify 依赖真实 LLM 输出质量≥60，LLM 一波动即随机失败；一次通过≠稳定通过，无重复运行记录，**不可复现**。另 [id]/route.ts:89 直接透传 `qualityScore`，auto-confirm 与 batch-confirm 均无条件采信 DB 分数——护栏可被任意伪造分绕过，「不被蒙混过关」只对诚实客户端成立。

## 二、提升框架

1. **诚实边界**：每条宣称标注证据等级——「脚本跑过且断言了副作用」才算验证过；「代码看起来对」只是推测，必须降级表述。
2. **反自欺闸门**：验证脚本必须断言副作用落库，而非只断言主返回；必须包含一个预期失败的反例（低质文本被拦截），没有反例的验证是合影。
3. **可复现优先**：真实 LLM 验证只作冒烟；正式回归用固定样本 / 可注入 mock，保证任何人在任何环境复跑同果。

## 三、必须验证才信的点

1. **batch-confirm 空正文放行漏洞（最优先）**：建空正文章 qualityScore=90，分别走 batch-confirm 与 auto-confirm，断言二者行为不一致——我读代码判定不一致。若确认，「单一护栏」宣称即破产，必须收编 batch-confirm 到 confirm-guard。
2. **analyzer 空文本评分**：对空字符串跑 `analyzeQuality`，我推断得满分 100（六维对空集合均给 100，加权=100）。这正是空正文拦截必须存在的原因，而 batch-confirm 恰好丢了它。
3. **填表副作用对账**：auto-confirm 后查世界卡/角色等表单表的新增记录，而非只看 reviewLogs.fillMsg。
4. **伪造分绕过验证**：低质正文 PUT qualityScore=90 后 auto-confirm，观察是否放行。需明确这是产品接受的信任模型，还是必须改为流水线独占写分。
5. **并发幂等**：对同一节点并发/重复调 auto-confirm，断言 revisionCount 只 +1、reviewLogs 不重复追加——当前无 CAS 守卫。

## 四、风险提示

- **mock 当真机**：脚本用 PUT 塞分代替 analyzer 真判，注释声称的路径可能与实际路径脱节。
- **只测成功路径**：固定 GOOD 文本反复用，从未测 59/60/61 边界分。
- **环境差异**：验证脚本 BASE 一处 hardcode `localhost:3001`、一处默认 `127.0.0.1`；`prisma.cmd` 依赖 Windows 路径，换环境即碎。
- **自证陷阱**：autoRate=100% 这类自我实现的断言，通过不等于验证。

## 五、与其他职能的张力

- **与方向职能**：我坚持先验真再定方向；若已规划下一圈功能冲刺，会认为我拖延。但方向建立在假宣称上就是沙上筑塔。
- **与产品职能**：自动确认漏洞在演示中不暴露，产品可能判定「不影响上线」；但「已验证」必须降价为「已冒烟」，否则是对用户的欺骗。
- **与工程职能**：复制粘贴与丢失守卫是重构债，工程可能「先交付后收编」；我要求在收编前不得宣称复用。填表失败「不影响确认」的语义也须由工程明确是设计还是兜底。
- **与用户职能**：真机验证随 LLM 波动随机失败，给用户的是不确定承诺；若用户职能用「均真机验证通过」安抚用户，我会当场拆台。

结论：本轮唯一能信任的，是「代码路径可读」这一事实本身；所有功能宣称，先复跑，再谈方向。
