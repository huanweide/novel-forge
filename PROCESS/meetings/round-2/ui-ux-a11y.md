## 一、三块布局（总纲·七要素 / 章节时间轴 / 线索集）IA 评审

当前右列（查看态）是一个 `space-y-4` 的**单滚动纵向列**，自上而下堆三块（`StorylineWorkbench.tsx:621-872`）：

1. **七要素·总纲**（:765-795）：7 张要素卡（欲望/阻碍/行动/结果/意外/转折/结局）两列网格；
2. **章节进展时间轴**（:797-823）：自动记录的大事件时间线（ol + 左侧竖线）；
3. **线索集**（:825-868）：可折叠的 CLUE 卡片 + 新增表单。

### 问题诊断

**(1) 三块「等权纵向堆叠」掩盖了真实的信息层级与交互频率差异。**
- 七要素是**核心编辑面**（作者最常改），却被埋在顶部、下方还压着两块长内容；要看/改线索集得滚很远。
- 时间轴是**系统自动回写、作者极少手动编辑**的只读型区块，却和七要素、线索集占了同等篇幅。
- 线索集是**高频追加型**（写作中随时记一条伏笔），当前默认折叠（:836 `cluesExpanded` 初始 true 其实默认展开，但结构仍是「埋在底部」）。
- 三块用同一种卡片描边同权呈现，读者第一眼无法区分「哪个是我现在要用的」。

**(2) 右列顶部没有常驻「概要区」。**
标题、类型徽章、完结/编辑/删除按钮在 `:708-763`，滚动时一滑就丢；改七要素要回顶部找「编辑」。核心元数据（进度、状态）没有 sticky 锚点。

**(3) 时间轴当前为空**，因为该项目尚无章节事件回写（实测 `timelineEvents.length === 0`，走 :816 的 `EmptyState`）。这意味着「章节进展时间轴」的真实密度与可读性**尚未被真实写作验证**——用户在原话里说「用当前章节继续续写几章试探」，正是为这一块补真实数据。本轮 UI 评审只能确认其空态/结构，非空态的卡片密度、长内容截断需待续写后二次走查。

### 1.0 直接回答 lead 的三栏重构提问（线导航 + 七要素因果链 + 推进/试探墙）

lead 在本轮 nudge 中把 IA 问题明确重述为：「三块是否该重排为『线导航 + 七要素因果链 + 推进/试探墙』三栏」。我的结论：**应该，且这是比子标签（原方案 A）更优的*目标态* IA**——但它对当前代码是「重组」而非「重排」，需在组件层补一个「因果链」可视化基元。

**为什么三栏优于子标签：**
- 子标签（原方案 A）只是把右列三块变可切换视图，七要素**仍只在切到它时才满高可见**；三栏让七要素（最核心编辑面）**永久常驻成列**，作者边看因果边在「推进/试探墙」记伏笔，无需任何切换。
- 「推进/试探墙」把『章节时间轴（推进）』与『线索集（试探/伏笔）』合到同一语义柱下，概念比现在「时间轴 + 线索集」两张等权卡更紧——伏笔本就是为推进服务的，二者不该被分割。
- 它保留了产品既有的「左列导航」心智（线导航仍是第一栏），只是把右列从「单滚动三块」拆成「两并列常驻列」，改动沿原双栏骨架延展，不算另起炉灶。

**映射当前代码锚点（Before → After）：**
- 线导航栏：现 `StorylineWorkbench.tsx:552-554`（w-72 左列容器）+ `LineNav:878-948`。三栏下保持为第一栏，仅去嵌套（模块 1）。
- 七要素·因果链栏：现为右列第一块 `:765-795`（2 列网格）。三栏下升为**独立第二栏**，且从「7 张等权卡」升级为「带连接器的纵向因果链」（欲望→阻碍→行动→结果→意外→转折→结局）。
- 推进/试探墙栏：现为右列第二、三块 `:797-823`（时间轴）+ `:825-868`（线索集）。三栏下合并为**独立第三栏**，上半「章节进展（推进）」、下半「伏笔/试探墙」。

**Before（现状：双栏 + 右列纵向堆叠）：**
```
┌──────────────────────────────────────────────┐
│ Header: 标题/类型/状态 · 编辑 · AI生成         │
├──────────┬───────────────────────────────────┤
│ 线导航   │ 右列(单滚动)                       │
│ LineNav  │  ① 七要素 grid(2col)              │
│ ×13      │  ② 章节时间轴                     │
│          │  ③ 线索集                         │
└──────────┴───────────────────────────────────┘
```
左列 w-72(288)，右列单滚动，七要素被埋在第①块、要滚才能改。

**After（目标：三栏常驻）：**
```
┌────────────────────────────────────────────────────────┐
│ TopBar(常驻): 标题/类型/状态 ● 编辑 ● AI生成 ● 删除      │
├────────┬────────────────────┬──────────────────────────┤
│ 线导航 │ 七要素·因果链       │ 推进 / 试探墙             │
│ LineNav│ 欲望→阻碍→行动      │ ▸ 章节进展(推进) 时间轴   │
│ ×13    │  →结果→意外         │ ▸ 伏笔/试探墙 线索集      │
│        │  →转折→结局         │   + 新增伏笔入口          │
│        │ (纵向链+inline编辑) │                          │
└────────┴────────────────────┴──────────────────────────┘
```
每栏独立滚动；七要素永久可见；推进与试探同柱；TopBar 承载元数据与 CTA，不再随右列滚动丢失（解决原 :708-763 滚动丢标题）。

**必须正面处理的三个风险：**
1. **横向预算**：1024 弹窗里三栏 + TopBar，建议最小列宽 线导航 200 / 七要素因果链 320 / 推进墙 360，合计 ~880 + 间距，1024 可容纳但偏紧；`<lg` 必须降级（见下）。
2. **因果链是新产品组件**：现有七要素是纯 grid（:765-795），「链」需要连接器（箭头/竖线 + 因果文案槽）表达欲望→…→结局的因果流——这是交互流程 + 前端工程透镜要拍板的可视化基元，本透镜只定布局容器与可达性（链节点仍是可聚焦/可编辑的语义块）。
3. **TopBar 与编辑态关系**：现「编辑」整页替换为 11 字段表单（:627-704）。三栏下应改为「仅元数据在 TopBar 内联，七要素走 inline PATCH（模块 3）」，否则点编辑又要把三栏全盖掉，违背常驻初衷。

**响应式降级（关键）：** `<lg` 三栏过窄 → 折叠为「线导航 + (七要素 | 推进) 子标签」——即把第二、三栏收成子标签切换（原方案 A 成为**响应式形态**而非独立方案）；`<md` 进一步上下堆叠或全屏。这把原方案 A 从「竞争方案」重新定位为「三栏在窄屏的必然退化」，二者不再冲突。

> 落地定位：三栏是 v1.9+ 的目标 IA；若 v1.8.11 想先收口且不想立刻做因果链组件，可用原方案 A（子标签）作为**过渡**，待因果链基元就绪再升三栏。无论哪条路径，P0 去嵌套（模块 1）与 AI 按钮对比度（模块 6）都不依赖 IA 决策，应独立 hotfix 先合。

### IA 重排提案（粒度对照，原方案保留为过渡/响应式）

- **原方案 A（过渡/响应式形态）：右列子标签（Sub-tab）导航。** 右列顶部 sticky 子标签 `[总纲·七要素 | 章节时间轴 | 线索集 (n)]`，下方单面板占满剩余高度。现定位为「三栏在 `<lg` 的退化形态」与 v1.8.11 过渡方案。
- **原方案 B（最小改动）：保留纵向，但「时间轴+线索集」合并为手风琴**，默认仅七要素展开；右列顶部加 sticky「概要卡」。仅作最低成本兜底。

> 我的建议：以**三栏（线导航 + 七要素因果链 + 推进/试探墙）为目标态**，原方案 A 作为过渡/窄屏退化。三栏同时解决了「核心被埋」「滚动距离长」「等权误导」三个问题，且把「推进/试探」合柱，比单纯子标签更贴近作者「边写边留伏笔、看因果推情节」的真实工作流。

## 二、写入 / 编辑态表单 UX 评审

### 2.1 七要素卡片编辑

当前写入路径：**查看态（七要素只读卡片）→ 点「编辑」→ 整视图替换为 11 字段大表单（标题/简述/类型/状态/7 要素）→ 保存**（:627-704）。

**问题：**
- **「编辑」是大颗粒全量表单**，改「一句阻碍」也要进入含类型/状态选择器的完整表单，退出后再回查看态。对「总纲」这种高频微调场景，步骤过重。
- 七要素卡片在查看态**完全只读**，没有 inline 编辑入口。
- 「结局」要素在编辑态仍是可填 textarea（:682），但与产品「结局不预填、仅标记收束」的设定冲突——查看态显示「待收束」（:786），编辑态却可填，语义割裂。Round-1 在 *AI 中间态* 把结局改成了只读（:507-513），但*手动编辑态*漏了这层约束。

**提案：七要素 inline 编辑 + 元数据独立。**
- 查看态七要素卡片**可点即编辑**：点卡片 → 变 textarea → 失焦或 ⌘/Ctrl+Enter 触发**单字段 PATCH**（新增 `handleElementPatch(id, key, val)`，复用 `handleCluePatch` 的写法 :379）。常见微调零跳转。
- 「编辑」按钮收窄为**仅元数据**（标题/简述/类型/状态/归属）；七要素改为 always-editable inline。
- 「结局」在手动编辑态也改为**「标记收束」开关**（与 AI 中间态一致），不再可填文本。

### 2.2 线索集增删改

当前线索：每条 `ClueRow`（:951-1027）有 编辑/删除 图标按钮（已带 `aria-label`，Round-1 修好），编辑时整行切为输入框。新增线索是底部一个虚线框表单（标签+内容+「添加线索」）。

**评价：** 这部分 UX 基本合理，是本轮最稳的区块。两点可优化：
- 新增线索的「标签」输入框 `w-40`（:851）在窄屏会挤压内容框；建议标签/内容改为纵向堆叠或标签可省略。
- 删除线索**无确认**（:1006 直接 `onDelete`），而删除故事线有 `useConfirmDelete` 二次确认（:335）。同样是危险操作，线索删除应至少加轻量确认或撤销，避免误删伏笔。

### 2.3 commit / AI 生成落库流程

当前流程：头部「AI 生成」→ 建后台任务 → 轮询 → 完成后整页被「AI 生成结果·中间编辑态」覆盖（:471-549），每条建议可改七要素 → 「保存到故事线」（:545，原「采用并落库」）。

**问题：**
- **触发前没有 prompt 入口**：`genExtra`（补充要求）输入框出现在*生成完成后的中间态*（:476），且文案是「对下一次生成的补充要求（可选，本次不发送）」——在「已经生成完了」的界面里说「下一次」「本次不发送」，逻辑矛盾、用户困惑（F-07 同源问题）。
- **生成中无区域级反馈**：轮询期间（实测「生成中… 10%」）右列仍显示普通列表视图（:550 之后），只有头部按钮一行小字在变。长任务下用户不知进度归属（F-07 仍存，Round-1 未动）。
- 中间态里「结局」被强制只读（:507），但落库时 `handleCommitGen` 仍把 `ending` 当作字段传（suggestions 里 ending 是 null），静默丢弃——逻辑自洽但界面没说清。

**提案：**
- 把「生成要求」prompt 移到**生成前**（头部「AI 生成」点击展开轻量输入行，或弹一个小 prompt），文案改「生成要求（可选）」，确认后才建任务。
- 生成中：右列（或整主体）替换为**「生成中」区域态**（步骤骨架 + 百分比 + 可取消），而非安静的列表视图。
- 落库粒度：除「保存到故事线」外，增加「仅保存主线 / 保存并继续编辑」等选择，降低「一次性全采纳」的心理门槛。

## 三、触控 / 响应式 / 可访问性（WCAG AA 实测）

### 3.1 嵌套 `<button>` 回归（P0 级，必须优先修）

`LineNav`（:878-948）结构是：
```
<button onClick={onSelect}>            // 外层（:891）
  ...
  <button type="button" aria-label=...> // 内层完结切换（:921）
```
**`<button>` 不能包含 `<button>`**，这是 HTML 规范硬错误。实测弹窗内 `button button` 嵌套 **13 处**（对应 13 条故事线），浏览器控制台明确报：
```
[error] In HTML, %s cannot be a descendant of <%s>. <button> button
[error] <%s> cannot contain a nested %s. button <button>
```
后果：① React hydration error（SSR/CSR 不匹配告警，污染控制台、影响性能诊断）；② 浏览器会强制截断 DOM，外层按钮的点击区域/可访问名可能被破坏；③ 我上轮提的 F-01（键盘可达）靠「把切换改成 button」解决，却因外层本就是 button 而引入了更严重的嵌套问题——**这是 Round-1 修复的副作用，本轮必须正确收口**。

**根因：** Round-1 只改了内层，没意识到外层已是 button。正确做法是让外层不再是 button。

### 3.2 AI 按钮对比度回归（F-02 实质未修好）

实测 AI 生成按钮：`color=rgb(240,238,232)`（浅色）、`background=lab(52.57 44.47 -67.76)` ≈ `rgb(128,103,244)`（鲜紫）。
**对比度 = 3.51:1**（12px / weight 500，属正常文字，需 ≥4.5:1）。

我上轮测的「紫罗兰文字 on 浅紫底」是 3.75:1；Round-1 改成「浅色字 on 实心紫」后变成 **3.51:1——不仅没修好，反而更差**，且仍不达标。即便退回 outline 风格（紫字 on 深面板）也只有 4.48:1（卡在 4.5 边缘）。**唯一稳妥的解法是用更深的紫作按钮填充**。

### 3.3 其余 a11y 实测

- 弹窗 `role="dialog"` + `aria-modal` + `aria-labelledby="workbench-title"`，Esc 关闭、焦点陷阱生效（Round-1 继承，良好）。
- 文字层级令牌在常规背景均过 AA（primary 14.98 / secondary 7.99 / tertiary 5.41 / muted 4.72）；但 **placeholder 用 `--nv-text-muted`(#8E8B82) ≈ 4.33:1 仍临界**（F-06 未动）。
- 4px 自定义滚动条（globals.css:709-721）在粗指针/触屏环境难抓取（F-12 未动）。
- 部分图标按钮 24px 高（`px-1` 类），触控区偏紧。

### 3.4 响应式

实测：弹窗 `max-w-5xl`(1024)，左列固定 `w-72`(288)。视口 820px 时弹窗 788、左列仍 288（占 37%），右列被挤压到 ~460px。左列在窄屏占比过高，缺 `md` 断点收窄或上下堆叠。

## 四、系统级布局大改企划草案（Before → After，可落地）

> 下面按模块给出 before/after 与精确文件:行号。仅提案，未改任何文件。

### 模块 1 · 左列 LineNav 去嵌套 + 键盘可达 + 层级强化
- **Before**：外层 `<button>`(:891) 内含内层 `<button>`(:921) → 非法嵌套 + hydration error；主线/支线文字同色仅图标区分。
- **After**：
  - 外层改为 `<div role="button" tabIndex={0} aria-pressed={selected} aria-label={`${s.title}${selected?'，已选中':''}`} onClick={onSelect} onKeyDown={e=>{(e.key==='Enter'||e.key===' ')&&onSelect()}}>`；内层切换保持真 `<button aria-label>`（:921 不动）。DOM 合法 + 键盘可达。

## 五、发现清单（结构化，含 Round-1 回归）

> 严重度：P0=阻断/非法 DOM；P1=重要 a11y/体验；P2=打磨。

**【R2-P0-1】嵌套 `<button>` 触发 hydration error（Round-1 回归）**
- 文件:行号：`StorylineWorkbench.tsx:891`（外层 button）嵌套 `:921`（内层 button）；实测 13 处嵌套、控制台 2 条 error。
- 现象：`<button>` 内含 `<button>` 非法；React 报 hydration error；DOM 可能被浏览器截断，外层点击/可访问名受损。

## 六、落地顺序与跨透镜协作

### 6.1 建议实现顺序（依赖关系）

1. **P0 先修**：模块 1（去嵌套 button，R2-P0-1）—— 这是非法 DOM，且修起来最小（外层 div 化），不应进入任何大改之后再处理，应作为独立 hotfix 立即合入。
2. **对比度回归**：模块 6（AI 按钮 `--nv-creative-fill` + placeholder 提亮，R2-P1-1 / R2-P2-1）—— 纯令牌/类名改动，无结构风险，可与 P0 同批。
3. **IA 主干**：模块 2（三栏：线导航 + 七要素因果链 + 推进/试探墙）—— 这是「系统级大改」的核心，牵动 :552-872 整段右列重组并新增 `StorylineCausalChain` 组件，需与交互流程透镜对齐「因果链连接器动效」、前端工程透镜对齐「单字段 PATCH 契约」。若 v1.8.11 想先过渡，可用原方案 A 子标签顶上，待因果链基元就绪再升三栏。
4. **写入解耦**：模块 3（七要素 inline 编辑）—— 依赖后端单字段 PATCH 接口（参考 `handleCluePatch` 已存在，七要素大概率可复用同一 `/api/storyline-events` 或新增 `/api/storylines/:id/elements`）；需前端工程透镜确认接口契约。
5. **流程重排**：模块 4（AI prompt 前置 + 生成中区域态）—— 与交互流程透镜强相关（生成态的「可感知性」本质是交互设计问题）。
6. **响应式/触控**：模块 5 —— 可在前述结构改动后统一收口，避免重复改布局。
7. **协作验证**：模块 7（时间轴真实数据）—— 依赖作者透镜实写章节，不在本透镜排期内。

### 6.2 跨透镜协作接口

- **interaction-flow（交互流程）透镜**：模块 2 的「子标签 vs 手风琴」、模块 4 的「生成中区域态」属于交互范式决策，应由该透镜拍板动效与状态机的细节（如子标签切换是否带过渡、生成中骨架屏的步进文案）。本透镜只负责布局容器与可达性约束。
- **copy-empty-state（空状态文案）透镜**：模块 7 时间轴非空态文案、EmptyState 的 description（当前「写作时会自动回写关键情节节点」:820）、AI 中间态提示（:474「中间编辑态（可修改后再落库）」）属文案范畴；若空状态文案要统一语气/动词，请该透镜 review。
- **frontend-engineering（前端工程）透镜**：模块 3 的单字段 PATCH 接口、模块 1 的 `role="button"` 化是否需要同步抽成共享 `KeyboardButton` 组件（避免未来再次出现「交互元素该不该是 button」的争议），建议该透镜沉淀一个语义化交互基元，从根上防住 R2-P0-1 这类回归。
- **musk-perspective（决策）透镜**：本企划的「右列升格子标签」「七要素 inline 编辑」是产品层面的范式选择，若涉及资源排期优先级，请决策透镜在投票环节权衡「修回归（P0）」与「做新布局（模块 2/3）」的先后。
