## 0. 背景与 Round-1 遗留

瑞宝宝的 Round-2 方向（原话要点）：*布局与写入逻辑都不够好；用当前章节继续续写几章试探、多测试看效果；主线/支线/剧情线索推进；七要素到底怎么放。*

这是一个**系统级**诉求，不是改错别字。它要求故事线工作台从「一个静态的规划/查看面板」升级为「**驱动写作的闭环引导器**」。

先用一句话总结现状断点：**故事线和写作是两张皮。** 用户在故事线工作台里能「生成、编辑、标记完结」，但没有任何一处告诉 TA「去写一章试试」「写了之后会发生什么」。时间轴空状态只说「写作时会自动回写」——是被动陈述，不是行动召唤。这正是「布局与写入逻辑都不够好」在文案层的根因。

## 1. 总体改版思路（系统级，不是修字）

把故事线工作台重新定位为 **「写作闭环引导器」**，核心叙事一句话：

> **故事线不是写死的大纲，而是你写着写着长出来的骨架。先有一条线 → 去写 2–3 章试探 → 系统自动把关键节点记进时间轴、把进展回填七要素 → 回来看效果 → 再调线。**

围绕这条叙事，提出三大改版：

1. **续写闭环引导** —— 让「去写一章」成为一等公民（重点）
2. **空状态系统设计** —— 从「零散的占位文字」升级为「分级的引导体系」
3. **命名与说明文案** —— 让七要素/主线/支线/线索集「秒懂」，并收口术语分裂

## 2. 核心改版一：续写闭环引导话术（重点）

### 2.1 写作闭环说明条（新增组件，置于右详情面板顶部）

**问题**：当前右详情面板一进来就是「七要素网格 → 时间轴 → 线索集」三块静态内容，没有任何一句话解释「故事线和工作有什么关系」。新手会以为这是另一个要填空的表单。

**位置**：`StorylineWorkbench.tsx` 查看态 `<div className="space-y-4">`（约 707 行）**最顶部**新增一条引导条。

| | 内容 |
|---|---|
| **Before** | （无） |
| **After** | 一条轻量信息条（icon `sparkles` + 文案）：<br>*「故事线会跟着你的写作一起长出来。先有这条线，去写 2–3 章试探，系统会把关键情节自动记到时间轴、把进展回填到七要素。写完回这里看效果、再调线。」* |

**配套交互（需 frontend-engineering 支持，见 §6）**：条内「去写一章」链接 → 关闭工作台并定位到该线的章节写作入口。

### 2.2 时间轴空状态：从被动陈述 → 行动召唤（改）

**位置**：`StorylineWorkbench.tsx:817-821`

| | 标题 / 描述 / 操作 |
|---|---|
| **Before** | 标题：`还没有章节进展`<br>描述：`写作时会自动回写关键情节节点`<br>操作：无 |
| **After** | 标题：`还没写这一线的章节`<br>描述：`时间轴会在你写作时自动记录关键情节节点——先去写一章，回来就能看到它长出来。`<br>操作（新增按钮）：`去写一章` |

**理由**：用户原话「用当前章节继续续写几章试探」。空状态必须给出**唯一明确的下一步**，而非解释机制。「去写一章」把被动的「会自动回写」变成主动的召唤。

### 2.3 每条故事线详情：新增「据此续写」入口（新增）

**位置**：`StorylineWorkbench.tsx` 查看态头部操作区（约 728-762 行，与「标记完结/编辑/删除」并列）

| | 内容 |
|---|---|
| **Before** | 仅 `标记完结`、`编辑`、`删除` |
| **After** | 新增 `据此续写` 按钮（icon `pencil` 或 `book-open`）：<br>*「据此续写」*（tooltip：`以这条线的七要素为骨架，去写它的下一章；写完这章，进展会自动长回这条线的进度里（点开的是写作页，不是原地生成内容）`） |

**理由**：主线/支线/剧情线索推进，需要一条「从线到章」的最短路径。当前从故事线跳到写作要关弹窗、回 CenterPanel、找章节，路径太长，用户根本不会去做，于是「试探几章」这个核心行为就不会发生。

### 2.4 七要素空态引导（改）

**位置**：`StorylineWorkbench.tsx` 七要素网格区（约 770-794 行），当该线七要素全空时。

| | 内容 |
|---|---|
| **Before** | 六个 `—` + 一个 `待收束`，无任何解释 |
| **After** | 网格上方小字提示：*「七要素是这条线的骨架。你可以直接填，也可以先写几章、让 AI 在写作后自动回填进展。」*<br>空卡片文案从 `—` 改为 `待填` 或 `—`（保留），但新增首元素（欲望）下的一句示例：*「例：她想查清父亲死亡的真相」* |

**理由**：用户问「七要素到底怎么放」。答案是——既要能手动放，也要让写作放。空态必须说清「可以两种方式」，否则用户面对六个 em-dash 会愣住。

## 3. 核心改版二：空状态系统设计（分级体系）

当前空状态是「哪里空了补一句」，零散且无层级。提出**四级空状态体系**：

### 3.1 一级：整个故事线为空（零内容首屏）

**位置**：`StorylineWorkbench.tsx:564-573` 与 `StorylineList.tsx:154-163`

| | 标题 / 描述 / 操作 |
|---|---|
| **Before（WB）** | 标题：`还没有故事线`<br>描述：`让 AI 基于你的大纲自动规划主线与支线，填充七要素框架`<br>操作：`AI 自动生成` |
| **Before（List）** | 同标题/描述，操作：`点击 AI 自动生成` |
| **After（统一）** | 标题：`还没有故事线`<br>描述：`故事线是跟着写作长出来的骨架。先让 AI 规划一条主线与几条支线，或手动新建一条，然后去写几章试探效果。`<br>操作（双按钮）：`AI 自动生成`（主）+ `手动新建`（次，见 §3.5） |

**理由**：补上「手动新建」路径（Round-1 的 P1-06 仍未解决——当前全界面只有 AI 一条创建路径）。同时把「长出来」叙事前置到首屏。两处文案必须完全一致（现在 WB 与 List 描述相同但操作按钮措辞不同：`AI 自动生成` vs `点击 AI 自动生成`，属不一致）。

### 3.2 二级：选中某线但七要素 + 时间轴全空（单线空骨架）

| | 内容 |
|---|---|
| **Before** | 三块各自显示空（七要素 `—`、时间轴 EmptyState、线索 `暂无线索`） |
| **After** | 合并为一张**首登引导卡**（替代三块零散空态）：<br>标题：`这条线还是空的`<br>描述：`三步走：① 填或让 AI 补七要素骨架 → ② 去写 1–2 章试探 → ③ 回来看时间轴和七要素自动长出来。`<br>操作：`据此续写` + `AI 补骨架` |

**理由**：当前三块空态同时出现，信息重复且零碎（「还没有章节进展」「暂无线索，可在下方添加」挤在一起）。合并为一张引导卡，给清晰的「下一步地图」。

### 3.3 三级：时间轴空（已建线、未写章）—— 见 §2.2

### 3.4 四级：线索集空

**位置**：`StorylineWorkbench.tsx:839`

| | 内容 |
|---|---|
| **Before** | `暂无线索，可在下方添加。` |
| **After** | `还没埋线索。伏笔、物证、人物备注都可以记在这里——写的时候随时回看，别漏掉自己挖的坑。` |

**理由**：把「线索集是什么、为什么记」讲清楚（呼应瑞宝宝「剧情线索推进」），而非仅说「可在下方添加」。

### 3.5 选中态无选择（中间态）

**位置**：`StorylineWorkbench.tsx:623-626`

| | 内容 |
|---|---|
| **Before** | `从左侧选择一条故事线查看详情` |
| **After** | 加一个向左箭头图标 `←`，文案改为：`从左侧选一条故事线，或直接点「AI 自动生成」开一条新的` |

**理由**：当前纯文本居中无方向感；加箭头 + 给出第二条路径（生成），消除「死等点击」的空态。

## 4. 核心改版三：命名与说明文案（让术语秒懂）

### 4.1 七要素：每个要素配「一句话释义」

用户问「七要素到底怎么放」——光有「欲望/阻碍/行动/结果/意外/转折/结局」七个词，新手并不知道往里填什么粒度。

**位置**：`StorylineWorkbench.tsx` 的 `ELEMENT_META`（32-44 行）新增 `hint` 字段，并在查看态/编辑态卡片下方以小字显示。

| 要素 | Before label | After label（不变） | 新增 hint（每个一句话） |
|---|---|---|---|
| desire | 欲望 | 欲望 | `这条线里角色最想要什么` |
| obstacle | 阻碍 | 阻碍 | `挡在欲望前面的力量或人` |
| action | 行动 | 行动 | `角色为越过阻碍做了什么` |
| result | 结果 | 结果 | `行动带来的直接后果` |
| twist | 意外 | 意外 | `打乱预期的反转事件` |
| turn | 转折 | 转折 | `角色立场或局势的关键变化` |
| ending | 结局 | 结局 | `收束时的最终状态（写时再定，不预填）` |

**落地样例**（ELEMENT_META 改法）：
```ts
{ key: "desire", icon: "gem", label: "欲望", hint: "这条线里角色最想要什么" },
// ...
```
查看态渲染（约 779-790 行）：在 `{label}` 下方加一行 `<p className="text-[11px] text-tertiary">{hint}</p>`（结局卡仍显示 `待收束`）。

### 4.2 主线 / 支线 / 线索集：命名澄清，消灭「剧情线索」歧义

瑞宝宝原话把「主线/支线/剧情线索」并列，说明三者关系在用户心智里仍模糊。当前实际模型是：**主线/支线是「线」（storyline），线索集是「线」上挂的「点」（clue）**。但「剧情线索」这个词容易让人以为线索集也是一条「线」。

**提议文案整改**：

1. **线索集**标题（832 行）改为带副标题，明确它是「点」不是「线」：
   - Before：`线索集（伏笔、物证、人物备注等）`
   - After：`线索与伏笔（挂在线上的一颗颗「钉」：伏笔、物证、人物备注）`
   - 更短版（推荐）：`线索集 · 你埋下的坑（伏笔/物证/人物备注）`

2. **新建一条线时的类型说明**（编辑态 `类型（主线/支线可互换）`，640 行）补充：
   - After：`类型（主线是骨干，支线是旁支；可随时互换）`

3. **术语收口（P0-02 收尾）**：全项目把 `剧情线` 统一为 `故事线`。优先级：
   - 高：UI 层 `BackupDialog.tsx:18`、`ImportDialog.tsx:17` 的 label `剧情线` → `故事线`
   - 中：AI 后台 prompt / 变量名 `plan-chapter.ts`、`outline-context.ts`、`generate.ts` 中的「剧情线」→ 下一轮重构统一（不影响用户可见文案，但避免开发者与用户术语错位）

### 4.3 进度文案与标签收尾

| 位置 | Before | After | 理由 |
|---|---|---|---|
| `StorylineList.tsx:199` `主线进度` | 仅主线显示，支线无同名 | 统一为 `故事线进度`（主线/支线都用） | 支线卡片无进度标题，不一致 |
| `LeftPanel.tsx:47` `故事线 (13)` | 半角括号 | 全角 `故事线（13）` | P2-02 收尾，与工作台统一 |
| `storyline-progress.ts:34` | `要素 ${n}/${m}（不含结局）` | `七要素 ${n}/${m}（结局另计）` | 当前 label 未上屏但作为语义锚点，先统一措辞 |
| `StorylineWorkbench.tsx:119/121` | `轮询失败` | `获取生成结果失败` | P1-02 收尾，去掉技术黑话 |
| `StorylineWorkbench.tsx:474` | `AI 生成结果 · 中间编辑态（可修改后再落库）` | `AI 生成草稿（可改，确认后保存）` | 「中间态」「落库」黑话收口 |
| `StorylineWorkbench.tsx:511` | `结局不可在此填写，落库后可通过「标记收束」设定` | `结局先不填——写完这章、确定走向后再「标记收束」` | 更口语、更讲清原因 |

### 6.1 工程依赖已核实（frontend-engineering 确认，2026-08-10）

`onWriteChapter` 回调经前端 lens 核实为**必要新增项**——当前无任何「故事线→写作」通道可复用。已确认的四层 prop 透传路径：

```
StorylineWorkbench  新增 prop: onWriteChapter?: (storylineId?: string) => void
StorylineList       透传 onWriteChapter → <StorylineWorkbench onWriteChapter={...} />
LeftPanel           透传 onWriteChapter → <StorylineList onWriteChapter={...} />（L124-125）
[projectId]/page.tsx 新增 handleWriteFromStoryline(storylineId?) → <LeftPanel onWriteChapter={...} />
```

页级 handler 契约（前端侧，已据 v1.8.10 核实）：
- ① **必须先解析目标章节点**：写作流是**节点绑定**的——`/api/generate/write`（`route.ts:48-50`）要求 `nodeId`、缺失即 400，`handleWriteConfirmed`（`page.tsx:708`）亦用 `selectedNode.id`；且 `StorylineData` 本身**不带任何 nodeId 引用**（故事线是项目级全局对象，不与具体章节绑定），工作台模态此刻也无选中节点。因此 `onWriteChapter` **不能直接调 `handleWrite`**（其 `page.tsx:562` 有 `if (!selectedNode || !project) return` 守卫）。解析顺序：优先已选节点 → 否则按「该线最新 MILESTONE 的 chapterOrder+1」定位下一章 → 否则回退让用户先选/新建一章。
- ② 暂存 `storylineId`；③ 打开既有写作流（`setPreGenMode("write"); setPreGenOpen(true)`，与 CenterPanel「生成/重写」同源）。
- ④ **MVP 中 `storylineId` 仅作 UX 聚焦提示**（前端高亮/埋点）：服务端 `loadGenerationContext`（`context-loader.ts:88-92`）已把全部 ACTIVE 故事线注入 prompt，MVP **不必改服务端上下文**；精确约束（让 AI 严格优先该线七要素）留待阶段 2.5 增强。

**CTA 触发映射（文案侧已锁定，见 §5 第 2/3/6 项）**：
- 时间轴空态「去写一章」→ `onWriteChapter()`（无参，走默认章）
- 详情头部 / 单线空骨架「据此续写」→ `onWriteChapter(selected.id)`（精确约束该线七要素）

**与企划 B 的关系（重要）**：本 `onWriteChapter` 为**轻量、用户在线、单章** handoff（契合「试写一章看效果」）；企划 B 的 `targetType:"storyline-advance"` 为**真后台、批量 N 章**集成。MVP 优先走本 handoff（复用 100% 现有写作流、风险最低），autonomous 批量降为阶段 2.5 增强，二者不冲突。

## 7. 风险与权衡

1. **引导条会不会太啰嗦？** §2.1 的引导条是一段较长的说明。权衡：首次进入显示完整版，之后可折叠/记忆「已读」。文案本身控制在 60 字内（样例已压到 ~55 字）。
2. **「长出来」隐喻是否易懂？** 「故事线会跟着写作长出来」是核心隐喻，对非写作者可能略抽象。备选：`故事线是写作时自动累积的进度地图`。建议 A/B 或投票定。
3. **双操作按钮（AI 生成 + 手动新建）是否稀释 AI-first 定位？** 瑞宝宝方向是「多测试看效果」，手动新建能降低试探门槛，与方向一致；且手动线也会被时间轴/七要素回填，同样进入闭环。建议保留。
4. **七要素 hint 是否信息过载？** 七张卡片各加一行小字，可能显拥挤。权衡：hint 仅在**查看态**显示、字号 11px、 tertiary 色；编辑态可不显示（编辑时用户已在填，不需要提示）。
