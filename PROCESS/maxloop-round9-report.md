## 一、干了什么（一句话）

把上一轮诚实边界里剩下的三项「规范性收尾」全部做完：章节状态名在全项目核心链路里统一到单一真相、我们新建的代码 lint 归零、游戏导出后的结果在界面上明确告诉作者下一步该干嘛；然后跑了一轮最终全链路复检确认没有回归。

## 二、为什么这么做（第一性原理）

前几轮 Max Loop 把「确认体系」的**功能正确性**修完了（护栏可信、幂等、审校联动……），但留下三类「债」：

1. **状态名两套真相**：状态机枚举 `story-status.ts` 已经建好，但只有 3 个核心文件在用，其余几十处地方还在手写字符串 `"confirmed"`、`"drafting"`。手写字符串的坏处是**拼错不报错**——比如把 `"pending_confirm"` 写成 `"pending_confrim"`，编译能过、运行时空字符串不匹配任何状态，确认流程静默失效。这不是「好不好看」的问题，是**可维护性→正确性的风险**。
2. **lint 增量债**：我们每次改代码都可能顺手留下 lint 错误（比如 `as any`），日积月累会变成新的 2542 债。正确姿势是**新增代码零债**，存量债另算。
3. **游戏导出结果不透明**：游戏导出后章节可能被自动定稿、也可能待手动确认，但结束屏永远显示同一句话，作者不知道下一步该干嘛——体验闭环缺最后一环。

## 三、用了什么方法/工具、效果如何

### ① 状态枚举全面落地（10 个文件）

在 `src/core/story-status.ts` 增加 6 个单态常量（`STATUS_CONFIRMED`、`STATUS_DRAFTING` 等），再把核心确认链路 10 个文件里的字面量逐一替换成常量引用：

`auto-confirm` / `[id] PATCH` / `batch-confirm` / `nodes` / `rollback` / `game-engine` / `post-processor` / `stats-monitor` / `projects-confirm` / `generate-write`

**替换过程中的关键判断**（这是最容易翻车的地方）：`game-engine.ts` 里有一处 `status: "completed"` 是写给 **`gameSession`**（游戏会话）表的——那是会话自己的状态机，和章节状态机**不是一回事**。如果无脑替换，就破坏了会话状态语义。所以替换时只动 `StoryNode` 的状态，会话状态保留原样。同理，`create/import/dissect` 域的初始创建态字面量保留——那些状态不参与确认判定，替换收益低、风险高。

**效果**：tsc 零错误通过（替换是等价的——常量值就是原字符串），行为零变化，但以后想改状态名/加状态，只改 `story-status.ts` 一个文件，编译期就能抓出所有引用点。

### ② lint 增量归零

逐文件跑 eslint，把「我们新建/改过的代码」里的问题清零：

| 问题 | 修复方式 |
|---|---|
| `confirm-guard.ts:110` 唯一 `as any[]` | 改为 Prisma 的 `JsonArray` 类型（`Record<string,unknown>[]` 太窄，Prisma Json 含 `null`，会报 TS2322——用对类型库自带类型才是正解） |
| `scripts/*.cjs` 的 `require()` 报错 | 这是**规则误伤**：`.cjs` 是 CommonJS 原生格式，`require` 是标准用法。在 eslint 配置里对 `scripts/*.cjs` 豁免该规则（只豁免脚本目录，不全局关） |
| `ChapterConfirmBar` 的 `s.icon as any` | icon 字段类型改为 `IconName`（`keyof typeof iconMap`），类型化而不是绕过 |
| `ChapterConfirmBar` 的 `allConfirmed` 未使用 | v0.46.101 简化后该 prop 已无用，从解构移除（类型定义保留兼容父组件） |
| `PreGenConfirm` 的 `loadCards` 声明前使用 | `const` 箭头函数无提升，改为 `function` 声明（函数声明有提升），消 `no-use-before-define` |

**效果**：新建文件 lint 全干净；两个组件剩 2 个**存量 warning**（`exhaustive-deps` / `no-unused-expressions`，历史代码），明确标注为历史债不强行修（避免无谓回归风险）。存量 2542 个 lint 问题做了基线存档，留待专项。

### ③ 游戏导出状态提示

`game/[nodeId]` 页的结束屏按导出结果分三种提示：

## 四、关键取舍（为什么这样做，而不是那样做）

1. **为什么不全量替换 30+ 文件的状态字面量？**
   只替换核心确认链路 10 个文件。`create/import/dissect` 域的字面量是「初始创建态/流程内固定态」，不参与确认判定——替换它们纯属机械劳动、收益趋近于零，还引入额外 import 耦合。**优化要按「风险×收益」排优先级，不是按「数量」**。

2. **为什么 lint 存量债不清？**
   2542 个问题里绝大多数是历史 `no-explicit-any`（早期代码风格）。一次性全清 = 大范围改动 + 回归风险，收益只是「数字好看」。本轮目标定在**增量归零**——以后新代码不添债，存量债建档等专项。这符合「不为了形式上的完美冒实质风险」的工程原则。

3. **为什么 eslint 配置豁免而不是改脚本代码？**
   脚本是 CommonJS 文件，`require` 就是它的正确写法。用 `import` 语法改 .cjs 反而会跑不起来。**规则服务于正确代码，不是让正确代码迁就规则**——所以豁免的是规则的适用范围（脚本目录），不是规则本身。

4. **游戏导出提示为什么放「结束屏」而不是 toast？**
   导出后作者马上要做的就是「返回工作区处理」，这是唯一一个「下一步决策点」。结束屏是常驻信息（不看会一直显示），toast 弹一下 3 秒就没了——决策点信息要持久，过程信息才用 toast。
