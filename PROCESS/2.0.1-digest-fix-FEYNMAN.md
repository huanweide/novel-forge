# 工作单元完成报告：摘要大纲去重 + 垃圾过滤 + 标题归一（v2.0.1）

> 费曼式（零基础也能照做复现）· 面向瑞宝宝 · 2026-08-12

---

## 一、干了什么（一句话）

摘要大纲面板（「更多▾ → 摘要大纲」）过去会把 **AI 应答模板的残片** 当成正经内容吐出来，比如「您提供的章节内容似乎为空」「我注意到您提供了模板…」。这次把它**从源头根治**：聚合层改成纯函数、过滤掉这些垃圾，并在摘要生成入口拦住新脏数据；同时把已经脏掉的两本小说库一次性清理干净，打开就是清爽的。

---

## 二、为什么这么做（拆到底层原理）

**用大白话讲清问题本质**：摘要大纲本质是「把每章的摘要串成一条时间线」。它本来只负责「把已有的摘要拼起来」，自己不生产内容。但底层数据库里混进了**脏数据**——有些章节的摘要根本不是摘要，而是 AI 在拿到空内容/模板时，反过来问用户「请把正文粘贴进来」的**元应答**（就像你问助手一个问题，助手不答、反手把问卷丢回给你）。旧代码忠实地把这些「问卷」也拼进了大纲，于是你看到了模板残片。

**类比**：这就像你让秘书把各部门的周报贴成一张大表（大白话：汇总），结果有个部门交上来的是一张「请填写以下信息」的空白表格（大白话：没干活反而要你填表）。秘书不管三七二十一贴上去，整张表就出现了空白表格。问题不在秘书贴表，而在那个部门交了空白表。

**第一性原理推导**：
- 秘书（聚合层）只能照贴 → 要干净，必须保证交上来的每一张都是真周报 → 所以在「贴」这一步就过滤掉空白表。
- 空白表还会持续产生（AI 偶尔仍会生成）→ 所以在「交表」（落库）那一刻就拦住，不让空白表进数据库。
- 已经进库的空白表 → 一次性人工清掉，让打开即干净。

---

## 三、方法 / 工具与效果（对比过什么、结果数据）

### 1. 把聚合抽成「纯函数」（核心修复）
- **新文件** `src/core/pipeline/digest-aggregate.ts`，零 Prisma 依赖、零副作用，输入数据、输出字符串，可被单测直接断言。
- 三个关键函数：
  - `isGarbageSummary(summary)`：**判定垃圾**。命中任一即垃圾——空/空白、长度 < 12 字、或命中模板元应答关键词（「您提供的章节内容似乎为空」「没有提供实际的正文内容」「等待您补充」「出场角色」「章末原文」「完整正文」「我注意到您提供了模板」等）或「模板/章节标题/占位」字样。
  - `buildTimelineDigest(summaries, orderMap)`：**按章去重 + 过滤垃圾 + 排序 + 拼装**。每章只留「非垃圾且最长」一条；已删节点的遗留行直接排除；按章序取最近 20 章；标题自带「第X章」前缀循环剥离（中/阿数字都算），杜绝三重前缀。
  - `buildStorylineDigest(...)` / `formatStorylineEvents(...)`：主线事件聚合同步纯函数化，可单测。
- `digest.ts` 的 `rebuildProjectDigest` 改为只做「取数 → 调纯函数 → 落库」，逻辑没变、但脏数据进不来。

### 2. 入口拦截（杜绝新脏数据）
- `src/app/api/generate/summarize/route.ts`：默认生成模式 + 确认落库模式，落库前都先 `isGarbageSummary` 判一遍，命中直接 422 拒收、不落库、不重建大纲。
- `src/core/pipeline/post-processor.ts`：写完一章自动摘要落库 / 重建大纲前加同一守卫，AI 偶发返回占位元应答时按垃圾处理。

### 3. 已脏库一次性清理（让用户打开即干净）
- 独立脚本（用完已删）直连 PostgreSQL，清理「新城·龙陨之地」（15 行脏数据 → 4 行干净）与「星辰」（4 行 → 1 行），用纯函数重算 `timelineDigest` / `storylineDigest` 写回。

### 4. 效果数据（可复现）
- `SAFE_DELETE_DISABLE=1 npx tsc --noEmit` → **0 错误**。
- `npx vitest run` → **55 文件 482/482 全绿**（新增 14 条 `digest-aggregate.test.ts` 单测）。
- 库清理后重算的大纲：无任何「您提供的章节内容似乎为空」式残片，无三重前缀。

## 四、关键取舍（工具 A 为何不选 B、踩坑与修复）

**为什么抽纯函数而不是在旧聚合里打补丁？**
- 旧聚合嵌在 `digest.ts`（依赖 Prisma/Next 运行时），无法脱离数据库单测，垃圾逻辑混在 SQL 取数里，改一处怕动全局。抽成纯函数后，去重/过滤/标题归一都能用「喂假数据、看输出」的方式锁死行为，以后谁改都不会让模板残片回来。**这是「逻辑之下且真的有用」的关键：不是擦表面，是把漏洞从结构上焊死。**

**为什么不引入 LLM 重新生成摘要？**
- 用户说「不需要弄得太复杂」。脏数据由一次性脚本清掉即可；运行时只需「不进脏、不吐脏」，纯正则/字符串判定零 token、幂等、可断言，远比调 LLM 重算省钱且可控。

**踩坑现场（真实发生过，已修复）**：
1. **tsx 缓存导致旧代码跑清理**：第一次重跑清理脚本时，tsx 缓存了未加 strip 的旧 `digest-aggregate`，DB 里存的仍是带三重前缀的旧大纲。排查方式：用 `node -e` 验证正则本身正确 → 确认文件确有新代码 → `rm -rf node_modules/.cache/tsx` 清缓存后重跑，输出才正确。**反自欺**：不要只看「脚本跑过了」，要直接 dump 库里的最终字符串核对。
2. **三重前缀的真正来源是「畸形节点标题」**：最初以为前缀来自摘要文本，反复在 `text` 上做 strip 无效；直到 dump 每个 chapterId 对应的节点标题，才发现 ch3 的标题本身就是「第三章：第3章」（中文+阿拉伯数字叠的废标题）。于是把 strip 改成**循环剥离标题前缀**（中/阿数字都吃、剥到干净为止），才真正根治。这说明：修 bug 要顺着数据追到最底层，别凭猜。

**货物崇拜检测（去掉形式还剩什么）**：去掉「纯函数」「去重」「幂等」这些词，这份报告剩下的核心仍是——「保证交上来的是真周报、空白表不让进库、已经进的清掉」，以及「追到节点标题才找到真凶」。这俩结论不依赖任何术语，照做就能复现。
