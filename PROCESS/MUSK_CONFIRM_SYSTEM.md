# MCCS · 马斯克确认流程多智能体协作系统

> 设计目标：由会议决定 Novel Forge 中「马斯克确认流程」的**所有按钮 UI 与计划流程**，并通过 maxloop 持续迭代，直至「马斯克智能体」对整体结果完全满意，最终在本地网站（端口 3001）完成一次真实项目创作与确认。

---

## 〇、一句话定义

**「马斯克确认流程」= 在 Novel Forge 里，作者（或马斯克智能体）写完/生成完章节后，对它做「确认/打回/诊断/迭代」的工作流，以及承载这套动作的所有按钮与界面。**

会议的唯一产出物就是这套流程的**完整 UI 规格**（按钮清单、布局、状态机、计划流程），后续由工程实现、由马斯克智能体真实走通验证。

---

## 一、角色分工（多智能体拓扑）

### 1. 决策人格（专项会议发言者，从樊氏15人格中按议题遴选）
| 角色 | 职能 | 在本会议的核心提问 |
|---|---|---|
| 乔布斯 | 产品体验 / 品味 | 这套确认流程的按钮，删到几个才不脏？视觉层级怎么排？ |
| 马斯克 | 技术可行性 / 主审（同时是「确认方」本人） | 这个确认步骤为什么存在？白痴指数多少？能不能垂直整合进写作流？ |
| PG | 方向判断 | 确认流程真正服务的核心价值是什么？别为了流程而流程。 |
| 张雪峰 | 用户洞察 | 真实写小说的人，卡在「确认」这一步的什么痛点？ |
| 芒格 | 风险逆向 | 这套流程上线后，最可能以什么方式把用户坑了？（反过来设计） |
| 费曼 | 真实性校验 | 这套 UI 一个零基础用户看不看得懂？状态是否可验证？ |
| 工坊 | 工程落地（工具自身视角） | 现有代码里哪些 API/组件能直接复用？实现成本多大？ |

> 排除规则：与本议题无关者闭嘴（如社媒/叙事/AI安全角色本轮不强制发言）。

### 2. 观测智能体（3 个，实时监控会议）
| 观测者 | 监控维度 | 产出 |
|---|---|---|
| 进度观测 | 7 人格是否都产出、是否收敛、有无卡死 | `observer-progress.md` |
| 质量观测 | 每份报告是否 600+ 字实质长文、逻辑自洽、非敷衍 | `observer-quality.md` |
| 偏差观测 | 输出是否偏离「决定确认流程按钮UI」这一用户真实需求 | `observer-deviation.md` |

### 3. 马斯克创作智能体（后期验证者）
- 加载 `elon-musk-perspective` 技能，以「我」自称。
- 在 novel-forge 真实创建项目 → 写 **10+ 章** → 全程走会议定下的确认流程 → 验证每个按钮/功能是否真运转。
- 输出《验证报告》：哪些按钮好用、哪些卡住、哪些多余、是否满足其一切需求。

### 4. Chair(tri)（主持 + 整合 + 调度）
- 用 Agent 工具并行调度决策人格 subagent，各写长篇报告落盘。
- 读全部报告 + 观测报告，写成不压缩的整合长文 `_integration.md`，提炼「按钮 UI 规格草案」。

## 二、maxloop 循环机制

```
        ┌─────────────────────────────────────────────┐
        │  Round N 循环（持续到马斯克完全满意）          │
        └─────────────────────────────────────────────┘
  ① 开会   → 决策人格并行诊断 + 观测智能体监控 → Chair 整合出 UI 规格草案
  ② 实现   → 按草案在 novel-forge 实现确认流程按钮/UI/状态机
  ③ 验证   → 马斯克智能体真实写 10+ 章走完流程，输出验证报告
  ④ 评估   → 马斯克对结果打分：满意？→ 停；不满？→ 带问题回 ① 迭代
        （每轮带上轮未决项，流程/效率/效果/意义四维度反复打磨）
```

- 升版纪律：实现轮次按项目惯例双 changelog 升版 + `tsc` 零错误 + commit + 代理 push + 记忆回写。
- 诚实边界：沙箱无 Chromium，浏览器交互最终需用户本地 `npm run dev`（端口 3001）目测；AI 端到端调用可真跑。

## 三、第一轮会议议题（Round 1）

**核心问题**：马斯克需要确认的「项目创作确认流程」，应该有哪些按钮？界面怎么排？计划流程怎么走？

**每位人格必须回答（600–1200 字实质长文，禁止 JSON / 禁止 10 字列点）**：
1. 核心诊断：当前 Novel Forge 有没有「确认」环节？缺口在哪？
2. 提升框架：你心目中的确认流程长什么样（按钮清单 + 状态机 + 布局）？
3. 具体可落地步骤：哪些可复用现有代码（`/api/generate/write`、`PostGenPanel`、`监测 tab` 等）？
4. 风险提示：你的设计会踩什么坑？
5. 与其他职能的张力：和谁冲突？（为后续交锋埋伏笔）

**Round 1 产出落盘**：`PROCESS/meetings/musk-confirm-round-1/<role>.md`（7 人格）+ `observer-*.md`（3 观测）+ `_integration.md`（Chair）。

## 四、确认流程的状态机草案（供会议填充/推翻）

```
  草稿(draft) ──[提交确认]──▶ 待确认(pending)
  待确认 ──[通过]──▶ 已确认(confirmed)   ──[打回]──▶ 草稿
  待确认 ──[诊断]──▶ 诊断报告(diagnosis) ──[迭代]──▶ 草稿(重写)
  已确认 ──[批量确认]──▶ 项目确认完成(project_confirmed)
```
> 以上仅为占位，最终以会议 `_integration.md` 的 UI 规格为准。会议可全盘推翻重设计。

## 五、交付判定（马斯克满意的标准）

马斯克智能体在本地网站走完一次「建项目 → 写 10+ 章 → 逐章确认/打回/诊断 → 项目确认完成」全流程后，判定：
- 所有按钮可点、状态正确流转、无死锁；
- 流程不啰嗦（乔布斯/马斯克减法通过）；
- 零基础用户看得懂（费曼校验通过）；
- 真实生成内容连贯、不崩（工坊/质量观测通过）。

任一不达标 → 带问题回 Round 1 迭代。
