# 002 · 乔布斯视角：功能实用性裁决报告

## 一、核心诊断

novel-forge 的根本命题只有一个：一个本地作者，能不能顺畅地把自己脑子里的小说写出来，并且写长不崩。所有功能都必须过三道关——第一眼能懂、写作流不断、删掉它产品是更轻还是更残。用这三关照一遍，真相很清楚：真正构成「写小说」这件事骨架的，只有写章、续写、精修、自动填表、导入、导出、删节点这七样；章节摘要是无名英雄，该藏起来做功；限流是看不见的脚手架，留着但别挡道；伏笔检测是好心办坏事的话术堆；游戏开局则是一个完全不该出现在这里的陌生人。

最刺眼的问题不是某个功能坏了，而是产品「长了一张模糊的脸」。一个普通小说作者打开 novel-forge，他脑子里想的是「我要写一章」。但他会同时看见写章、续写、精修、摘要、伏笔、游戏开局……这些词里有一半他第一眼不知道干嘛。认知负担就是在这里悄悄长出来的。我们不是在卖功能清单，我们是在卖「我能写下去」的安全感。

## 二、提升框架

我的框架只有一句话：**让核心隐形，让边缘退场**。写章、续写、精修应该合并成一个连贯的「写作循环」心智模型，而不是三个并排的按钮让人选。章节摘要和伏笔检测这类「为了不崩坏而存在」的引擎，必须沉到水面之下，用「你的故事还很连贯」这种温柔反馈代替「收束率 87%」这种工程师黑话。凡是需要用户先理解概念才能用的功能，都还没毕业。游戏开局这种把小说平台变成文字冒险游戏的东西，不是优化能救的——它从根上动摇了「我们在做一个写作工具」这件事，必须砍。

## 三、具体可落地步骤

第一，把「写章 / 续写 / 精修」收拢成一条主路径：写新章、接着写、改这段。三者共享同一套流式生成与同一套心智，不要在首页平铺成三个并列入口。第二，章节摘要默认自动跑、不弹窗、不教用户什么是摘要；只在长文出现潜在矛盾时，轻量提示「第 3 章和第 8 章似乎对不上」。第三，伏笔检测改名换皮，从「收束率幂等重算」改成「未收尾的线索」，且只在用户主动点开「脉络」时才展示，绝不默认打扰。第四，限流保留但调到几乎不会误伤本地用户的宽松阈值，并在触发时给一句人话「生成太快了，稍等几秒」，而不是冷冰冰的 429。第五，导出先砍到 Markdown 与纯文本两种，epub/docx 等真有用户喊了再做。第六，游戏开局进入砍除清单。

## 四、风险提示

最大的风险是「用力过猛的好意」：自动填表、章节摘要、伏笔检测每一项单独看都合理，叠在一起却把写作工具变成了仪表盘。用户不想要仪表盘，他想要一张干净的稿纸。另一个风险是砍游戏开局会动到已经投入的实机代码与测试，但和「产品人格清晰」比，这点沉没成本不值得留。还有，限流若调得太松，本地模型遇到失控循环可能被打满——所以「留着但宽松」比「直接删」更稳。

## 五、与其他职能的张力

马斯克会从第一性原理说游戏开局不服务核心目标，我们在这点一致。但工程视角会心疼已写好的 game/start 链路与测试投入，我的回答是：代码可以留作技术债参考，产品入口必须消失，二者不矛盾。算法视角会为伏笔检测的幂等重算引以为豪，我要把它从「算法成就」翻译成「用户价值」才肯收。芒格会提醒别被「功能越多显得越专业」的错觉骗了——这正是我担心的，功能数量制造了虚假的成熟感，真正的成熟是敢于少。

### 十一功能裁决总表

| 项 | 功能 | 裁决 | 一句话产品理由 |
|---|---|---|---|
| ① | 写章 | 有意义 | 这就是产品本身，没有它一切免谈。 |
| ② | 续写 | 有意义 | 顺着写下去是作者最自然的动作，必须顺滑。 |
| ③ | 精修 | 有意义 | 改稿是写作的一半，但应并入写作循环而非另立山头。 |
| ④ | 章节摘要 | 有意义 | 长文不崩的隐形引擎，价值大但必须藏起来别让用户操心。 |
| ⑤ | 限流 | 待优化 | 单用户本地是过度防御，留着但调宽松、说人话。 |
| ⑥ | 自动填表 | 有意义 | 「我写它替我记」的魔法感，直接减负。 |
| ⑦ | 伏笔检测 | 待优化 | 意图好，但「收束率」是黑话，要变成温柔的未收尾提醒。 |
| ⑧ | 游戏开局 | 傻子功能 | 把写作工具变成文字游戏，分裂产品人格，砍。 |
| ⑨ | 导出 | 有意义 | 作品必须能拿走，但五格式是膨胀，先两三种。 |
| ⑩ | 导入 | 有意义 | 作者的草稿在别处，这是进门的第一块砖。 |
| ⑪ | 删节点 | 有意义 | 删章节天经地义，但改名「删章节」更直觉。 |
