## 二、核心共识：8 项承重墙

写章 / 续写 / 精修 / 章节摘要 / 自动填表 / 导入 / 导出 / 删节点，七位人格一致判「有意义」，构成「写→续→修→记→进→出→删」核心闭环。这是产品存在的理由，资源必须优先保其质量与稳定性。Phase 1 已钉死的两个 P0 bug（summarize 500、refine 截断）正是落在承重墙上，修复优先级正确。

## 三、全票傻子功能：游戏开局（7/7 砍除）

**唯一一项七票全红的傻子功能。** 剖析其本质：novel-forge 的定位是「本地运行的 AI 小说创作平台（类比 SillyTavern）」，核心承诺是「让本地作者高效写出连贯、长线、不崩坏的小说」。游戏开局把平台偷换成「AI 叙事 + 选项分支的互动游戏引擎」，犯了两重错——

1. **方向偏离**：真实作者要的是写完一本书，不是做个会冒选项的玩具。它稀释了「写作利器」的最初印象，让早期被「纯粹写作」吸引的用户不确定这工具到底为谁而造。
2. **工程吸血**：多一个子系统就多一条模型抽风后产出破烂状态的尾部，还吸走本该投给 truncate/parse 这类真脆弱点的工程注意力。代码可留作技术债参考，但**产品入口必须消失**。

## 四、高共识降级 / 改造清单（6 项）

1. **限流 rate-limit**：7/7 认为单用户本地是过度防御。它把 SaaS 的「防滥用」铃铛挂到自家门上，唯一正当性只剩「别把用户自己的 API key / 供应商额度打爆」。决议：降级为监听模型供应商 `429/Retry-After` 的优雅退避，默认关闭或极宽松，不弹窗邀功、不叫「功能」。
2. **伏笔检测 foreshadowing**：意图好，但「收束率幂等重算」是给工程师看的黑话。决议：改名「未收尾线索」，按需触发（非常驻重算），弃用单一收敛率数字，输出「已埋未收 / 已收 / 悬空」可行动清单。
3. **导出 export**：五格式是格式蔓延（epub/docx 依赖地狱）。决议：默认 markdown/txt/html，epub/docx 折叠为进阶选项。
4. **自动填表 babylore**：魔法感强，但自动覆盖同名词条是单点脆断。决议：提取结果进「待审区」，用户逐条确认/拒绝后才并入世界卡，禁止自动覆盖。
5. **删节点 delete**：本地硬删 + 无回收站 = 教科书级黑天鹅。决议：硬删改软删（tombstone + 撤销期），仅「清空回收站」为显式二级确认。
6. **精修 refine**：T2 截断已修，但塔勒布指出 `cap 5000 字` 静默截断是新尾巴。决议：补 diff 预览 + 可撤销；取消静默 cap，超限时前端明确警告让用户选「分段精修」或「提高预算」。

## 五、张力剖析（最有价值的干货）

- **工程严谨 vs 用户感知**：限流、伏笔在工程师眼里是「健壮性 / 专业性」的体现，在用户眼里却是「功能堆砌制造的虚假成熟感」。真正的专业是让写作顺到作者忘了工具存在，而不是给本地工具装上多租户才需要的护栏。
- **产品卖点 vs 方向聚焦**：游戏开局倡导者想做差异化拉新，但真实作者要的是「写完一本不崩的小说」。拉新靠的是那一个被做透的点，不是菜单长度。方向错了，功能再精也白做。
- **沉没成本陷阱**：砍游戏开局会动已写代码与测试，但和「产品人格清晰」比，这点沉没成本不值得留——代码可保留，入口必须消失。
