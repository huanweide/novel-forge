# Round 16 · 005-张雪峰（用户洞察）· 功能实用性独立裁决

> 视角声明：我是樊氏15人格里的「张雪峰」——只替真实普通用户说话。我脑子里装的是那个在县城出租屋、用着老旧笔记本、想用 AI 把一本 30 万字小说写完的普通人。他不在乎架构多优雅，只在乎三件事：**别让我丢稿、别让我崩、别让我写得不连贯**。下面每项都拿这把尺子量。

## 一、核心诊断

novel-forge 现在最大的问题是：**一多半功能在替「平台工程师」而不是「写书的人」设计**。本地、单用户、不联网——这个定位决定了它的敌人是「长线遗忘、崩坏、手写卡表的累」，而不是「多用户滥用、并发攻击、SaaS 成本」。但评审输入里的限流、游戏开局，明显是把 SaaS 那套防滥用、炫交互的思维带了进来，属于典型的「看起来牛，但写完一本书也没碰过一次」。

真正天天用的，是写章、续写、精修、章节摘要、导出——这五个是作者的命根子。自动填表和导入是「进门和减负」的刚需。删节点是基本的 CRUD。伏笔检测是「 periodic 体检」，有用但不日常。限流和游戏开局，我直接判傻子功能或严重待优化。

## 二、11 项功能逐条裁决（用户视角）

| 项 | 功能 | 裁决 | 一句话用户理由 |
|---|---|---|---|
| ① | 写章 write | 有意义 | 不流式出章节，这个软件就不存在，作者每天第一件事就是它。 |
| ② | 续写 continue | 有意义 | 「卡文/想往下走」是长篇作者最高频动作，一键续下一节点直接救命。 |
| ③ | 精修 refine | 有意义 | 改稿是日常，但 Phase1 的截断 bug 让它等于摆设，修好才是真功能。 |
| ④ | 章节摘要 summarize | 有意义 | 30 万字超出模型记忆，摘要是「不崩坏、不断片」的唯一保险，必保。 |
| ⑤ | 限流 rate-limit | 待优化 | 本地就你一个人写，跟自己限流纯属脱裤子放屁，除非为防死循环烧钱。 |
| ⑥ | 自动填表 babylore | 有意义 | 手写世界卡累死人，正文自动提词是实打实的减负，但得让作者能改。 |
| ⑦ | 伏笔检测 foreshadowing | 待优化 | 长篇作者确实会忘自己埋的坑，但它是「写完一阶才体检」的工具，不是天天用。 |
| ⑧ | 游戏开局 game/start | 傻子功能 | 人家是来写书的不是来玩文字游戏的，旁支炫技，砍了不心疼。 |
| ⑨ | 导出 export | 有意义 | 稿子得是「我的」，多格式导出是防锁死、能拿去发的底气，必保。 |
| ⑩ | 导入 import | 有意义 | 谁还没点旧稿？没导入就没人进得来门，是上车的刚需。 |
| ⑪ | 删节点 delete | 待优化 | 删章谁都要，但本地最怕误删丢稿，得加二次确认或软删回收。 |

## 三、提升框架

把功能分成三层来对待：**命根子层（①写章 ②续写 ③精修 ④摘要 ⑨导出）** 砸资源保稳定、保质量；**减负层（⑥填表 ⑩导入）** 做顺手、做可编辑；**体检层（⑦伏笔）** 做成事后审计而非前置负担。**砍掉/收起层（⑧游戏）** 直接移出核心路径，想留就塞进「实验」标签页别占主界面。**存疑层（⑤限流）** 改成可关的「防死循环熔断」，默认关，不弹窗烦人。

## 四、具体可落地步骤

第一，先把两个 P0 bug 复检跑通，尤其摘要（④）和精修（③）——这两个一旦好用，作者才敢放心写长线；坏着就是「花架子」实锤。第二，导出（⑨）把 epub/docx 打通，这是作者「能拿去发」的临门一脚，优先级高于第五种格式。第三，自动填表（⑥）提取结果必须**可逐条编辑、可拒绝**，否则作者不信任、宁可自己写。第四，删节点（⑪）加软删除回收站，本地丢稿比任何 bug 都伤用户心。第五，游戏开局（⑧）从主流程移除，限流（⑤）降级为可选熔断。

## 五、风险提示

最大的风险不是某个功能没用，而是**把精力铺在炫技功能上，命根子层反而出 bug**。一个普通作者第一次遇到摘要 500、精修截断，他不会怪代码，他只会觉得「这破软件不行」然后卸载。所以本轮千万别因为游戏开局「实装了」就觉得完成，用户根本不点它。另一风险是过度工程：本地单用户要什么限流、什么幂等重算的复杂度，都是在给维护加债、给稳定性埋雷。

## 六、与其他职能的张力

我跟「工程架构」那位的张力最明显：他可能觉得限流、幂等锁是工程严谨，但我眼里那是替不存在的多用户操心。我跟「产品愿景」也有张力——他可能想用游戏开局做差异化卖点，但真实作者要的是「写完一本不崩的小说」，不是会冒选项的玩具。我的建议就一句：**少整花活，把写章、续写、摘要、导出这四件事做到作者闭眼都信，这个软件就成了。**
