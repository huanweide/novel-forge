# Round 16 · PG（Paul Graham）方向判断裁决

## 一、核心诊断

novel-forge 最初的那个「点」应该非常清楚：它是一个**本地运行、私密、不废话的 AI 写作伴侣**，帮作者真正把一部长篇写完、写不崩。早期用户不是因为它能玩游戏、能做仪表盘才来的，而是因为它像一个只属于自己、随时能续上的写作利器。任何功能都要过这一关：**它让我更想坐下来写，还是让我觉得这工具「功能挺多」？**

逐项的裁决与方向理由：

① **写章 write — 有意义。** 这是产品的全部意义，没有它就没有 novel-forge。
② **续写 continue — 有意义。** 把「写下一章」的摩擦力降到零，正是本地写作利器该有的手感。
③ **精修 refine — 有意义。** 写作九成是改稿，能让已有正文被重写得更干净，是核心价值而非装饰。
④ **章节摘要 summarize — 有意义，且是聪明的聚焦。** 长篇崩坏的根因是上下文丢失，把章节压成中期记忆直击「不崩坏」痛点，不是绕路。
⑤ **限流 rate-limit — 待优化。** 单用户本地没有滥用者，滑动窗口更像 SaaS 思维残留；若保留，只该为「别把用户自己的 API key 打爆」这一种场景服务。
⑥ **自动填表 babylore — 待优化。** 方向对（一致性是长篇真痛点），但它把作者从「写」拽向「管卡」，必须做成不打断心流的静默提取。
⑦ **伏笔检测 foreshadowing — 待优化。** 对严肃作者有价值，但「收束率幂等重算」已像在造追踪仪表盘；它属于管理层锦上添花，不该喧宾夺主。
⑧ **游戏开局 game/start — 傻子功能。** 最典型的发散陷阱：这是写小说的平台，不是文字游戏引擎。加它只会稀释「写作利器」的最初印象。
⑨ **导出 export — 有意义。** 本地优先的哲学就是「小说是你的」，干净导出是刚需；五格式略铺张，epub/docx 可后置。
⑩ **导入 import — 有意义。** 让已有草稿能带进来，是「不被锁定」的承诺，迁移能力即可信度。
⑪ **删节点 delete — 有意义（必要管道）。** 算不上卖点，但缺了它就是残废的 CRUD，必须存在。

## 二、提升框架

我的提升框架只有一条铁律：**守住「写—续—修—记」这个核心闭环，其余一律默认砍，除非它能用一句话证明自己加深了写作利器的印象。** 写章、续写、精修、摘要构成了最小可用且真正差异化的心脏；导出、导入是本地工具的信任锚；限流、自动填表、伏笔检测是「锦上添花层」，要做也必须隐形嵌入写作流，而不是变成独立菜单和仪表盘。游戏开局则根本不在这个产品里——它是另一个公司、另一个产品的故事。

## 三、具体可落地步骤

第一，把资源集中复检并打磨核心四件套（写章/续写/精修/摘要），尤其先消掉那两个 P0 bug 的复现证据，让「写不崩」成为可被复述的口碑。第二，导出保留 markdown/txt/html 三格式即可，epub/docx 推迟到有人真正要时再做，别提前为想象中的需求付费。第三，限流降级为「保护自有 API key 的单次轻量节流」，删除那套为多人场景设计的窗口逻辑。第四，自动填表与伏笔检测合并进「写作时的静默侧栏」——正文写完后后台悄悄补卡、悄悄标伏笔，绝不让作者离开编辑器去「管理」。第五，游戏开局从路线图移除，若团队真想做，另起一个独立项目，别借 novel-forge 的壳。

## 四、风险提示

最大的风险不是某个功能没用，而是**功能总数本身在制造「我们不专注」的气质**。当一个写作工具的首屏开始和游戏、仪表盘抢注意力，早期被「纯粹写作」吸引的用户会最先流失——他们不是讨厌那些功能，而是忽然不确定这工具到底为谁而造。第二个风险是工程复杂度：限流窗口、伏笔幂等重算这类「防御性/分析性」代码，维护成本会悄悄吃掉本该投给写作质量的精力。砍掉游戏开局不是损失，是替产品找回它该有的样子。

## 五、与其他职能的张力

我和马斯克那位的「第一性原理」大概率在游戏开局上一致——它过不了「没有它用户是否被迫绕路」这一问。但和注重「严谨工程」的视角会有张力：限流、伏笔检测在工程师眼里是「健壮性/专业性」的体现，我会反驳说，本地单用户场景里这种健壮性是假想敌，真正的专业是让写作顺到作者忘了工具存在。和偏「完整体验」的视角也会冲突——他们可能认为导出五格式、游戏开局能拉新；我的立场是：拉新靠的是那一个被做透的点，不是菜单长度。方向判断的职责，就是在大家都想加东西时，提醒我们当初为什么出发。
